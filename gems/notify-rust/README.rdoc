= ferro-notify-rust

{rdoc-image:https://justin.searls.co/img/shovelware.svg}[https://justin.searls.co/shovelware/]

Desktop notifications for Ruby, through notify-rust 4.18.2.

A program that finishes a long job, or hears about something the user
cares about, should say so where the user looks: a notification in the
corner of the screen. Each system has its own way to show one: the XDG
notification server over D-Bus on Linux and the BSDs, the notification
center on macOS, toasts on Windows. Ruby's standard library has none of
them.

ferro-notify-rust binds notify-rust (https://github.com/hoodie/notify-rust)
one to one. It keeps notify-rust's names and behavior. Where Rust has no
Ruby meaning it translates, and it adds little: Ferro::NotifyRust::Future,
which stands in for the Rust futures of Linux's async calls, and
Ferro::NotifyRust::Builder, the setters a Notification shares with a Linux
or Windows handle, as Rust's +Deref+ shares them. Use it to tell the user a
build finished, ask them to approve something with an action button, or
change a notification already on screen.

ferro-notify-rust binds notify-rust 4.18.2. The gem's version follows its
own API; its +notify_rust_version+ metadata names the notify-rust release.

== Install

Add the gem to your Gemfile, with a version, or let Bundler write the line:

--
SPDX-SnippetBegin
SPDX-SnippetCopyrightText: 2026 Kerrick Long <me@kerricklong.com>
SPDX-License-Identifier: MIT-0
++

  gem "ferro-notify-rust", "~> 0.1"

  # or, from the command line:
  bundle add ferro-notify-rust --version "~> 0.1"

--
SPDX-SnippetEnd
++

The gem needs Ruby 4.0 or newer. It compiles a Rust extension when it
installs, so the machine that installs it needs:

* Rust and Cargo, 1.89 or newer (the highest +rust-version+ among the
  locked dependencies). On Windows, use Rust's
  +x86_64-pc-windows-gnu+ toolchain, since RubyInstaller's Ruby is a MinGW
  build and rb-sys refuses to build it with the MSVC target.
* libclang, which rb-sys's bindgen reads Ruby's headers with
  (<tt>libclang-dev</tt> on Debian and Ubuntu, +clang+ with the Xcode
  command line tools on macOS, LLVM on Windows).

The build runs <tt>cargo --locked</tt>, so it compiles exactly the
dependency versions this gem was tested with. To build against newer ones
anyway, set +RB_SYS_EXTRA_CARGO_ARGS+ (an empty string will do); it
replaces <tt>--locked</tt>.

Showing a notification needs more than the build does:

[Linux and the BSDs] A D-Bus session bus and a notification server on it,
                     which desktops run (GNOME Shell, Plasma, dunst, mako,
                     and others). notify-rust talks to D-Bus through zbus,
                     pure Rust, so no libdbus is linked at build time or
                     run time. With no session bus or no server, +show+
                     raises a Ferro::NotifyRust::Error.
[macOS]              Nothing to install. A notification comes from the
                     application notify-rust names, Finder unless you
                     choose another (see below), so it follows that
                     application's notification settings.
[Windows]            Nothing to install. A toast needs an application's
                     <tt>System.AppUserModel.ID</tt>. Without one,
                     notify-rust uses PowerShell's, so the toast reports
                     PowerShell as its origin. Pass your app's own with
                     +app_id+.

== Use

--
SPDX-SnippetBegin
SPDX-SnippetCopyrightText: 2017 Hendrik Sollich
SPDX-License-Identifier: MIT OR Apache-2.0
SPDX-SnippetComment: Translated from notify-rust 4.18.2 src/lib.rs:15-26
++

  require "ferro/notify_rust"

  Ferro::NotifyRust::Notification.new
    .summary("Firefox News")
    .body("This will almost look like a real firefox notification.")
    .icon("firefox")
    .timeout(Ferro::NotifyRust::Timeout::Milliseconds.new(6000))
    .show

--
SPDX-SnippetEnd
++

Each setter returns the notification, so calls chain, and +show+ sends it.
Without an argument, a method with a field of the same name returns it:
+summary+ returns the summary. A failure raises a subclass of
Ferro::NotifyRust::Error with notify-rust's message:

--
SPDX-SnippetBegin
SPDX-SnippetCopyrightText: 2026 Kerrick Long <me@kerricklong.com>
SPDX-License-Identifier: MIT-0
++

  begin
    Ferro::NotifyRust::Urgency.try_from("urgent")
  rescue Ferro::NotifyRust::Error::Conversion => e
    e.message # => "Conversion Error: invalid input \"urgent\""
    e.debug   # => "Error { kind: Conversion(\"invalid input \\\"urgent\\\"\") }"
  end

--
SPDX-SnippetEnd
++

=== Actions

+show+ returns a NotificationHandle, which can wait for the user. On Linux:

--
SPDX-SnippetBegin
SPDX-SnippetCopyrightText: 2017 Hendrik Sollich
SPDX-License-Identifier: MIT OR Apache-2.0
SPDX-SnippetComment: Translated from notify-rust 4.18.2 src/lib.rs:46-62
++

  Ferro::NotifyRust::Notification.new
    .summary("click me")
    .action("default", "default")
    .action("clicked", "click here")
    .hint(Ferro::NotifyRust::Hint::Resident.new(true))
    .show
    .wait_for_action do |action|
      case action
      when "default" then puts "you clicked \"default\""
      when "clicked" then puts "that was correct"
      when "__closed" then puts "the notification was closed" # a hard-coded keyword
      end
    end

--
SPDX-SnippetEnd
++

+wait_for_response+ yields a NotificationResponse instead, which tells a
click, an action, and a close apart without keywords, and +on_close+ yields
the CloseReason when the notification goes away. A handle can also +close+
the notification, or change it and +update+ it in place.

As in Rust, each wait, and +close+, takes the handle: afterwards any call
on it raises +IOError+, as a closed IO does. So does a handle after the end
of +show+'s block, which is its scope. On Linux, +wait_for_action_async+
and +close_async+ borrow the handle instead, so one thread can wait while
another closes.

Every wait releases Ruby's global VM lock, so other threads keep running,
and no call ever runs with the lock held. On Linux an interrupt (Ctrl-C,
<tt>Thread#raise</tt>, +Timeout+) ends a wait; notify-rust offers no way
to stop a wait on macOS or Windows, or +handle_action+, +update+,
+get_capabilities+, and +get_server_information+ on Linux, so there the
interrupt takes effect when the user answers or the call returns, and
discards what the call returned. zbus sets no timeout on a D-Bus call, so
a server that never answers blocks those Linux calls for good, as it does
in Rust.

=== macOS

On macOS, notify-rust sends a notification when its handle drops, unless
one of the handle's waits sends it and waits first. Ruby has no moment when
an object drops, so +show+ decides:

--
SPDX-SnippetBegin
SPDX-SnippetCopyrightText: 2026 Kerrick Long <me@kerricklong.com>
SPDX-License-Identifier: MIT-0
++

  # On macOS, without a block, the notification is sent at once, and the
  # handle show returns is used up. On Linux and Windows it stays usable.
  Ferro::NotifyRust::Notification.new.summary("Done").show

  # With a block, it is sent when the block ends, unless a wait sent it.
  Ferro::NotifyRust::Notification.new.summary("Approve?").action("yes", "Yes").show do |handle|
    handle.wait_for_action { |action| puts action }
  end

--
SPDX-SnippetEnd
++

Notifications come from an application: Finder, unless you choose another
with +set_application+ before the first one. notify-rust does it by
replacing what <tt>NSBundle.mainBundle</tt> reports as its bundle
identifier, and by making itself the notification center's one delegate.
Both are set once per process, so the first +set_application+ wins, and no
other library in the same process may link notify-rust or
mac-notification-sys.

A wait needs the main thread's run loop. On the main thread, it runs the
loop itself; on any other thread it finishes only while the main thread
runs its run loop, as a windowed app's event loop does, and otherwise
blocks indefinitely. On macOS notify-rust uses a notification's summary,
subtitle, body, sound, image path, and actions (as buttons named by their
labels), and ignores its icon, timeout, app name, and id; +hint+ and
+urgency+ do not exist there.

=== Windows

--
SPDX-SnippetBegin
SPDX-SnippetCopyrightText: 2026 Kerrick Long <me@kerricklong.com>
SPDX-License-Identifier: MIT-0
++

  Ferro::NotifyRust::Notification.new.summary("Build done").app_id("Example.App").show

--
SPDX-SnippetEnd
++

+app_id+ exists only on Windows, and +urgency+ only on Windows and Linux.
On Windows, a critical urgency makes the toast a reminder, which stays on
screen until the user dismisses it.

== How it maps notify-rust

The API is notify-rust's, translated where Rust has no Ruby meaning:

* Notification wraps notify-rust's builder. +dup+ and +finalize+ copy it,
  as Rust's +Clone+ does; a frozen one refuses its setters.
* +Debug+ is +debug+, which answers notify-rust's text exactly, as Rust
  formats it, on every value, handle, and error that has one; +inspect+
  stays Ruby's.
* Enums are constants (Urgency::Critical, Timeout::Never,
  CloseReason::Dismissed); variants with data are Data classes
  (Timeout::Milliseconds, Hint::Category, NotificationResponse::Action).
  A variant's fields are positional, through +deconstruct+ and +to_a+, as
  a Rust pattern reads them. +Default+ is <tt>.default</tt>. Conversions keep
  notify-rust's rules: <tt>From</tt> is +from+, <tt>TryFrom</tt> is
  +try_from+, <tt>FromStr</tt> is +from_str+, and
  <tt>i32::from(timeout)</tt> is Timeout#to_i, and
  <tt>Urgency::Critical as u8</tt> is Urgency#to_i.
* A Rust +Duration+ is a Numeric number of seconds. Timeout.from and
  Notification#timeout read an Integer as milliseconds
  (<tt>From<i32></tt>) and any other Numeric as a +Duration+, so
  <tt>timeout(2)</tt> is two milliseconds and <tt>timeout(2.0)</tt> two
  seconds, as in Rust.
* A value a Rust method consumes raises +IOError+ when used again, as a
  closed IO does: a handle after a wait, +close+, or the end of +show+'s
  block, and a Future after +value+.
* Closures are blocks, called after the wait ends, with Ruby's lock held.
* A Rust future is a Future (Linux), and <tt>.await</tt> is Future#value.
  As a Rust future does, it starts its work when first awaited, and
  answers once.
* Each kind of error is a subclass of Ferro::NotifyRust::Error with
  notify-rust's message. A wrong argument type raises +TypeError+; an
  error that is not notify-rust's own, such as Timeout.from_str's parse
  failure, raises +ArgumentError+ with Rust's message. A wait without the
  block Rust requires raises +ArgumentError+ before it waits.
* Methods a platform lacks are not defined there, so <tt>respond_to?</tt>
  answers. On Linux and Windows a NotificationHandle answers every
  Notification setter, as notify-rust's +Deref+ gives.
* notify-rust's hidden and deprecated items are not bound: the +actions+
  setter (the field still reads and writes), Notification.at_bus, and
  +show_debug+. On macOS the Urgency constant, whose export notify-rust
  deprecates there, stays, since Hint::Urgency holds one; naming it warns
  in Ruby's <tt>:deprecated</tt> category.

What differs from calling notify-rust from Rust:

* Rust refuses at compile time to change a handle a wait borrows. In
  Ruby, a setter or +update+ on a Linux handle while another thread's
  +wait_for_action_async+ or +close_async+ runs waits for that to end, as
  with a Mutex, and Ctrl-C, <tt>Thread#raise</tt>, and +Timeout+ end that
  wait; on the waiting thread itself, from a signal trap, it raises
  +ThreadError+ (<tt>already borrowed: ...</tt>). A wait or close already
  under way on another thread when a handle is used up finishes, and keeps
  the handle's D-Bus connection until it does; a setter or +update+ still
  waiting for its turn then raises +IOError+.
* On macOS, +show+ without a block uses its handle up at once, since that
  is when notify-rust sends; wait inside +show+'s block there.
* A panic inside notify-rust would end your Ruby process. It raises
  Ferro::NotifyRust::Error with <tt>notify-rust panicked: ...</tt>
  instead. Rust still prints its usual panic message to stderr first.
* notify-rust's Error keeps its kind private, so ferro reads it from
  notify-rust's +Debug+ text.
* Not bound: macOS's <tt>NotificationHandle::new</tt> (+show+ makes the
  same handle), and Image's conversions from the image crate's types (use
  Image.open).

notify-rust's Cargo features built here are +z+ (zbus, the default),
+images+, and +chrono+. Not built: +d+ and +d_vendored+, which add dbus-rs
beside zbus and link the system's libdbus; +tokio+ and +z-with-tokio+,
which need a tokio runtime around every call; +debug_namespace+, which
renames the bus for notify-rust's own tests; and +preview-macos-un+, which
replaces the macOS backend with +UNUserNotificationCenter+, a preview that
needs a signed app bundle.

The extension is Ractor-safe, and a frozen Notification, Image, or value may
cross Ractors. One caveat belongs to Ruby, not to the gem: on Windows,
Ruby 4.0.9 can hang when a Ractor starts a garbage collection while the
main Ractor has another thread asleep; ferro-arboard's README says more.
