= ferro-time

{rdoc-image:https://justin.searls.co/img/shovelware.svg}[https://justin.searls.co/shovelware/]

Dates, times, offsets, and durations for Ruby, through time 0.3.55.

Ruby's ::Time and ::Date answer most date questions, by Ruby's rules. A
program that exchanges dates with a Rust service, or must agree with
Tauri, needs the Rust side's rules instead: which ISO 8601 and RFC 3339
strings parse, how RFC 2822 writes a date, how far a date may range, and
the words an error uses. Getting those right by hand means porting a
parser step for step and keeping the port current.

ferro-time binds time (https://github.com/time-rs/time), Rust's date and
time library, one to one. It keeps time's names and behavior. Where Rust
has no Ruby meaning it translates, and it adds no class that time lacks:
the refinements under Ferro::Time::Ext are time's extension traits, and
the errors are time's error types as classes. Use it to parse a date the
way a Rust program will, format one it will read back, or do calendar
arithmetic with time's answers.

ferro-time binds time 0.3.55. Its +time_version+ metadata names the time
release; the gem's own version follows its own API.

== Install

Add the gem to your Gemfile, with a version, or let Bundler write the line:

--
SPDX-SnippetBegin
SPDX-SnippetCopyrightText: 2026 Kerrick Long <me@kerricklong.com>
SPDX-License-Identifier: MIT-0
++

  gem "ferro-time", "~> 0.1"

  # or, from the command line:
  bundle add ferro-time --version "~> 0.1"

--
SPDX-SnippetEnd
++

The gem needs Ruby 4.0 or newer. It compiles a Rust extension when it
installs, so the machine that installs it needs:

* Rust and Cargo, 1.88 or newer (the highest +rust-version+ among the
  locked dependencies). On Windows, use Rust's +x86_64-pc-windows-gnu+
  toolchain, since RubyInstaller's Ruby is a MinGW build and rb-sys
  refuses to build it with the MSVC target.
* libclang, which rb-sys's bindgen reads Ruby's headers with
  (<tt>libclang-dev</tt> on Debian and Ubuntu, +clang+ with the Xcode
  command line tools on macOS, LLVM on Windows).

The build runs <tt>cargo --locked</tt>, so it compiles exactly the
dependency versions this gem was tested with. To build against newer ones
anyway, set +RB_SYS_EXTRA_CARGO_ARGS+ (an empty string will do); it
replaces <tt>--locked</tt>.

== Use

--
SPDX-SnippetBegin
SPDX-SnippetCopyrightText: 2026 Kerrick Long <me@kerricklong.com>
SPDX-License-Identifier: MIT-0
++

  require "ferro/time"

  t = Ferro::Time
  well_known = t::FormatDescription::WellKnown

  # Parse an instant as time's ISO 8601 parser reads it:
  at = t::OffsetDateTime.parse("2026-10-26T12:00:00.000Z", well_known::Iso8601::DEFAULT)
  at.unix_timestamp # => 1_793_016_000

  # Move it, and write it back:
  later = (at + t::Duration.hours(36)).to_offset(t::UtcOffset.from_hms(9, 0, 0))
  later.format(well_known::Rfc3339) # => "2026-10-28T09:00:00+09:00"
  at.format(well_known::Rfc2822)    # => "Mon, 26 Oct 2026 12:00:00 +0000"

  # Describe your own format, checked once and used as often as you like:
  day = t::FormatDescription.parse_owned(3, "[weekday], [month repr:long] [day padding:none]")
  later.format(day) # => "Wednesday, October 28"

  # Walk the calendar:
  first = t::Date.from_calendar_date(2026, t::Month::January, 1)
  first.iter_to(t::Date.from_calendar_date(2026, t::Month::January, 4)).map(&:to_s)
  # => ["2026-01-01", "2026-01-02", "2026-01-03", "2026-01-04"]

--
SPDX-SnippetEnd
++

Every error time raises is a Ferro::Time::Error, with a class for each of
time's error types and variants nested as Rust nests them, so <tt>rescue
Ferro::Time::Error::Parse</tt> catches any failed parse. Every message is
time's own, and <tt>Error#source</tt> answers the error one holds, as
time's does:

--
SPDX-SnippetBegin
SPDX-SnippetCopyrightText: 2026 Kerrick Long <me@kerricklong.com>
SPDX-License-Identifier: MIT-0
++

  begin
    t::Date.from_calendar_date(2026, t::Month::February, 29)
  rescue t::Error::ComponentRange => e
    e.message # => "day was not in range"
  end

  begin
    t::Date.parse("2019-02-30", well_known::Iso8601::DATE)
  rescue t::Error::Parse => e
    e.source.class # => Ferro::Time::Error::TryFromParsed::ComponentRange
  end

--
SPDX-SnippetEnd
++

=== Durations and Ruby's numbers

A SignedDuration, also named Duration as in time, is time's
+SignedDuration+. Where time takes or returns std's unsigned duration,
Ruby takes any Numeric number of seconds and returns a Rational. As in
Rust, the operator picks the impl: <tt>*</tt>, and <tt>/</tt> by a
number, take a count, while <tt>+</tt>, <tt>-</tt>, comparisons, and a
number divided by a duration take seconds.

--
SPDX-SnippetBegin
SPDX-SnippetCopyrightText: 2026 Kerrick Long <me@kerricklong.com>
SPDX-License-Identifier: MIT-0
++

  minute = t::Duration.minutes(1)
  minute == 60                  # => true
  (minute + 1.5).to_s           # => "1m1s500ms"
  (minute * 3).to_s             # => "3m"
  minute.to_r                   # => (60/1)
  first + 86_400                # a day later: 2026-01-02
  first + 1                     # unchanged: one second adds no whole day
  minute / 0                    # raises RangeError: attempt to divide by zero

--
SPDX-SnippetEnd
++

time's extension traits are refinements, in effect only where you bring
them in, as Rust's are only where you +use+ them. Put +using+ at the top
of a file:

--
SPDX-SnippetBegin
SPDX-SnippetCopyrightText: 2026 Kerrick Long <me@kerricklong.com>
SPDX-License-Identifier: MIT-0
++

  require "ferro/time"
  using Ferro::Time::Ext::NumericalDuration
  using Ferro::Time::Ext::NumericalStdDuration
  using Ferro::Time::Ext::SystemTimeExt

  (5.seconds + 500.milliseconds).to_s # => "5s500ms"
  5.std_minutes                       # => (300/1)
  ::Time.utc(2026, 1, 1).checked_add_signed(2.hours) # => 2026-01-01 02:00:00 UTC

--
SPDX-SnippetEnd
++

== Ferro::Time, Ruby's Time, and Ruby's Date

Ferro::Time::Time and Ferro::Time::Date are time's types, not Ruby's
::Time and ::Date. The names are time's, and the module keeps them apart,
with one consequence: wherever ferro-time is loaded, a bare +Time+ inside
<tt>module Ferro</tt> names Ferro::Time, because Ruby looks a constant up
lexically first. Code in the Ferro namespace writes <tt>::Time</tt> and
<tt>::Date</tt> for Ruby's own.

OffsetDateTime, UtcDateTime, and Timestamp convert to and from Ruby's
::Time, which stands for Rust's +SystemTime+: OffsetDateTime.from(time),
#to_time (a UTC ::Time), and <tt>==</tt>, <tt><=></tt>, and <tt>-</tt>
with a ::Time on the right, as time's +SystemTime+ impls do. Ruby's own
::Time is not changed; its <tt><=></tt> already asks the other value
when that value is not a ::Time, so <tt>time == offset_date_time</tt> and
<tt>time < offset_date_time</tt> work as well, while
<tt>time - offset_date_time</tt> stays Ruby's +TypeError+. Timestamp
converts to and from UtcDateTime and OffsetDateTime as well, and compares
and subtracts with both. Nothing converts to or from Ruby's ::Date,
because time has no conversion for it.

== How it maps time

The API is time's, translated where Rust has no Ruby meaning:

* Rust's modules are Ruby modules: <tt>time::format_description::well_known::Rfc3339</tt>
  is Ferro::Time::FormatDescription::WellKnown::Rfc3339. The aliases
  +PrimitiveDateTime+ and +Duration+ are the same classes as PlainDateTime
  and SignedDuration.
* +Result+ raises; +Option+ is +nil+; tuples are Arrays; Month and Weekday
  are frozen constants.
* Every value is frozen and immutable, as Rust's +Copy+ values are, and
  compares, orders, and hashes as time's +PartialEq+, +Ord+, and +Hash+ do.
  +debug+ answers time's +Debug+ text, formatted by Rust, on every value
  but the errors (see below); +inspect+ is Ruby's own.
* Rust's operators are Ruby's: <tt>date + duration</tt>,
  <tt>datetime - other</tt>, <tt>duration * 3</tt>, <tt>-offset</tt>.
  Multiplying by an Integer uses time's <tt>i32</tt> impl, Rust's type
  for an integer literal, and by a Float its <tt>f64</tt> one, from either
  side: <tt>2 * duration</tt> reaches time's
  reflexive impl through SignedDuration#coerce.
* Rust's <tt>std::time::Duration</tt> is Numeric seconds in and a Rational
  out, exact to the nanosecond (see Durations above): <tt>date + 86_400</tt>,
  <tt>2 - duration</tt>, <tt>SignedDuration.try_from(1.5)</tt>,
  <tt>duration.unsigned_abs</tt>. The collision with Ruby is yours to
  mind: <tt>date + 1</tt> adds the whole days of one second, none, where
  Ruby's ::Date adds a day.
* The extension traits are Ext::NumericalDuration (Integer and Float),
  Ext::NumericalStdDuration (answering Rationals), and Ext::SystemTimeExt,
  which adds <tt>checked_add_signed</tt>, <tt>checked_sub_signed</tt>, and
  <tt>signed_duration_since</tt> to Ruby's ::Time.
* A description is a FormatDescriptionV3, the classes Rfc2822 and
  Rfc3339, an Iso8601 with any Config, or format items: a
  BorrowedFormatItem, an OwnedFormatItem, or an Array of either, as
  FormatDescription.parse_borrowed and parse_owned return for versions 1
  and 2, and parse_strftime_borrowed and parse_strftime_owned for
  +strftime+. +format_into+ appends to a String.
* Format items, components, and modifiers are frozen +Data+ values you
  can read and build: <tt>Component::Day.new(Modifier::Day.default)</tt>.
  A modifier comes only from its +default+ (or Modifier::Ignore.count)
  and its +with_+ builders, as in Rust. Naming a type or variant time
  deprecates warns in Ruby's +:deprecated+ category.
* A Timestamp counts seconds and nanoseconds from the epoch, with the
  nanoseconds always forward: <tt>Timestamp.new(-1, 500_000_000)</tt> is
  half a second before the epoch. #replace_millisecond,
  #replace_microsecond, and #replace_nanosecond differ from
  UtcDateTime's only on an instant before the epoch that has a fraction:
  there they replace the fraction as its decimal text writes it, so
  replacing the 500 ms of -0.5 with 400 gives -0.4, where a clock would
  give -0.6. A whole negative second is not special:
  <tt>Timestamp.new(-1, 0).replace_millisecond(400)</tt> is -0.6, as time
  does.
* Parsing::Parsed is time's parser state: mutable, with time's getters,
  setters (+true+ or +nil+), and +with_+ builders. Each date and time type
  has +try_from+ a Parsed and +parse_with_defaults+.
* The iterators of Iter are time's, not Ruby's Enumerator:
  <tt>date.iter_to(end_date)</tt>, Month.iter_from, and Weekday.iter_from
  make them, and +next+ advances one in place and returns +nil+ once a
  DateIter is done, never +StopIteration+. Each includes Enumerable, whose
  methods walk a copy and leave the iterator where it was. time's own
  methods keep their names (+next_back+, +nth+, +len+, +size_hint+,
  +all+, +any+, +is_sorted+); +count+ and +last+ on a never-ending month
  or weekday iterator raise +RangeError+ where Rust panics.
* The units of time are frozen values: <tt>Unit::Nanosecond.per(Unit::Second)</tt>
  is 1_000_000_000, and <tt>per_t(Float, ...)</tt> takes the output type
  first, Integer or Float. Rust's const +N+ on each unit is 1 here, the
  only value +per+ exists for. The deprecated +Convert+ is the same
  module, and naming it warns.
* time's macros check their input when Rust compiles; their run-time
  equivalents are bound. <tt>date!(2020-01-02)</tt> is
  <tt>Date.from_calendar_date(2020, Month::January, 2)</tt>; +time!+,
  +offset!+, +datetime!+, and +utc_datetime!+ are Time.from_hms,
  UtcOffset.from_hms, PlainDateTime.new with #assume_offset, and
  UtcDateTime.new; <tt>timestamp!</tt> is Timestamp.new, or Timestamp.from
  a UtcDateTime; and <tt>format_description!(version = 3, "...")</tt> is
  <tt>FormatDescription.parse_owned(3, "...")</tt>, while the macro's
  default version 1 is <tt>FormatDescription.parse_borrowed(1, "...")</tt>.

What differs from calling time from Rust:

* time panics on arithmetic that leaves its range, on a NaN or
  overflowing float, and on integer division by zero. The gem checks the
  same conditions first and raises +RangeError+ with the panic's message
  instead (<tt>duration / 0</tt> is "attempt to divide by zero"), or
  +ArgumentError+ for a failed assertion, such as a negative Float's
  +std_seconds+. Any other panic raises Ferro::Time::Error with
  <tt>time panicked: ...</tt> rather than ending your Ruby process.
* Formatting a type with a well-known format that needs more than the type
  holds, such as RFC 3339 for a Date, is a compile-time error in Rust. The
  gem raises +TypeError+ with time's assertion.
* A borrowed format item holds its own frozen copy in Ruby, so it differs
  from an owned one only by class; time never compares the two, and
  neither does the gem. A tree of items nested more than 255 levels deep,
  deeper than time's own parser goes, raises +ArgumentError+ rather than
  risk overflowing the native stack.
* Each ISO 8601 configuration is its own compiled type in Rust. The gem
  formats any configuration by formatting the date, time, and offset parts
  with time's formatters and joining them as time does; a test checks the
  result against time's own formatter.

Not bound, or bound differently, each for a reason:

* <tt>Div<std::time::Duration> for SignedDuration</tt> has no operator,
  since <tt>/</tt> by a number is a count; its value is
  <tt>duration / SignedDuration.try_from(seconds)</tt>.
* The <tt>*Assign</tt> operators are Ruby's <tt>+=</tt> and <tt>-=</tt>,
  an operator and an assignment, so <tt>x += duration</tt> leaves a
  SignedDuration in +x+ where Rust's <tt>AddAssign<SignedDuration> for
  std::time::Duration</tt> keeps std's type.
* +InstantExt+, since no Ruby class stands for std's +Instant+.
* time's hidden items.
* Rust's trait machinery that has no Ruby meaning, such as the width and
  fill of <tt>{:>8}</tt>: SignedDuration#to_s takes Rust's precision,
  <tt>duration.to_s(3)</tt> for <tt>{:.3}</tt>, and nothing else.

Four rulings of ADR 001 are not applied to ferro-time yet, so it differs
from the Rust API's shape in these ways (plan 007's follow-up has the
reasons):

* The errors do not answer +debug+. time's error types derive +Debug+
  with fields the Ruby classes do not keep, such as a ComponentRange's
  minimum, maximum, and value.
* time's iterators are consumed by <tt>rev</tt>, <tt>count</tt>,
  <tt>last</tt>, and <tt>is_sorted</tt> in Rust. Here each runs on a copy
  and leaves the iterator usable, where a consumed one should raise
  +IOError+.
* time's deprecated items are bound, and warn in Ruby's +:deprecated+
  category: <tt>FormatDescription.parse</tt>,
  <tt>Util.days_in_year_month</tt>, <tt>Convert</tt>, <tt>FormatItem</tt>,
  six deprecated +Component+ variants, the
  deprecated +Literal+ items, and the deprecated modifier enums. Tauri
  uses none of them, so a later release removes them.
* The format items and components that are tuple variants in Rust, such
  as BorrowedFormatItem, OwnedFormatItem, and +Component+, are +Data+
  classes with named readers (+literal+, +component+, +compound+, +item+,
  +items+, and each component's modifier) that time does not name, where a
  later release makes them positional. The error variants that are tuple
  variants in Rust, such as Error::Format::InvalidComponent, are
  positional already: they answer +deconstruct+ and +to_a+.

time's +large-dates+ feature is off, as Tauri and its plugins build time,
so years run from -9999 to 9999. The +serde+, +rand+, +quickcheck+, and
+wasm-bindgen+ features are off: they serve Rust callers only.

The local offset (UtcOffset.current_local_offset,
OffsetDateTime.now_local) comes from the system's time-zone rules and is
safe in a multi-threaded process, as time guarantees. Util.refresh_tz
refreshes those rules only where time can prove the call sound: on macOS
it runs and returns +true+, and on Linux, where a Ruby process is never
single-threaded, it returns +nil+. On Windows, where time has nothing to
refresh, it returns +true+ and does nothing.

The extension is Ractor-safe, and every value of time's types the gem
makes is frozen and shareable, but for Parsing::Parsed and the iterators
of Iter, which are mutable and stay in the Ractor that made them. The
errors it raises and the Arrays it returns, such as a version 1
description from FormatDescription.parse_borrowed, are not frozen, as
Ruby leaves exceptions and Arrays. One caveat belongs to Ruby, not to the
gem: on Windows, Ruby 4.0.9's scheduler can hang when a Ractor starts a
garbage collection while the main Ractor has another thread asleep (in
+sleep+ or Queue#pop) and its main thread waits in Ractor#value. It
happens without ferro-time, and Ruby 4.1 replaces the Windows scheduler
involved. ferro-arboard's README says more.
