# Plan 013: The pre-push hook on a machine with nothing installed

## Context

Plan 012 moved the gate to `.githooks/pre-push` and gave Ferro
`bin/setup`. The hook assumed someone had run `bin/setup` first, that
mise was activated, and, on Linux, that the packages ci.yml's "Install
display servers" step installs with sudo were already there.

A CI runner, a build machine, or a contributor's tool may check out the
commit you push and run the hook there with git's arguments and ref
lines, and nothing before it: no `bin/setup`, no mise activated, no root,
and none of Ferro's system packages. Tokra, Ferro's sibling, made its
hook enough on its own the same week (its plans 061 and 068). This plan
does the same for Ferro, on Linux and macOS.

## Problem

Run alone, the hook stopped at its first `bundle`: there was no Ruby and
no bundle. Set up by hand, it stopped on Linux at the first compile.
rb-sys reads Ruby's headers through bindgen, which loads libclang, and
clang then looks for its own headers (`stdbool.h` among them) beside
libclang. A machine with only the system compiler has neither.

Two stock Ubuntu machines without root, 24.04 under WSL2 and 26.04, were
asked which of ci.yml's packages they have (`dpkg-query -W`):

| Package | 24.04 | 26.04 |
| --- | --- | --- |
| `xvfb`, `xauth`, `dbus`, `pkg-config`, `libwayland-dev` | yes | yes |
| `libclang-dev`, and clang's headers | no | no |
| a libclang library | no | `libclang1-21`, left by something else |
| `xdotool`, `dunst`, `sway` | no | no |
| `x11-xserver-utils` (`xmodmap`) | no | yes |
| `bubblewrap` | 0.9 | 0.11 |

Without libclang nothing compiles. Without `xdotool`, `xmodmap`, and
`dunst`, ferro-global-hotkey's and ferro-notify-rust's real tests skip
(their test helpers' `PROGRAMS`), so the hook would pass while checking
less than CI does.

On the 26.04 machine, with `bin/setup` run first and bindgen pointed at
GCC's own headers (`BINDGEN_EXTRA_CLANG_ARGS="-I$(gcc
-print-file-name=include)"`), the whole gate passed under `xvfb-run` in
94 seconds on a warm build. That shows nothing else in the gate needs a
package. GCC's headers standing in for clang's is luck, not a fix, and
the 24.04 machine has no libclang to point anywhere.

## Decided

### The hook sets Ferro up

Once the hook has checked the push, it runs `bin/setup --gate`, then the
gate through `mise x --`, so the tools are mise.toml's whether or not
mise is activated. It writes what setup prints to
`tmp/pre-push-setup.log`, which git ignores; if setup fails, it shows the
last 40 lines and refuses the push with setup's status. A push the hook
refuses, or one that moves no branch, sets nothing up.

`bin/setup --gate` installs what the gate needs: `mise install`, the
REUSE tool, and the bundle, with ci.yml's frozen `vendor/bundle` when
`CI=true`. It leaves the pre-push stub and pre-commit's hook, which only a
person's clone wants: a hook that wrote them would write into whatever
clone runs it. Any other argument stops it with its usage before it
installs anything. This is Tokra's `--gate`, without its submodule, its
RDoc, and its Windows steps, which Ferro does not have.

Three ways were weighed, as Tokra weighed them. Plain `bin/setup` in the
hook would write the stub and the commit hook into every clone the hook
runs in. Leaving setup to whoever runs the hook is how it stood. Skipping
setup when a stamp of the lockfiles says nothing changed would save the
second or so a warm setup costs, against a gate of minutes, at the risk
of a stamp that is wrong; not worth it.

### Linux gets ci.yml's packages without root

`bin/linux-env` runs a command with ci.yml's apt packages in place. It is
Tokra's (its plan 068), ported with two changes: it reads the package
list from Ferro's "Install display servers" step, and it marks a command
it already wraps with `FERRO_LINUX_ENV`. `bin/setup` runs `bundle
install` through it, so the packages are fetched during setup, whose log
the hook shows if a download fails, and the hook runs the gate through
it.

It runs the command unchanged off Linux, without `dpkg-query` (off
Debian's family), when `dpkg-query` says every package is installed (as
on CI), and under itself. Otherwise:

1. `apt-get --simulate --no-install-recommends install` with ci.yml's
   packages lists what an install would bring, at the versions the
   system's package lists name. A simulation needs no root.
2. `apt-get download` fetches each from the distribution's mirrors,
   checking every file against the package lists and the lists against
   the distribution's signed `InRelease` files, as an install does. Files
   move into `tmp/linux-env/debs/` only once apt exits 0.
3. `dpkg-deb -x` unpacks each into `tmp/linux-env/KEY/root/`, moving what
   a package ships in `/bin`, `/sbin`, or `/lib` into `usr/` on a system
   whose `/bin`, `/sbin`, and `/lib` link there.
4. A tree of symbolic links joins the system's `/usr` and `/etc` with the
   unpacked ones; where both have a file, the unpacked one wins.
5. The command runs under bubblewrap, with the trees bound over `/usr`
   and `/etc`. Every file sits where its package put it, so bindgen finds
   libclang where it looks by default, libclang finds clang's headers
   beside itself, and the tests find `xdotool`, `xmodmap`, and `dunst` on
   `PATH`.
6. The first build makes what the packages' install scripts would have
   made, where a package it unpacked has the files for it: GLib's
   compiled schemas and gdk-pixbuf's loader cache.

`KEY` digests the package list, dpkg's status file, and the folder's
path, so a second run reuses the build in milliseconds, and installing a
system package or changing ci.yml's list builds again, downloading only
what is new. A lock keeps two runs in one checkout from building at once.

ci.yml's list includes `sway`, which only CI's Wayland pass uses, and the
hook does not run that pass. It stays in: one list, read from one place,
keeps the hook and CI from drifting, and its packages cost seconds to
fetch.

Considered:

- **bindgen pointed at GCC's headers**, as in the run above. It needs a
  libclang the machine may not have, and clang parsing with GCC's
  `stdbool.h` works by accident.
- **libclang from PyPI's wheel, and clang's headers from LLVM's source
  release**, as Tokra does on Windows (`bin/clang-headers`). Two more
  pins and checksums, and it would still leave `xdotool`, `xmodmap`, and
  `dunst` missing, which no wheel brings. apt fetches all of them, checked
  against the distribution's signed lists.
- **An overlay filesystem, settings alone, fuse-overlayfs, or a whole
  root filesystem**: Tokra's plan 068 tried each and says why each fails
  or costs more.

No new gem or crate. On Linux the setup uses `apt-get`, `dpkg-query`,
`dpkg-deb`, and `bwrap`, which a Debian or Ubuntu machine has once
bubblewrap is installed, and CI's runner does not need them.

### macOS

`bin/setup --gate` and the hook do the same there, with `bin/linux-env`
running every command unchanged. What the gate does on a Mac with no
desktop session is recorded below; making the tests that touch the
desktop behave there is plan 014's.

### Windows is deferred

Windows has no `bin/setup.ps1`, and Tokra's Windows setup, the model for
one, is changing this week. A Windows plan follows it, so Ferro ports
the settled version once rather than twice. Until then the hook and
`bin/setup` are untested on Windows, as plan 012 left them.

## Tests

Written first, against the real hook and the real `bin/setup`:

- `test/tasks/test_pre_push_hook.rb` stands in for `bin/setup`,
  `bin/linux-env`, and `mise` too. A gated push runs `bin/setup --gate`
  before the gate, with what it printed in the log; a failing setup
  refuses the push with its status and its last words, before the gate;
  the gate runs through `mise x --`, and on Linux through
  `bin/linux-env`, which a test checks by the environment the gate gets.
  Every refused push still runs nothing, setup included.
- `test/tasks/test_setup.rb` checks what `--gate` installs for a person
  and for a runner, that it writes no stub, that an unknown argument
  installs nothing, that `bundle install` runs through `bin/linux-env`,
  and, through a real `git push`, that the shipped hook runs the shipped
  `bin/setup` before the gate, without pre-commit's hook.
- `test/tasks/test_linux_env.rb`, ported from Tokra's, drives `LinuxEnv`
  with stand-ins for `dpkg-query`, `apt-get`, `dpkg-deb`, and `bwrap` on
  any system, with no network: when it runs a command unchanged, what it
  asks apt, what it downloads, unpacks, and binds, when it builds again,
  what a failed download or simulation says, and how the tree of links
  joins the two sides. One test reads the real ci.yml's list.

## What the runs showed

Each run started `.githooks/pre-push` and nothing else, in an empty
workspace with an empty home, with `CI=true`, mise on `PATH` but not
activated, no root, and one ref line for the checked-out commit.

- On Ubuntu 24.04 under WSL2, which has no libclang at all, the hook
  passed in 287 seconds, setup and every compile included.
- On Ubuntu 26.04, whose stray `libclang1-21` has no headers beside it,
  it passed in 443 seconds. The unpacked `libclang-dev` and its headers
  win over the system's library, so bindgen found clang's headers with
  no setting.
- Both skipped what CI's X11 pass skips, gem by gem (6, 19, 13, 8, 0, 2,
  and 0), where the gate run by hand above skipped 40 of
  ferro-notify-rust's tests and 26 of ferro-global-hotkey's for want of
  `dunst`, `xdotool`, and `xmodmap`.
- ferro-url made 916 assertions on both, and 926 on CI's runner, in the
  same 130 tests. The gate run by hand made 916 too, so the difference is
  the machines', not this change's.
- `git status` was clean after each run: the log, the unpacked packages,
  and the bundle all land in ignored folders.
- On a Mac in launchd's System session, with no window server, setup
  installed everything and the tooling tests passed (218, 2 skipped, the
  two that run only on Linux). The gate then stopped at
  ferro-arboard's Ruby tests, after 344 seconds in all: there is no
  pasteboard there, so `Clipboard.new` raised `ClipboardNotSupported`
  (10 failures and 43 errors of 94 tests), and no later gem ran. Plan
  014 sorts the tests that need a desktop from the rest.

## Plan 012's "Left for later"

- "`bin/setup` does not check Linux's system packages": closed on Debian
  and Ubuntu, where `bin/linux-env` brings them. Elsewhere a missing one
  still fails the compile, which names it.
- The Windows item stays open (above), and so do the REUSE pin and
  `rake package:install` after a `CI=true` setup, which this plan does not
  touch. The Mac item is plan 014's.

## Left for later

- Windows (above).
- The package lists are the system's. Once a mirror no longer has the
  versions they name, `apt-get download` fails and says so, and `sudo
  apt-get update` fixes it; lists of `bin/linux-env`'s own would not need
  root.
- Debian's family only. On another Linux, `bin/linux-env` runs the
  command as it is, and you install the packages the way that system does.
- The hook runs the whole gate, where a pre-push check is best kept to
  about a minute. Narrowing it is a decision of its own.
