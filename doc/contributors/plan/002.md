# Plan 002: Bind rfd

Tokra's dialog plugin needs native file and message dialogs, and ADR 001
puts rfd in Ferro's first phase: it keeps no process-wide state, so a
second copy is harmless. This plan adds `ferro-rfd` 0.1.0.pre.1, which binds
rfd 0.17.2, the latest release (crates.io, published 2026-01-12; Tokra's
ADR 011 research read the same release). [ADR 001](../adr/001.md) and
[plan 001](001.md) hold the rules and lessons this plan follows.

## Design decisions

1. **Builders are Ruby objects that rfd replays.** Each builder keeps the
   arguments its setters received, as frozen values, and its terminal
   method hands them to the native layer, which builds rfd's builder with
   rfd's own setters and runs the terminal call. This is plan 001's
   decision 1, for the same reasons: RDoc and RBS describe Ruby, and the
   native layer stays one small function per terminal call. rfd's setters
   run at replay, so their logic is rfd's: an empty `set_directory` path
   clears the directory (`src/file_dialog.rs:63-71`), and a second
   `set_title` replaces the first. Setters return the builder; rfd's
   consume `self` and return `Self`, and Ruby has no moves. rfd's terminal
   methods consume the builder too, so under ADR 001's ruling of
   2026-11-05 a terminal method uses the Ruby builder up: any later call
   on it, a setter, a terminal, or `debug`, raises `IOError`
   ("Ferro::Rfd::FileDialog consumed by FileDialog#pick_file"), as a
   closed IO does. The mark is set as the call starts, so a call that
   raises uses the builder up too, as Rust's move would. A frozen builder
   cannot take the mark, so its terminal methods raise Ruby's
   `FrozenError`; `dup` gives an unused copy, as rfd's `Clone` does. No
   block form: nothing is tied to a builder's scope. (The first version
   let a terminal method run again.) Ivars are replaced, never
   mutated, so `dup` and `clone` give independent builders, as rfd's
   `Clone` does, a frozen builder refuses its setters with Ruby's own
   `FrozenError`, and `Ractor.make_shareable` shares one. The async
   builders hold a sync one, as rfd's do (`src/file_dialog.rs:182-185`,
   `src/message_dialog.rs:92-93`), and each setter replaces it with a
   changed copy, so a frozen async builder refuses its setters too.
2. **`debug` is rfd's `Debug`; `inspect` stays Ruby's** (ADR 001,
   2026-11-05; the first version made `inspect` the `Debug` text). The
   builders derive `Debug`, so the native layer replays the builder and
   formats it with `{:?}`. That text is the crate's own account of its
   state, and the tests read it, so a setter that never reached rfd fails
   them. The enums (`src/message_dialog.rs:153`, `:161`, `:179`),
   `FileHandle` (`src/file_handle/native.rs:173-177`), and the
   raw-window-handle values (raw-window-handle 0.6.2 `src/windows.rs:11`,
   `:51`, `src/unix.rs:7`, `:47`, `:81`, `:121`, `src/appkit.rs:8`, `:87`)
   answer `debug` the same way, Rust rebuilding the crate's value and
   formatting it. `AppKitWindowHandle#debug` exists only on macOS, where
   it looks the window up as a dialog's parent is (plan 008); elsewhere
   no number names a view. The Ruby-only types (`Future`, `Error`) and
   the parent protocol have no `Debug` of rfd's.
3. **The async API returns futures.** Rust's `async` returns a value that
   finishes later, and what starts the work differs by platform. On macOS
   rfd starts the dialog when you call `pick_file` (`ModalFuture::new`,
   `src/backend/macos/modal_future.rs:37-122`): with a running
   `NSApplication` and a window it begins a sheet and returns at once, and
   the sheet finishes on the main thread's run loop. On Windows and Linux,
   nothing happens until the future is polled
   (`src/backend/win_cid/file_dialog.rs:14-29`,
   `src/backend/xdg_desktop_portal.rs:19-34`). A Ruby method that blocked
   until the result arrived would lose the macOS case, which rfd's docs
   and example recommend (`src/lib.rs:79-86`, `examples/async.rs`): start
   on the main thread, return to the event loop, and wait elsewhere.
   Blocking there would deadlock, since the main thread would wait for
   its own run loop. So each async terminal method returns a
   `Ferro::Rfd::Future`, wrapping rfd's future unchanged, and
   `Future#value` waits for it. `value` is Ruby's own name for waiting on
   a concurrent result (`Thread#value`, `Ractor#value`); Rust has no
   method here, only the `.await` syntax, so the name is Ruby's (tier 1).
   `.await` consumes the future, so under ADR 001's ruling of 2026-11-05
   the `value` that returns its answer, or raises the exception it
   finished with, uses the `Future` up, and a later `value` raises
   `IOError` (the first version returned the same value every time, as
   `Thread#value` does). An interrupted wait does not use it up, as a
   future polled through `Pin<&mut _>` stays pollable until it is ready.
   A Ruby `Mutex` lets one thread wait at a time.
   It polls once with the GVL held, then waits with the GVL released and
   an unblocking function that unparks the waiting thread (recorded where
   it parks, since a Ruby thread can resume on another native thread under
   the M:N scheduler), so Ctrl-C,
   `Thread#raise`, and `Timeout` interrupt the wait without cancelling the
   dialog, and a later `value` waits on. The native layer reports a
   finished future as a tagged Array (`[:handle, path]`, `[:raise,
   exception]`, and so on) rather than raising, so an exception that
   escapes it is an interrupt's and is never kept as the outcome. rfd's
   call that starts the dialog runs when the terminal method runs, not at
   the first poll, so macOS opens its sheet at once as rfd does.
   On macOS, `value` on the main thread refuses to wait for a sheet that
   needs the main thread's run loop and raises `ThreadError` (amended
   2026-11-05; it was `Error`) instead of deadlocking (decision 5).
4. **The GVL.** Every sync terminal method blocks on the user, so it runs
   with the GVL released, using plan 001's `gvl.rs` with no unblocking
   function: rfd cannot cancel a dialog, so Ctrl-C and `Thread#kill` take
   effect when it closes, and process exit waits for it. Creating an async
   future releases it too on macOS, where creation can run a whole modal
   (the fallback at `modal_future.rs:104-119`) or wait for the main thread
   (`dispatch2::run_on_main`); on Windows and Linux creation runs nothing
   and keeps the GVL. While the GVL is released the native layer touches
   no Ruby object, and the work catches its own panics. On macOS a modal
   dialog on the main thread runs a nested run loop, and the GVL is
   released meanwhile; any native code the run loop calls must not call
   Ruby without taking the GVL. tao, which Tokra runs, queues its events
   while its own callback is running instead of re-entering it
   (tao 0.37.2 `src/platform_impl/macos/app_state.rs:323-325`, `:369-374`,
   `:388-390`), so a dialog opened from a Tokra handler does not re-enter
   Ruby. The call is `rb_thread_call_without_gvl` inside magnus's
   `protect`, as plan 001, decision 14 now has it (amended 2026-11-05; see
   Follow-up: the GVL is never held), so a dialog never runs with the GVL
   held.
5. **Threads and event loops, per platform.** The table says what rfd
   does and what ferro-rfd does about it.

   | Platform, call | rfd 0.17.2 | ferro-rfd |
   |---|---|---|
   | macOS, sync, main thread | runs the dialog (`src/backend/macos/utils.rs:20-23`) | runs it, GVL released |
   | macOS, sync, other thread, `NSApp` running | runs it on the main thread and waits (`utils.rs:24-27`) | runs it, GVL released; the main thread must be pumping its run loop |
   | macOS, sync, other thread, no running `NSApp` | panics (`utils.rs:29`), after touching `NSApplication` from the wrong thread | refuses first: `Error`, `rfd panicked: ` and rfd's message |
   | macOS, async file dialog or message with a parent, other thread, no running `NSApp` | panics (`modal_future.rs:116-118`) | refuses first: `Error`, `rfd panicked: ` and rfd's message |
   | macOS, async, other thread, running `NSApp` without a window | panics (`modal_future.rs:116-118`) | the panic is caught: `Error`, `rfd panicked: ...` |
   | macOS, async message without a parent | runs `CFUserNotificationDisplayAlert` on a thread of its own (`utils/user_alert.rs:177-196`) | from any thread |
   | macOS, `Future#value` on the main thread while a sheet is pending | would deadlock | refuses: `ThreadError` |
   | Windows, any thread | initializes COM per call (`win_cid/utils.rs:15-35`); a thread already in a multithreaded apartment gets `None` | as rfd |
   | Linux (xdg-portal), any thread | asks the portal over D-Bus, else runs `zenity`; with neither, logs and returns `None` or `Cancel` | as rfd; `nil` |

   rfd asks `+[NSApplication sharedApplication]` before it panics, which
   creates the application on the wrong thread: a scratch program that
   called `pick_file` on a spawned thread found AppKit's `NSApp` null
   before and set after the caught panic. So the check reads the `NSApp`
   global itself (null until an application exists) and sends
   `isRunning` only to an existing one, through objc2, which rfd already
   links; the main-thread test is objc2's `MainThreadMarker::new`.
6. **`set_parent` takes a parent that answers `window_handle` and
   `display_handle`.** rfd takes `&W` where `W: HasWindowHandle +
   HasDisplayHandle`, and reads both handles at once, keeping each only if
   the call succeeds (`src/file_dialog.rs:96-103`). A trait bound is a
   duck type in Ruby: `set_parent` calls `parent.window_handle` and
   `parent.display_handle`, each returning a raw-handle value or `nil`
   (rfd's `.ok()` turns an error into `None`; Ruby's `nil` is that `None`).
   The values are raw-window-handle's structs as `Data` classes, holding
   Integers, so they cross from any gem (ADR 001, Context 1).

   A raw handle is unsafe: nothing proves the window exists. Only the kinds
   rfd never dereferences are bound, so a stale or made-up handle cannot
   corrupt memory:

   - `Win32WindowHandle`: rfd passes the `HWND` to `IFileDialog::Show` and
     `MessageBoxW` (`win_cid/file_dialog/dialog_ffi.rs:114-118`,
     `win_cid/message_dialog.rs:205-213`). An `HWND` is a handle Windows
     validates, not a pointer; a bad one fails the call, which rfd returns
     as `nil` or `Cancel`.
   - `XlibWindowHandle` and `XcbWindowHandle`: the portal backend formats
     the window ID as text, `x11:<hex>`, and never reads the display
     (`xdg_desktop_portal/window_identifier/mod.rs:33-43`, `:70-83`).

   Not bound as raw-window-handle has them, because rfd dereferences
   them: `AppKitWindowHandle`, whose `ns_view` rfd retains and asks for
   its window (`src/backend/macos/utils.rs:34-45`), and
   `WaylandWindowHandle`, whose surface and display pointers
   wayland-backend reads (`window_identifier/wayland.rs:25-44`). An
   Integer from Ruby could be anything, and a wrong one crashes the
   process. [Plan 008](008.md) binds `AppKitWindowHandle` by the window's
   `windowNumber`, which AppKit looks up and rejects safely, and builds
   the `ns_view` rfd takes from the window it finds (plan 008, decisions
   1-3); it records why Wayland stays unbound (decision 7), and reads
   handles by kind (decision 8). Without a parent, rfd's macOS async file
   dialogs attach to the app's main window anyway (`modal_future.rs:71-75`).

   Kinds rfd would panic on are refused in `set_parent` with rfd's panic
   text verbatim as an `ArgumentError` (ADR 001's error rule; the first
   version dropped the `unreachable!` prefix): on Windows anything but
   Win32 (`dialog_ffi.rs:154-158`, `win_cid/message_dialog.rs:53-57`,
   "internal error: entered unreachable code: unsupported window handle,
   expected: Windows"), and on macOS every bound kind but AppKit
   (`utils.rs:43`, "... expected: MacOS"). A Rust test drives rfd's real
   panic with an Xlib parent and compares: on macOS through
   `AsyncFileDialog::pick_file`, which converts the parent on the calling
   thread before it builds anything (`backend/macos/file_dialog.rs:50-51`),
   and on Windows through `FileDialog::pick_file`, which converts it
   before it shows anything (`dialog_ffi.rs:151-161`). On Linux
   rfd ignores kinds it cannot use (`window_identifier/mod.rs:41`), and so
   does the gem. A zero `hwnd` or `hinstance`, Xcb `window` or
   `visual_id`, or display address raises `RangeError` with the text
   Rust's `TryFromIntError` gives for one ("number would be zero for
   non-zero type"), since raw-window-handle holds them as `NonZero`
   values. The handle values are `Data` with every field, as ADR 001's
   table makes a struct with public fields. The structs are
   `#[non_exhaustive]`, so raw-window-handle's `new` is how Rust code
   makes one, and it fills the optional fields: `hinstance` with `None`,
   Xlib's `visual_id` with 0, Xcb's with `None` (`src/windows.rs:83-88`,
   `src/unix.rs:71-76`, `:145-150`). The Ruby values default those fields
   the same way, so `Win32WindowHandle.new(hwnd)` works as Rust's does.
   Message dialogs on Linux take no
   parent (`xdg_desktop_portal.rs:297-341` runs zenity without one). The
   parent works only while its window lives, and on Windows a dialog owned
   by another thread's window waits on that thread's message loop.
7. **Cargo features.** `xdg-portal`, `wayland`, and `file-handle-inner` are
   built; `wayland` has a cost, and two features are not built:
   - `wayland` links the system's `libwayland-client` (wayland-sys
     0.31.11 `build.rs` probes it with pkg-config), so building on Linux
     needs `pkg-config` and libwayland's development files, and the
     library must exist at run time even under X11. rfd uses it only to
     name a Wayland parent window (`window_identifier/mod.rs:8-9`,
     `:34-38`), which ferro-rfd does not bind yet (decision 6), so today
     it costs a dependency and buys nothing. It stays on anyway: it is
     rfd's default, so a Rust program built on rfd links the same
     library, every feature is on (AGENTS.md), and binding Wayland
     parents later needs it.
   - `gtk3` and `xdg-portal` exclude each other (`build.rs` panics with
     both). rfd's default is `xdg-portal`, and three things argue against
     `gtk3` beside the default. rfd's GTK backend runs GTK on a thread of
     its own (`src/backend/gtk3/utils.rs:7-50`), and GTK is single-threaded,
     so in a GTK host app, Tokra on Linux among them, two threads would
     drive GTK. When GTK cannot start (no display), that thread exits and
     every dialog call waits forever on a condition variable no one signals
     (`utils.rs:29-34`, `:77-82`), a hang no Ruby code can detect. And
     building it needs GTK's development headers on every Linux machine
     that installs the gem. Tauri builds `gtk3` by default
     (tauri-plugin-dialog 2.8.3 `Cargo.toml:21-23`); Tokra can weigh that
     when it ports the plugin. Offering both would need an install-time
     switch and a second Linux build in CI, which waits for a user who
     needs GTK.
   - `common-controls-v6` makes rfd call `TaskDialogIndirect`, which only
     version 6 of ComCtl32 exports, and rfd says the application needs a
     manifest that selects it (`src/lib.rs:88-98`). windows-sys links it as
     a load-time import (windows-link 0.2.1 `src/lib.rs:18-28`, `raw-dylib`),
     so without the manifest the extension would fail to load. The
     application is `ruby.exe`, whose manifest declares no Common-Controls
     dependency (Ruby `win32/ruby.manifest`), and a gem cannot change it.
     UNVERIFIED on Windows here. Without the feature, rfd shows
     `MessageBoxW`: the custom-button variants show the standard buttons
     and return `Ok`, `Cancel`, `Yes`, or `No`
     (`win_cid/message_dialog.rs:43-51`, `:204-222`). An isolation-aware
     manifest embedded in the extension (resource ID 2) could select
     ComCtl32 v6 for its own imports; that needs a Windows machine to prove.
8. **Enums.** Unit variants are frozen instances named for the variant
   (plan 001, decision 7): `MessageLevel::Warning`,
   `MessageButtons::YesNo`, `MessageDialogResult::Cancel`. Variants with
   data are `Data` classes whose members take the names rfd's backends
   bind them to (`src/backend/macos/message_dialog.rs:49-58`, `:117-134`):
   `MessageButtons::OkCustom.new(ok_text)`,
   `OkCancelCustom.new(ok_text, cancel_text)`,
   `YesNoCancelCustom.new(yes_text, no_text, cancel_text)`, and
   `MessageDialogResult::Custom.new(custom)`. `Default` becomes `.default`.
   `MessageDialogResult#to_s` is rfd's `Display`; `==` is `PartialEq`, by
   variant for the unit instances, so a `dup`, `clone`, or `Marshal` copy
   equals its original as rfd's `Clone` does, and by value for `Custom`.
   Every variant has the enum's type, as in Rust: `MessageButtons` and
   `MessageDialogResult` are modules that the unit instances' private
   class and each `Data` variant include, as ferro-url's `Host` is
   ([plan 005](005.md), decision 4; [plan 009](009.md), decision 4). A
   value that
   is not one of these raises `TypeError`, as Rust's type checker would.
9. **Strings and paths.** `impl Into<String>` takes a String; `add_filter`'s
   `&[impl ToString]` takes an Array whose elements become Strings with
   `to_s`, since `ToString` formats any `Display` value. `set_directory`
   takes a String or an object with `to_path`, through `File.path`, which
   refuses a NUL byte with Ruby's own `ArgumentError`. Paths pass byte for
   byte on Unix; returned paths are Strings in the filesystem encoding.
   rfd's portal backend unwraps `CString::new` on each filter name and
   `*.extension` (`src/backend/xdg_desktop_portal.rs:47-65`), so a NUL
   byte there panics on Linux; `add_filter` refuses one there with
   `ArgumentError` and that panic's text, such as "called
   `Result::unwrap()` on an `Err` value: NulError(2, [116, 101, 0, 120,
   116])", which the native layer builds from the same conversions; a
   Linux Rust test drives rfd's real panic to pin it. For
   `AsyncFileDialog` rfd's panic happens on a thread of its own, and the
   future resolves to `None` (`xdg_desktop_portal.rs:28-32`), so the
   caller would not crash; `add_filter` refuses there too, because no
   Ruby-reachable input may panic the crate, even on rfd's thread, which
   also prints the panic to standard error. Elsewhere rfd takes
   the byte without panicking, so the gem does too: refusing what the
   crate accepts is not fidelity, as ferro-arboard's image guard found
   (plan 001, decision 4). (The first version refused it on every
   platform with Ruby's "string contains null byte".) Titles,
   descriptions, and button labels with a NUL byte panic nowhere in the
   backends built here, so they pass. The native layer checks again at
   the terminal call, so a call around the builder cannot reach rfd with
   one.
10. **FileHandle.** rfd's handle wraps a path (`native.rs:113-114`), and its
    field is private, so it is a class, not `Data`. `From<PathBuf>` becomes
    `FileHandle.new(path)` and `From<FileHandle> for PathBuf` becomes
    `to_path`, Ruby's own conversion to a path, so `File.read(handle)`
    works. Instances are frozen and shareable. `read` and `write` return
    futures, as `async fn` does. `read` unwraps the read's result
    (`native.rs:48-56`), so an unreadable path panics in rfd; the panic is
    caught and raises `Error` (`rfd panicked: ...`), since rfd has no error
    to refuse it with and a path checked first could change before the
    read. `write` returns `std::io::Result<()>`: an error with an OS code
    raises the matching `Errno` class on Unix; Windows' codes are not
    errno values, so there, and for errors without a code, it raises
    `IOError` with Rust's message.
11. **No panic reaches Ruby** (plan 001, decision 5). Every rfd call and
    every poll runs under `catch_unwind`. A panic raises
    `Ferro::Rfd::Error` with `rfd panicked: <message>`. rfd has no error
    type of its own, so `Error` is Ferro's, and under ADR 001's error rule
    it carries only rfd's panics: those caught, and on macOS the two
    thread refusals of decision 5, which raise exactly what the caught
    panic would, `rfd panicked: ` and rfd's text, but before rfd creates
    the application on the wrong thread. A future that panicked is dropped
    and its exception kept for the `value` that uses the future up.
12. **Ractors (ADR 001, section 7).** rfd's builders are `Send`
    (`src/file_dialog.rs:30-33`, `src/message_dialog.rs:24-26`), and a call
    may come from any thread, macOS's checks included, so the extension is
    marked Ractor-safe. The Ruby builders, handle values, and `FileHandle`
    are frozen-shareable; a `Future` holds a Ruby `Mutex` and stays with
    its Ractor. On Windows, the Ractor tests run in a child process, for the
    Ruby 4.0.9 barrier bug plan 001 found.
13. **Dependencies.** rfd `=0.17.2` with `file-handle-inner` beside its
    defaults. raw-window-handle `0.6.2`, rfd's own, to hand rfd a parent.
    objc2 `0.6.5` (macOS), rfd's own, for decision 5's check. magnus
    `0.9.3` with `bytes`, as ferro-arboard has it, and rb-sys `0.9.130`.
    The tests use Fiddle, a gem Ruby bundles, only in child processes
    that run outside Bundler.
14. **Two gems in one rake run.** rb_sys's `rb_sys:env:default` task sets
    `RB_SYS_CARGO_MANIFEST_DIR` with `||=` (rb_sys 0.9.130
    `extensiontask.rb:106-110`), every extension task shares it, and each
    Makefile assigns the variable with `?=` (rb_sys `mkmf.rb:77`), so the
    environment wins and the second gem compiled the first gem's crate:
    `compile:rfd` copied a `libferro_rfd` that cargo never built.
    `FerroExtensionTask` now leaves the variable unset, and each Makefile
    names its own crate.

## Follow-up: the GVL is never held

An audit of errors the gems make themselves found the defect plan 001's
follow-up fixed in ferro-arboard here too. `gvl.rs` released the GVL with
`rb_thread_call_without_gvl2`, which skips the work whenever any interrupt
is pending (`thread.c:320-327` at Ruby v4.0.9), and after three skips in a
row ran it with the GVL held: a sync dialog then stalled every Ruby thread
until the user answered, and `wait` polled once with the GVL held and
looped, forever, which spun with the GVL held. Three skips need an
interrupt Ruby holds back, which is certain inside a user-defined
`Exception#backtrace`: Ruby calls it with the thread marked as raising
(`eval.c:542-543`, `error.c:1929`), and a thread so marked runs no
interrupts (`thread.c:2625`).

`gvl.rs` now takes arboard's design. It calls the plain
`rb_thread_call_without_gvl`, which always runs the work, inside magnus's
public `protect` (magnus `src/rb_sys.rs:186-191`, `src/error.rs:449-510`,
behind its `rb-sys` feature, which adds no crate). Ruby runs pending
interrupts before releasing the GVL, proceeding even when the thread is
marked as raising (`thread.c:319-343`), and again after taking it back
(`:1636-1638`); an interrupt that raises jumps out with `longjmp`, which
`protect` turns into an `Err` that magnus raises once the method's Rust
values are dropped. The jump skips only the closure `protect` runs, which
holds raw pointers, as magnus's own `thread_check_ints` does
(`src/thread.rs:404-410`). A sync dialog still has no unblocking
function, since rfd cannot cancel one; `wait` keeps its unblocking
function, which unparks the waiting thread, and when Ruby runs an
interrupt that raises nothing the wait starts again. An interrupt that
arrives while a sync dialog is open raises when it closes, and the answer
is discarded; before, the same interrupt fired as the method returned and
discarded it all the same. The RDoc and README say so. Ruby's own IO
does the same: `rb_thread_io_blocking_call` checks interrupts after a
read or write returns (`thread.c:1986-1999`), and one that raises there
discards what it read. The passage on `rb_thread_call_without_gvl` calls
that check harmful for work that has finished and recommends
`rb_thread_call_without_gvl2` for such work (`thread.c:1685-1699`); this
follow-up rejects that function on purpose, because it skips the work
while any interrupt is pending, and the interrupt Ruby holds back stays
pending, which is what led to running the work with the GVL held.

A future does not lose its answer that way. An interrupt that arrives as
rfd's future finishes raises after `poll` was ready, and `gvl::wait`
drops what `poll` returned; rfd's future, polled to completion, stayed in
the slot, so the next `#value` polled it again, it panicked ("`async fn`
resumed after completion"), and the panic was kept as a lasting
`Ferro::Rfd::Error`, so a `FileHandle#write` that succeeded reported an
error. Now `Native::Future`'s poll stores what rfd's future finished
with, or the panic it raised, in `native_value`'s frame, which the
interrupt's jump does not skip, and `native_value` keeps it in the slot
in place of rfd's future, which is never polled again. `native_value`
then returns that outcome on every call, building the tagged Array anew,
because Ruby also checks for interrupts as a C method returns
(`vm_pop_frame`, `vm_insnhelper.c:452`, from
`vm_call_cfunc_with_frame_`, `:3914`), which can discard the Array before
`Future#settle` keeps it. `Thread.handle_interrupt` around `settle` would
not close that gap: `:never` would keep a wait from being interrupted at
all, and `:on_blocking` defers an interrupt pending before the wait past
the check before the GVL is released, so the wait would run until the
dialog closed. The released gem had the same gap at the return, after
which `#value` raised "this future has already finished"; that refusal is
gone with the slot that needed it.
`Gvl::Held`, `TRIES`, the explicit `thread_check_ints` calls, and the
unreachable "the work had already run" are gone.

The same audit's error rule settled two refusals: `Future#value` on the
main thread for a sheet raises `ThreadError`, Ruby's class for a thread
that would wait on itself, with the same message (decision 3; still
checked only by hand, as Unverified here says), and a window number that
names no window raises `ArgumentError` (plan 008, Follow-up). Left as they
are: `inspect` still looks an AppKit window up rather than printing its
number, since that changes rfd's `Debug` text; and `Native::Future`'s
"another thread is waiting on this future", which only a `__send__` past
the Ruby `Future`'s lock reaches, stays a refusal, because a blocking
`lock()` there would hold the GVL while the other thread's released wait
needs it back to return.

`test_future.rb` gains four tests: `Thread#kill` ends a wait and leaves
the future pending; an `Interrupt` made pending under
`Thread.handle_interrupt(Object => :on_blocking)`, which Ruby defers past
the check before the wait and raises at the check after, once a writer
thread has written to the FIFO, raises from the first `#value`, and the
second returns what was written; an `Interrupt` a `TracePoint` raises as
`native_value` returns, standing in for the check there, leaves the
second `#value` the file's contents; and a wait begun inside
`Exception#backtrace` with `Thread#wakeup` pending, in a child Ruby,
returns what a writer thread wrote to the FIFO once the reader slept in
the wait, which proves the writer ran during it. `test_linux_dialogs.rb` gains the same proof for a
sync dialog: the fake `zenity` answers only once a Ruby thread writes to
its gate, which that thread does only once the picking thread sleeps in
the dialog. No test opens a real dialog. A failing run ends when the
helper kills the child after 30 seconds, which only bounds it.

## Follow-up: ADR 001's rulings of 2026-11-05 and ADR 002

ADR 001's amendment of 2026-11-05 settles five translations the first
version made its own way, and its error rule settles the verification's
RULING-5 rows (plan 011's verification records, rows 1, 19, and 20). rfd
0.17.2 and raw-window-handle 0.6.2 meet them as follows.

- **`Debug`** (decision 2). Every bound type with `Debug` answers
  `debug` with that text, which Rust formats from the crate's own value,
  and `inspect` is Ruby's: `FileDialog` (`src/file_dialog.rs:19`),
  `AsyncFileDialog` (`:182`), `MessageDialog` (`src/message_dialog.rs:14`),
  `AsyncMessageDialog` (`:92`), `MessageLevel` (`:153`), `MessageButtons`
  (`:161`), `MessageDialogResult` (`:179`), `FileHandle`
  (`src/file_handle/native.rs:173-177`), and raw-window-handle's
  `WindowsDisplayHandle` (`src/windows.rs:11`), `Win32WindowHandle`
  (`:51`), `XlibDisplayHandle` (`src/unix.rs:7`), `XlibWindowHandle`
  (`:47`), `XcbDisplayHandle` (`:81`), `XcbWindowHandle` (`:121`),
  `AppKitDisplayHandle` (`src/appkit.rs:8`), and `AppKitWindowHandle`
  (`:87`), whose `debug` exists only on macOS and looks the window up for
  the `ns_view` rfd would get (plan 008, decision 5). The handle texts
  are the struct's, not the `RawWindowHandle` variant around it. Without
  `Debug`: `Future` and `Error`, which rfd lacks, and the parent
  protocol, a trait bound. This settles the verification's row about
  `inspect` looking the window up: `inspect` looks nothing up now, and
  `debug`, which must show rfd's exact text, does.
- **Consumed values** (decisions 1 and 3). rfd's terminal methods take
  the builder (`src/file_dialog.rs:121-174`, `:266-330`,
  `src/message_dialog.rs:81-84`, `:147-150`), so the gem's builders work
  once, through a private `Builder` module like ferro-arboard's, and
  raise `IOError` after. `.await` takes a future, so `Future#value`
  answers once. `FileHandle`'s methods borrow it (`native.rs:124-170`),
  and `From<&FileHandle> for PathBuf` exists beside the consuming one
  (`:185-195`), so a handle stays reusable. No block form: nothing in
  rfd is tied to a scope's end.
- **Iterators.** None: rfd returns no iterator. `pick_files` and
  `pick_folders` return `Option<Vec<PathBuf>>`, and the async ones
  `Option<Vec<FileHandle>>`, which stay Arrays (or `nil`), as
  ferro-arboard's `file_list` does.
- **`Duration`.** Neither crate takes or returns one.
- **Hidden and deprecated items.** rfd 0.17.2 marks nothing
  `#[doc(hidden)]` or `#[deprecated]`. raw-window-handle deprecates
  `HasRawWindowHandle` and `HasRawDisplayHandle` (`src/lib.rs:79`,
  `:226`), which the gem never bound: the parent protocol is the
  borrowed `HasWindowHandle` and `HasDisplayHandle`.
- **Errors the gem makes.** A NUL byte in a filter (row 1) is refused
  only on Linux, where the portal backend panics, with that panic's text,
  and a Rust test on Linux drives the real panic (decision 9). A handle
  rfd cannot use (row 19) keeps `ArgumentError`, now with the panic's
  whole text, and a Rust test drives rfd's real `unreachable!` on macOS
  and Windows (decision 6). `Ferro::Rfd::Error` (row 20) carries only
  rfd's panics: caught, or on macOS refused first with exactly the text
  the caught panic would give, `rfd panicked: ` and rfd's message
  (decision 5), since the refusal exists only to spare the side effect
  rfd makes before it panics (creating the application on the wrong
  thread); a child test checks `NSApp` stays null, which is what tells
