# Plan 007: Bind time

Tauri's notification plugin reads a scheduled notification's date with
the time crate's ISO 8601 parser, and rejects a date it cannot read with
that parser's words: "the 'year' component could not be parsed". Ruby's
`Time.iso8601` accepts and refuses different strings, so Tokra's
notification plugin hand-ported time 0.3.41's parser
(`plugins/notification/lib/tokra/plugins/notification/iso8601.rb`, Tokra's
plan 024), step for step, with time's `large-dates` feature assumed off.
Plan 005's "Next: time" section deferred the binding to its own plan. This
plan adds `ferro-time` 0.1.0.pre.1, which binds time 0.3.55, the latest
release (crates.io, published 2026-08-01; the tag `v0.3.55` of
https://github.com/time-rs/time), so Tokra can parse with the crate itself.
[ADR 001](../adr/001.md) and plans [001](001.md) to [006](006.md) hold the
rules and lessons this plan follows.

ADR 001 skips crates that duplicate the standard library. time does not:
Ruby's `Time` and `Date` have no `UtcOffset` value of their own, no
format-description language, and parse ISO 8601, RFC 3339, and RFC 2822
by other rules and with other errors. A Ruby program that must agree with
a Rust service, or with Tauri, needs time's parser.

### From 0.3.41 to 0.3.55

Tokra's notification plugin ported time 0.3.41. The releases since change
what a binding sees (time's `CHANGELOG.md`):

- 0.3.54 renamed `PrimitiveDateTime` to `PlainDateTime` and `Duration` to
  `SignedDuration`, keeping the old names as aliases (`src/lib.rs:160-173`),
  and added iterators over `Date`, `Month`, and `Weekday`.
- 0.3.50 added `Timestamp`; 0.3.52 added `parse_with_defaults`.
- 0.3.48 added version 3 format descriptions, deprecated
  `format_description::parse` and non-UTF-8 formatting, renamed `convert`
  to `unit`, fixed the handling of `T` in ISO 8601 and the parsing of the
  full range of UTC offset hours, and turned an ISO week date past the
  last year from a panic into an error.
- 0.3.47 made formatting a type with a well-known format that needs more
  than the type holds a compile-time error (it was
  `Format::InsufficientTypeInformation` at run time), and bounded RFC
  2822's recursion.
- 0.3.46 added the `truncate_to_*` methods and fixed `UtcOffset`'s
  ordering; 0.3.44 fixed comparisons across a sign change of the year;
  0.3.42 made the local offset available in multi-threaded programs on
  macOS and added `Time::duration_until` and `duration_since`.
- 0.3.55 fixed panics in `from_unix_timestamp_nanos` and
  `checked_to_offset` for out-of-range values.

None changes an ISO 8601 parse error message Tauri's plugin reports; the
`T` fix changes which strings 0.3.55 accepts, so Tokra moving to this gem
moves from 0.3.41's answers to 0.3.55's, which its plan records.

## Naming

The gem is `ferro-time`, `require "ferro/time"`, module `Ferro::Time`,
extension `ferro_time`, as ADR 001's table names a crate's gem. The crate's
root items sit under it: `Ferro::Time::Date`, `Ferro::Time::Time`,
`PlainDateTime` (and `PrimitiveDateTime`, the same class), `UtcDateTime`,
`OffsetDateTime`, `UtcOffset`, `SignedDuration` (and `Duration`, the same
class), `Month`, `Weekday`, and `Error`. Modules become modules:
`time::format_description` is `Ferro::Time::FormatDescription`, its
`well_known` module `FormatDescription::WellKnown`, and `time::util`
`Ferro::Time::Util`.

### `Ferro::Time` and Ruby's `::Time`

`Ferro::Time` is a module and `Ferro::Time::Time` a class, both distinct
from Ruby's `::Time`, as `Ferro::Time::Date` is from Ruby's `::Date`. The
names are the crate's (design precedence 2), and the namespace keeps them
apart, with one consequence: inside `module Ferro`, a bare `Time` now
names `Ferro::Time` wherever ferro-time is loaded, because Ruby looks a
constant up lexically before it looks at `Object`. Code in any `Ferro`
namespace must write `::Time` and `::Date` for Ruby's own classes.
ferro-notify-rust's macOS `schedule` checked `time.is_a?(Time)`, which
would have refused every Ruby `Time` with ferro-time loaded, and its
signature named `Time`, which RBS resolves to `::Ferro::Time` once it
loads every gem's signatures together, as `rbs:validate` does; both now
say `::Time` (decision 18). ferro-time's own code says
`::Time` for Ruby's class everywhere. The README tells users the same.

## Design decisions

1. **What this plan binds, and what waits.** time's public API is several
   times url's. This plan binds the calendar, clock, and span types
   (`Date`, `Time`, `PlainDateTime`, `UtcDateTime`, `OffsetDateTime`,
   `UtcOffset`, `SignedDuration`, `Month`, `Weekday`) whole, their
   formatting and parsing with the well-known formats and version 3
   format descriptions, every error type, and `util`. It defers, each
   whole, five groups that stand apart: `Timestamp` (row 54), a sixth
   instant type added in 0.3.50 that mirrors `UtcDateTime`; `Parsed` (row
   58), time's low-level parsing state, with every `parse_with_defaults`,
   which takes one; the `iter` module (row 60), with `iter_from` and
   `iter_to`, whose Ruby form is an Enumerator design of its own; the
   format-item tree (row 61), roughly a hundred component and modifier
   types that versions 1 and 2 and `strftime` descriptions return, while
   version 3, which time recommends, is opaque by design and bound; and
   `unit` (row 74), whose conversion constants pick Rust numeric types
   Ruby lacks. Each is a later plan's, and nothing bound here depends on
   one: a deferred group's types never appear in a bound signature.
   `parse_borrowed` and `parse_owned` take the version as an argument
   (Rust's const parameter) and raise `ArgumentError` for 1 and 2,
   naming this plan, rather than returning a type the gem lacks.
2. **Cargo features.** `std`, `alloc`, `formatting`, `parsing`,
   `local-offset`, `macros`, and `serde-human-readable` (with `serde`) are
   built. `macros` and the serde features add no Ruby API: macros run in
   the Rust compiler (decision 15), and serde's impls and `with` modules
   serve a serde caller, which Ruby is not; the formats they use are bound
   directly. Off, each an exception to "every feature on" with its reason:
   - `large-dates` changes behavior rather than adding to it: years reach
     ±999,999, a `+` sign appears before five-digit years in `Display`
     (`date.rs:1577-1580`), RFC 2822 refuses five-digit years
     (`formatting/formattable.rs:712-716`), and time warns of new parsing
     ambiguities (`lib.rs:33-39`). Tauri enables it nowhere: its crates
     ask for `formatting` and `parsing` only (`crates/tauri-codegen/Cargo.toml:40`,
     `crates/tauri-bundler/Cargo.toml:61`), and Tokra's plan 024 assumed
     it off. A Ruby program that must agree with Tauri needs it off, and
     one gem cannot offer both, since the feature changes the crate's
     compiled behavior. Years run from -9999 to 9999.
   - `rand08`, `rand09`, `rand010` (and `rand`) and `quickcheck` implement
     Rust traits for Rust's random generators and property tests. Ruby
     code cannot call them, and building them would add four crates to the
     lockfile and the license review for nothing.
   - `wasm-bindgen` compiles nothing outside WebAssembly
     (`Cargo.toml`, `[target.'cfg(all(target_family = "wasm", ...))'.dependencies]`),
     and Ruby has no `js_sys::Date`.
3. **Values hold the native value.** Every type here is `Copy` with
   private fields, so a Ruby value is frozen and holds the native one,
   made only by native functions, never by Ruby's allocator, as
   ferro-idna's `AsciiDenyList` is (plan 006, decision 7). Ruby objects
   hold no mutable native state, so there is no lock anywhere in this
   gem, and plan 005's decision 20 (nothing of Ruby's under a native
   lock) holds trivially. `==`, `eql?`, `hash`, and `<=>` are time's
   `PartialEq`, `Eq`, `Hash` (through Rust's `DefaultHasher`, whose keys
   are fixed), and `Ord`; a type that derives `Ord` includes Comparable.
   `OffsetDateTime` compares and hashes by instant (`offset_date_time.rs:43-82`),
   so two values in different offsets can be `==`; `Weekday` derives no
   `Ord`, since "order is dependent on context" (`weekday.rs:13-15`).
   The wrapped Rust type's class is the public Ruby class itself
   (`Ferro::Time::Date` holds a `time::Date`), so no Ruby object stands
   between a value and its native one; the native layer freezes each value
   as it makes it. `dup` and `clone` return the value itself, as Ruby's own
   frozen values (an Integer) do, which is what Rust's `Copy` gives a value
   no method changes; `clone(freeze: false)` raises `ArgumentError`, as it
   does for an Integer.
4. **Enums.** As plans 002 to 006: unit variants are frozen instances
   whose `inspect` is the constant (`Ferro::Time::Month::January`), equal
   by identity. Rust's `Debug` for them is the variant name, which `to_s`
   (time's `Display`, the English name) already gives.
5. **Conversions.** As plan 003, decision 9: `FromStr` is `from_str`,
   `TryFrom` is `try_from`, and `From<X> for Y` is `Y.from(x)`, each
   raising where Rust returns `Err`. `From<Month> for u8` is `Month#to_i`,
   Ruby's own conversion to an Integer, as `From<Timeout> for i32` is in
   ferro-notify-rust. `Display` is `to_s` and `Debug` is `inspect`.
6. **Aliases.** `PrimitiveDateTime` and `Duration` are type aliases in
   Rust, the names the types had until 0.3.54, which time keeps without
   deprecating them (`lib.rs:155-173`). In Ruby each is a constant holding
   the same class, so `Ferro::Time::Duration.equal?(Ferro::Time::SignedDuration)`.
   `inspect` and class names say the new name, as Rust's `Debug` and
   type names do.
7. **Panics.** No input reachable from Ruby panics the crate. time
   documents its panics (each `# Panics` section): arithmetic that
   overflows the representable range (`Date + Duration`,
   `Duration::days(i64::MAX)`, `to_offset` past `Date::MAX`), a NaN or
   overflowing float (`seconds_f64`), and division by zero. The native
   layer calls the crate's checked twin where it has one
   (`checked_add`, `checked_sub`, `checked_neg`, `checked_to_offset`,
   `checked_to_utc`, `checked_seconds_f64`, `checked_seconds_f32`) and
   otherwise checks the same condition the crate's `expect` checks: the
   `checked_mul` in `weeks` to `minutes`, the range test in
   `nanoseconds_i128`, the day steps of the private
   `checked_next_occurrence` and `checked_prev_occurrence`
   (`date.rs:1046-1108`), and the date steps `From<SystemTime>` takes
   (`interop/offsetdatetime_systemtime.rs:59-67`,
   `offset_date_time.rs:1686-1770`). It refuses with `RangeError` and
   time's own panic message, as plan 001 refused an `Instant` Rust could
   not build, so a refusal never prints a Rust panic on standard error.
   A Rust test drives each unchecked operation into its real panic and
   asserts the message the gem copies; for the occurrences and
   `From<SystemTime>`, it compares refusal and panic for every case near
   both ends of the range. Division by an integer zero raises
   Ruby's `ZeroDivisionError` ("divided by 0"), Ruby's own words for it.
   Every crate call also runs under `catch_unwind` as a net: a panic no
   check foresaw raises `Error` with `time panicked: <message>`.
8. **Numbers.** Integers cross through magnus, which raises `RangeError`
   outside the Rust parameter's type (`u8` for a day, `i32` for a year,
   `i128` for nanoseconds). `Duration * n` and `Duration / n` take an
   Integer through the `i32` impl, the type Rust gives an integer literal,
   and magnus raises `RangeError` outside it. The six integer impls do not
   behave alike: the unsigned ones reinterpret the bits as signed before
   they widen (`cast_signed`, `signed_duration.rs:1620-1660`), so in Rust
   `duration * 200_u8` multiplies by -56, which a Rust test pins; a Ruby
   Integer never reaches them. A Float goes through the `f64` impl; Ruby
   has one Float, so the `f32`
   impls have no operator, while `seconds_f32`, `as_seconds_f32`, and the
   other named `_f32` methods round through a 32-bit float as Rust's do.
   `Duration / Duration` is a Float. time's reflexive
   `Mul<SignedDuration> for i32` and `for f64` (`signed_duration.rs:1657-1668,
   1757-1768`) are reached without changing `Integer` or `Float`: their
   `*` asks the right-hand value to `coerce` the left (`numeric.c`,
   `rb_num_coerce_bin`, at Ruby v4.0.9), so `SignedDuration#coerce`
   returns the number in a private wrapper whose `*` computes
   `duration * number`, as Rust's `rhs * self` does, the pattern Ruby's
   own `Matrix::Scalar` uses. Rust has no other operator with a number on
   the left, so the wrapper refuses the rest with Ruby's own words:
   `2 + duration` raises the same `TypeError` as before and `2 < duration`
   the same `ArgumentError`, which `test_values.rb` pins, with time's
   `int_mul` and `f64_mul` ported.
9. **std's `Duration` is deferred.** `std::time::Duration` is unsigned,
   and Ruby has no value for it: Ruby code measures spans in Float
   seconds, which `SignedDuration` already covers. Every operation time
   offers with std's type (`checked_add_std`, `Add<StdDuration>`,
   `unsigned_abs`, the conversions) has a `SignedDuration` twin bound
   here, so nothing is out of reach. A later plan may map it once Ruby
   code needs one.
10. **Ruby's `::Time` is `SystemTime`.** `SystemTime` is the system
    clock's instant, and Ruby's value for it is `::Time` (`Time.now`),
    as ferro-notify-rust's `schedule` takes a `::Time` for chrono's
    instant (plan 003, decision 9). time's `From<SystemTime>` impls are
    `OffsetDateTime.from(time)` and `UtcDateTime.from(time)`, which read
    the `::Time`'s seconds and nanoseconds since the epoch
    (`Time#to_i`, `Time#nsec`), build the `SystemTime` Rust would, and
    call the crate's `From`; the result is in UTC, as time's is
    (`interop/offsetdatetime_systemtime.rs:59-67`). A sub-nanosecond
    fraction a Ruby `Time` may hold is dropped, as a `SystemTime` cannot
    hold it, and on Windows `SystemTime` keeps 100 ns, as Rust's does.
    `From<OffsetDateTime> for SystemTime` is `#to_time`, a UTC `::Time`,
    since a `SystemTime` has no offset; `PartialEq`, `PartialOrd`, and
    `Sub` with a `SystemTime` on the right are `==`, `<=>`, and `-` with
    a `::Time` argument. The impls with `SystemTime` on the left need no
    binding for comparison: Ruby's own `Time#<=>` asks the other value
    when it is not a `Time` (`rb_invcmp`, `time.c:3987` and
    `compar.c:50-60` at v4.0.9), so `::Time == offset_date_time` and
    `::Time < offset_date_time` answer through the gem's `<=>`, as Rust's
    `PartialEq` and `PartialOrd` for `SystemTime` do. `Sub` with
    `SystemTime` on the left, and `SystemTimeExt`, would change Ruby's
    `::Time`, which a library must not, so `time - offset_date_time`
    stays Ruby's `TypeError`.
    These are translations of the crate's `From` impls, not inventions:
    the gem offers no conversion to or from Ruby's `::Date`, because time
    has none for any date type. A `::Time` outside `SystemTime`'s range,
    or one that lands outside time's years, raises `RangeError` with
    std's or time's panic text, checked first.
11. **Formatting and parsing.** A description is a version 3
    `FormatDescriptionV3`, the class `WellKnown::Rfc2822` or
    `WellKnown::Rfc3339` (Rust's unit structs, passed as themselves), or an
    `Iso8601` (or the class `Iso8601` itself, Rust's unit-struct value
    with the default configuration); anything else raises `TypeError`, as
    Rust's trait bound would. `parse` takes UTF-8 text, as `&str`;
    `format` returns UTF-8 text. `format_into` writes to a `W: io::Write`
    and returns the bytes written; Ruby's takes a String, which the output
    is appended to even when formatting fails partway, as Rust's writer
    keeps what was written, and a frozen String raises `FrozenError`
    first (ferro-idna's sinks, plan 006, decision 14). A String never
    fails to write, so `Format::StdIo` never arises.

    Since 0.3.47 a well-known format that needs more than a type holds is
    a compile-time error in Rust: `Rfc3339` and `Rfc2822` need a date,
    time, and offset (`formatting/formattable.rs:702-708`, `:808-814`),
    and an `Iso8601` configuration its components
    (`:927-946`). Ruby has no compile time, so `format` raises `TypeError`
    with time's assertion message, as Rust's compiler would refuse the
    type; parsing is unaffected.

    `Iso8601<CONFIG>` takes its configuration as a const parameter, so
    Rust compiles a formatter per configuration, and the configurations
    number about 130,000 (seven component sets, separators, six-digit
    years, three date kinds, three time precisions with up to 255
    decimal digits, two offset precisions). Parsing ignores the
    configuration (`parsing/iso8601.rs` reads none of it; `parsing/parsable.rs:894-954`),
    so the gem parses with one instantiation. Formatting writes the date,
    then the time, then the offset, each reading only its own fields
    (`formatting/formattable.rs:948-958`, `formatting/iso8601.rs`); the
    gem compiles each part separately (12 date, 1,536 time, and 4 offset
    formatters) and formats the value's own `date()`, `time()`, and
    `offset()` with them, adding the two rules that join the parts. time
    writes the time's `T` when `!USE_SEPARATORS || FORMAT_DATE`
    (`formatting/iso8601.rs:118-123`): always in the basic format, and in
    the extended format only after a date, the one case a time-only
    formatter leaves to the gem. The other rule is `Z` for a UTC offset
    after a time (`:185-187`). A Rust test checks
    the composition against time's own formatter for every named constant
    and a sample of other configurations on every type, so a later time
    that changes either rule fails it. `Config` is not `Copy` and has
    no `PartialEq` (`well_known/iso8601.rs:155-174`); the Ruby `Config`
    is frozen, each setter returns a new one, and `==` is identity, while
    `Iso8601` derives `PartialEq`, so two `Iso8601`s with the same
    configuration are `==`. `Config#encode` returns time's encoding, an
    Integer, which only `Iso8601`'s Rust parameter has a use for. time's
    serde uses `Config::DEFAULT.set_year_is_six_digits(true)` (its
    private `SERDE_CONFIG`, `serde/iso8601.rs:24-26`), which a Ruby
    program reproduces with the same calls.
12. **Debug and Display.** `inspect` is time's `Debug` and `to_s` its
    `Display`: `2020-01-02`, `0:00:00.0`, `+00:00:00`, `1d2h3m4s`. Rust's
    formatter options (width, fill, a duration's precision) are
    formatting machinery a Ruby `to_s` has no counterpart for; the
    concise precision form of `SignedDuration`'s `Display` is deferred
    with them.
13. **Local offsets and soundness.** `local-offset` reads the system's
    offset with `localtime_r` on Unix and `SystemTimeToTzSpecificLocalTime`
    on Windows (`sys/local_offset_at/unix.rs:1-108`,
    `sys/local_offset_at/windows.rs:35-120`). Since 0.3.37 the reads need no single-threaded
    process: `util::local_offset::set_soundness`, which older releases
    used to opt out of that check, is a hidden, deprecated no-op that
    always reports `Sound` (`util.rs:135-156`), and is dropped. What
    remains process-wide is the time-zone cache `tzset` refreshes.
    `refresh_tz` refreshes it only when time can prove the call sound: on
    illumos, NetBSD, and macOS, whose environment functions are
    thread-safe, or in a single-threaded process (`sys/refresh_tz/unix.rs:1-58`),
    and returns `None` otherwise. A Ruby process is never single-threaded
    on Linux (the VM starts its own threads), so `Util.refresh_tz` returns
    `true` on macOS and `nil` on Linux, an `Option<()>` translated to
    `true` and `nil` because Ruby's `nil` alone could not tell the two
    apart. `refresh_tz_unchecked` is not bound: time's own safety section
    says "it is not possible for a library to soundly call this method",
    because the caller must vouch for every thread in the process, and
    Ruby's `ENV[]=`, which any Ruby thread can call, runs `setenv`.
    Setting `TZ` through `ENV` does not refresh the zone at once: Ruby
    only marks its zone stale (`reset_by_modified_env` and
    `ruby_reset_timezone`, `hash.c:5251-5261` and `time.c:752-758` at Ruby
    v4.0.9), and runs `tzset` at its own next local-time conversion
    (`update_tz` from `rb_localtime_r`, `time.c:762-775`), such as
    `::Time.now.utc_offset`. Until then, or until `Util.refresh_tz` where
    time can make it sound, time may read the zone `tzset` last loaded.
    The calls are short and keep the GVL.
14. **Errors.** `Error < StandardError` is time's `Error`. Each of its
    variants holds exactly one error type of the same name, so the Ruby
    class is both: `Error::ComponentRange` is `time::error::ComponentRange`
    and the `Error::ComponentRange` variant, and `rescue
    Ferro::Time::Error` catches everything time raises, as `?` would
    convert it. An error type that is itself an enum has a subclass per
    variant, nested as Rust nests them, as ferro-notify-rust nested
    mac-notification-sys's (plan 003, decision 10): a failed parse raises
    `Error::Parse::ParseFromDescription::InvalidComponent` (with `name`),
    or `Error::Parse::TryFromParsed::ComponentRange` (with `name` and
    `is_conditional`), each a subclass of the variant above it, so
    `rescue Error::Parse` catches both. Every message is time's
    `Display` text, which a Rust test pins. A variant time adds later
    raises its enum's class with time's text, since every one is
    `#[non_exhaustive]`. The deprecated `UnexpectedTrailingCharacters`
    variants of `Error` and `Parse` hold `Infallible` and can never
    exist, so they have no class. The `From` and `TryFrom` impls between
    error types convert a Rust value from one enum to another; a Ruby
    exception has one class, which `rescue` and `is_a?` already match,
    so they are dropped, and `DifferentVariant`, their only source, is a
    class nothing in the gem raises, kept because `Error` names it.
15. **Macros.** time's macros check their input when Rust compiles. Ruby
    has no compile time; each macro's run-time counterpart is bound:
    `date!(2020-01-02)` is `Date.from_calendar_date(2020, Month::January, 2)`,
    `time!`, `offset!`, `datetime!`, and `utc_datetime!` are `Time.from_hms`,
    `UtcOffset.from_hms`, `PlainDateTime.new` and `assume_offset`, and
    `UtcDateTime.new`, and `format_description!(version = 3, "...")` is
    `FormatDescription.parse_owned(3, "...")`. The README lists them.
16. **Text.** Every `&str` argument is a UTF-8 String (magnus converts,
    and raises `EncodingError` otherwise); every result is UTF-8. time
    deprecated non-UTF-8 formatting (0.3.48), so the gem offers none.
17. **GVL and Ractors (ADR 001, section 7).** Every call is short CPU
    work, or a single system call for the clock and the local offset, so
    every call keeps the GVL (plan 001, decision 14). time's types are
    plain `Copy` data, `Send` and `Sync`; the extension keeps no Ruby
    value in a static, so it is marked Ractor-safe, and every value it
    makes is frozen and shareable. Windows runs the Ractor tests in a
    child process, for the Ruby 4.0.9 barrier bug plan 001 found.
18. **ferro-notify-rust's `::Time`.** Its macOS `schedule` and signature
    now name `::Time` (see Naming). The consequence reaches further than
    an app that requires both gems: every Ferro gemspec loads its
    `version.rb`, so Bundler defines `Ferro::Time` in any process whose
    bundle holds ferro-time, the repository's own test runs included.
    ferro-notify-rust's existing macOS test,
    `test_scheduling_in_the_past_raises_mac_notification_sys_error`,
    failed with `TypeError` before the fix and passes after it. Its
    CHANGELOG records the fix. ADR 001's amendment of 2026-10-27 makes
    `::Time` and `::Date` the rule inside `module Ferro` for every gem but
    this one; RuboCop's `Lint/ConstantResolution` (`Only: [Time, Date]`,
    over `gems/*/lib` outside `gems/time`) enforces it in Ruby, and
    `test/tasks/test_top_level_constants.rb` in the signatures, which
    RuboCop does not read.
19. **Dependencies.** time `=0.3.55` with the features of decision 2;
    magnus `0.9.3` and rb-sys `0.9.130`. No other dependency. time-macros
    is a proc-macro crate that runs in the compiler and ships no code in
    the extension; its build-time dependencies are the same kind the
    other gems' bindgen already brings.

What the session found:

- **Ruby's `Ferro::Time` reaches every bundled process.** Each Ferro
  gemspec loads its `version.rb`, so Bundler defines `Ferro::Time` wherever
  ferro-time is in the bundle, and a bare `Time` in `module Ferro` then
  names it. ferro-notify-rust's macOS `schedule` broke that way (decision
  18), and its existing test caught it.
- **Ruby's `Time#<=>` asks the other value** (`rb_invcmp`), so comparisons
  with a `::Time` on the left work through the gem with no change to
  `::Time` (decision 10).
- **time's unsigned `Mul` impls reinterpret the scalar as signed**
  (`duration * 200_u8` multiplies by -56), so `*` and `/` take the `i32`
  impl only (decision 8).
- **The ISO 8601 composition agrees with time's formatter** on all 32
  sampled configurations across all six types, partial output included.
  Without it, the 4,336 per-type instantiations a scratch build measured
  (1,276 for `OffsetDateTime` alone took 2.4 MB) would not ship.
- **Version 3 descriptions read time's version 1 test descriptions the
  same way**, except the `range` modifier, which version 3 refuses
  without `large-dates`; those cases stay as comments in the ports.
- **time's panic messages depend on the path**: `From<SystemTime>` panics
  with Date's "overflow adding duration to date", not with
  `OffsetDateTime`'s message, and the occurrence methods panic for `n` of
  zero with the overflow message; the refusals copy each, and Rust tests
  compare them with the real panics at both ends of the range.
- `ISO 8601` `2026-13-01T00:00:00Z` raises
  `UnexpectedTrailingCharacters`, as Tokra's hand port had it.
- On Linux a Ruby process starts with two threads (`/proc/self/task`, in
  `ruby:4.0.9-trixie`), so `Util.refresh_tz` returns `nil` there, as
  `test_local_offset.rb` asserts; macOS's environment is thread-safe and
  it returns `true`.

Unverified here: Windows, which never ran. The gem's library code has no
Windows-only branch, but a Windows `SystemTime` differs, and the tests
branch on it. It counts 100 ns intervals from 1601
(std `sys/pal/windows/time.rs:9-15`, `sys/time/windows.rs:105-118` at Rust
1.99.1), so a `::Time` crossing it keeps whole 100 ns intervals
(123,456,789 ns becomes 123,456,700), and an instant before 1601 is
refused by std's `checked_sub` with "overflow when subtracting duration
from `SystemTime`" before time could see it. `test_system_time.rb` expects
each per platform, the RDoc examples that compare with `#to_time` use a
multiple of 100 ns, and the Rust tests gate the pre-1601 cases with
`#[cfg(windows)]` and `#[cfg(not(windows))]`. `refresh_tz` returns `true`
through time's fallback (`sys/refresh_tz/imp.rs`). The Linux run had no
Clippy; CI runs it.

An independent review found the binding faithful and asked for these
changes, all made:

- the Windows `SystemTime` expectations above, which the first draft
  wrote as Unix's;
- the test ports: the first draft claimed one Ruby test per Rust test,
  which was false. A per-file listing of every `#[test]` and `#[rstest]`
  found 188 of the twelve ported files' tests missing. 82 are now ported
  (`sum_iter_ref` shares `test_sum_iter`), among them
  `new`, `to_offset_panic`, `checked_to_offset` with ±0:00:01,
  `from_unix_timestamp_nanos` with `(1 << 64) * 1e9`, `partial_eq`,
  `partial_ord`, `hash`, the `SystemTime` and `OffsetDateTime`
  comparisons both ways, `to_offset_regression`, `arithmetic_regression`,
  `from_iso_week_date_regression`, `regression_check`,
  `replace_millisecond_regression`, `checked_div_regression`, and
  `iso_8601_issue_678`, and the other 105 are listed under Tests with
  their reasons;
- `2 * duration`, which now reaches time's reflexive `Mul` through
  `coerce` (decision 8) instead of raising `TypeError`;
- the native `eq`, `cmp`, `hash`, `Display`, and `Debug` of every value
  type run under `guarded`, as every other crate call does; time's
  derives cannot panic, so no test can reach the guard;
- the naming guardrail of decision 18, now ADR 001's amendment of
  2026-10-27, enforced by RuboCop and a tooling test;
- prose: the ISO 8601 `T` rule (decision 11, `iso8601.rs`), row 66's
  citation, and decision 13's account of `ENV["TZ"]=`. `format_into`'s
  count already came from each part's own formatter, as time's does
  (`test_format_into_returns_time_s_count`: 0 for `00.00`, 12 for
