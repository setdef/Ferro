# Plan 001: Bootstrap Ferro and Bind arboard

Ferro exists because of Tokra's ADR 011: crate bindings leave Tokra's
plugins and become gems of their own, each answering to one crate. This
plan builds the repository and its pilot gem, `ferro-arboard`, which binds
arboard 3.7.0, the latest release. [ADR 001](../adr/001.md) restates the
decisions this plan carries out.

### Design decisions

1. **The public API is Ruby; the native layer is one private method per
   terminal operation.** Rust defines `Clipboard` (a magnus-wrapped
   `Mutex<arboard::Clipboard>`), `Clipboard.new`, and private methods such
   as `native_get_text(selection)` and `native_set_text(text, options)`.
   `Get`, `Set`, and `Clear` are Ruby objects that hold their clipboard and
   the settings their extension methods chose, and their terminal methods
   call the native method with those settings. This gives every public
   method real RDoc, RBS that Steep checks against code, and a native layer
   small enough to audit line by line. The alternative, native builder
   objects holding a reference to the clipboard, keeps more Rust and leaves
   RDoc nothing to read.
2. **Builders mutate and return themselves, and work once.** Rust's
   extension methods consume `self` and return `Self`
   (`src/platform/linux/mod.rs:383-408`). Ruby has no moves, so `set.wait`
   records the setting and returns the same `Set`. A terminal method
   (`src/lib.rs:189-212`, `:227-263`, `:275`; `ClearExtLinux::clipboard`,
   `src/platform/linux/mod.rs:452-456`) takes `self` and returns no
   builder, so under ADR 001's ruling of 2026-11-05 it uses the builder up:
   any later call on it, an option or another terminal, raises `IOError`,
   as a closed IO does, with the message `Ferro::Arboard::Get consumed by
   Get#text`. Rust consumes the builder whatever the call returns, so a
   terminal that raises uses it up too; the mark is set as the call
   starts. The shared private module `Builder` holds the mark, since the
   platform modules check it as well. There is no block form: a builder
   ties nothing to a scope here, since the gem opens nothing until the
   terminal call (below), and `Clipboard` has no method that consumes it.
   (The first version let a builder finish again; Tokra calls only
   `Clipboard`'s one-call methods, which build a fresh builder each time.)
   arboard builds its platform `Get`, `Set`, or `Clear` at the terminal
   call instead of at `clipboard.get`, which changes nothing observable
   except on Windows,
   where opening the clipboard (`src/platform/windows.rs:581`, `:665`, `:888`)
   moves from builder creation to the terminal call. `Get.new`, `Set.new`,
   and `Clear.new` are private, as arboard's fields are `pub(crate)`.
3. **Errors.** `Error < StandardError` with one subclass per variant. Rust
   raises each with `to_string()` of the crate's error, so the crate's
   `Display` is the message; each class also defaults to that text when you
   raise it yourself. `Unknown` takes the description and builds the message
   in the crate's format (`src/common.rs:62`). `Error` is `#[non_exhaustive]`
   (`src/common.rs:19`): a variant a future arboard adds raises the base
   `Error` with its `Display` text until Ferro adds a class for it.
4. **Images arboard would panic on raise `ConversionFailure` before they
   reach arboard.** On Linux and Windows, a width or height of zero, or a
   byte count other than `width * height * 4`, is refused: arboard 3.7.0
   would panic on a wrong byte count there, where the image crate's PNG
   encoder asserts the length (`image-0.25.10 src/codecs/png.rs:740-746`,
   reached from `src/platform/linux/mod.rs:38-46` and
   `src/platform/windows.rs:132-144`). On macOS only an empty buffer, on
   which arboard unwraps `CGDataProviderCreateWithData`
   (`src/platform/osx.rs:58-69`), and a size whose `width * 4 * height`
   overflows `usize` (arboard computes `4 * width` unchecked, `osx.rs:86`)
   are refused. arboard there returns `ConversionFailure` itself for a
   short buffer or a zero dimension, when `CGImageCreate` fails
   (`osx.rs:80-95`), and draws a longer buffer from its first bytes; the
   gem lets it, since refusing an input the crate accepts is not
   fidelity. (The first version refused every shape on every platform for
   one answer; the verification of 2026-11-04 found that deviation
   unsupported, and the follow-up below records the change.) Tokra's plan
   016, item 6 found this panic in 3.6.1
   (https://github.com/setdef/Tokra/blob/trunk/doc/contributors/plan/016.md).
   ADR 001's error rule (2026-11-05) allows the crate's own variant for
   an input refused because the crate would panic on it, if a Rust test
   drives the real panic; two do. Off macOS,
   `refused_images_are_ones_arboards_png_encoder_panics_on` gives image's
   PNG encoder each refused shape with a wrong byte count and checks its
   assertion's text, and checks that the empty zero-size image, which
   arboard refuses itself, does not panic. An arboard or image upgrade
   that stops panicking fails it, so the guard can shrink with it. On
   macOS only the predicate's own tests pin the guard: a test that set an
   empty image and an overflowing width through a real arboard clipboard,
   to check the unwrap's and the overflow's panic texts, passed locally
   but crashed CI's macOS runner with SIGSEGV (Ferro run for 90d55e4), so
   it was removed. Why it crashed is unproven: both panics come from
   `image_from_pixels` (`osx.rs:58-69`, `:86`), outside any autorelease
   pool, so the leading guesses are the pasteboard driven from a test
   thread, or a panic in a release-built dependency; driving arboard into
   a real panic in-process is not safe to rely on.
   The check, `is_drawable_rgba`, and its Rust tests come from Tokra's
   clipboard binding; their author, the copyright holder of both projects,
   relicensed them from AGPL-3.0-or-later to MIT OR Apache-2.0 for Ferro.
5. **No panic reaches Ruby as `fatal`.** magnus turns a panic in a bound
   method into Ruby's `fatal`, which `rescue` cannot catch
   (`magnus-0.9.3 src/error.rs:292-296`, `src/method.rs:340-345`). Every call
   into arboard runs under `std::panic::catch_unwind` inside the clipboard's
   lock, so the lock is never poisoned, and a panic raises the base
   `Ferro::Arboard::Error` with the message `arboard panicked: <message>`.
   It is not a crate variant because arboard never returned it. A lock
   poisoned anyway is recovered (`PoisonError::into_inner`), since arboard's
   clipboard holds no invariant a panic could break.
6. **`wait_until` takes a monotonic deadline.** Rust's `Instant` is a point
   on the monotonic clock. Ruby's equivalent is
   `Process.clock_gettime(Process::CLOCK_MONOTONIC)`, a Float, so
   `wait_until(deadline)` takes one, or any `Numeric` number of seconds,
   as ADR 001's `Duration` row (2026-11-05) takes one for a span;
   anything else raises `TypeError` naming `Numeric`. At the terminal
   call Ruby passes the seconds remaining, and Rust adds them to
   `Instant::now()`. A deadline in
   the past waits for nothing, as an `Instant` in the past does. A NaN or
   infinite deadline raises `RangeError` with Rust's own wording, since
   Rust code could not build such an `Instant` without panicking; a Rust
   test drives those panics (`Duration::from_secs_f64`, `Instant + Duration`)
   and checks the texts match, as ADR 001's error rule asks.
7. **`LinuxClipboardKind` is a class with three frozen instances** named for
   the variants, so `LinuxClipboardKind::Primary` reads as it does in Rust.
   A `selection` that is not one of them raises `TypeError`, as Rust's type
   checker would refuse it. The instances answer only `inspect`; the
   builders read the variant name privately, since arboard's enum has no
   method to convert it.
8. **Ownership helpers are dropped.** `ImageData::into_owned_bytes` and
   `to_owned_img` turn borrowed bytes into owned ones (`src/common.rs:133-150`).
   Ruby has no borrowed bytes, so `image.bytes` and the image itself already
   are what they return. ADR 001's table drops lifetime machinery.
9. **`Debug` is `debug`; `inspect` stays Ruby's.** ADR 001's ruling of
   2026-11-05: each type arboard gives `Debug` answers `debug` with that
   text exactly, formatted by Rust so it cannot drift. Those are `Error`
   (hand-written, `src/common.rs:69-90`: `ContentNotAvailable - "..."`, and
   `Unknown { .. } - "..."` for the struct variant), on each variant's
   class, whatever message the instance carries; `ImageData` (derived,
   `src/common.rs:126`: `ImageData { width: 2, height: 1, bytes: [...] }`);
   and `LinuxClipboardKind` (derived, `src/platform/linux/mod.rs:104`:
   `Primary`). The base `Error` is no arboard variant (it carries a panic,
   or a variant a later arboard adds), so it has none. The private module
   `Ferro::Arboard::Native` rebuilds the crate value and formats it.
   `LinuxClipboardKind`'s custom `inspect`, which imitated a constant
   path, is gone; `ImageData` keeps `Data#inspect` and errors keep
   `Exception#inspect`. (The first version mapped `Debug` to `inspect`.)
10. **Paths.** `Set#file_list` takes Strings or objects with `to_path`
    (`File.path` converts them, as Ruby's own file methods do). On Unix
    the bytes pass through unchanged; on Windows a path must be UTF-8.
    `Get#file_list` returns Strings.
11. **Text must be UTF-8.** arboard takes `str`; magnus converts a Ruby
    String to UTF-8 and raises `EncodingError` when it cannot.
12. **Clipboard lifetime.** arboard asks that every clipboard be dropped
    before the program exits (`src/lib.rs:38-43`). Ruby frees each wrapped
    object at a normal exit (`gc.c:338-350` at v4.0.1, which calls the free
    function of every typed data object), so the clipboard drops then, or
    when the garbage collector frees it. `exit!` and a crash skip it.
13. **Ractors (ADR 001, section 7).** arboard's `Clipboard` is `Send` and
    `Sync` (`src/lib.rs:510-516` asserts it; `src/platform/osx.rs:105-106`),
    and the wrapper adds a `Mutex`, so the class is `frozen_shareable`:
    `Ractor.make_shareable(clipboard)` works. The extension is marked
    Ractor-safe with `rb_ext_ractor_safe(true)` in `Init_`, which magnus
    does not wrap; its `SAFETY` comment walks Ruby's checklist
    (`doc/extension.rdoc:2207-2286` at v4.0.1). A non-main Ractor can open
    a clipboard or use a shared one; without the call it would raise
    `Ractor::UnsafeError` (`test_ractor.rb`).
14. **The GVL is released around the calls that can block** (`src/gvl.rs`):
    on Linux, every read, which polls the owning program for up to four
    seconds (arboard `src/platform/linux/x11.rs:101`, `:371-378`; Wayland
    reads a pipe the owner writes), and every write with `wait`,
    `wait_until`, or `wait_once` (`x11.rs:281-296`, `wayland.rs:63-68`).
    Every other call keeps the GVL. Releasing it for every call was tried
    first, and a reviewer measured about 330 ms per `get_text` with three
    busy threads: retaking the GVL waits out a time slice per competing
    thread, which Ruby warns about for short calls (`thread.c:1721-1723` at
    v4.0.1). macOS reads have no wait of their own (`osx.rs:135-153`,
    `:224-249`), and Windows' open retries last at most about 25 ms
    (`windows.rs:533-560`).

    magnus does not wrap `rb_thread_call_without_gvl`, so rb-sys's binding
    is called directly, inside magnus's `protect` (amended 2026-11-05; see
    Follow-up: the GVL is never held). Arguments become Rust values before
    the lock is released and results become Ruby values after; the work
    catches its own panics. The clipboard sits behind `lock::Lock`, a busy
    flag under a `Mutex` with a `Condvar`, rather than a bare `Mutex`, so a
    wait for it can be cut short. A short call takes it with `try_lock`
    while holding the GVL, and if another thread holds it (through a long
    wait, say) waits for it with the GVL released instead, so it never
    stalls the VM. The wait for the lock has an unblocking function, which
    wakes it: `Thread#raise`, `Thread#kill`, Ctrl-C, and process exit end
    it, and an interrupt that raises nothing lets it wait again. arboard
    itself cannot cancel a call in progress, so once arboard runs, those
    take effect when the call returns, and process exit waits for it
    (`thread.c:484-493`). Dropping a clipboard on X11 can block up to
    100 ms plus a thread join during a GC sweep, with the GVL held
    (`x11.rs:790`, `:1105-1135`). `drive`, the loop, takes Ruby's call as
    an argument so Rust tests cover each path; `test_gvl.rb` counts the
    calls that release the lock (Linux reads and waiting writes release it
    once; short writes and reads elsewhere never do), which replaced the
    first version's spinning-thread tests (Follow-up: CI), and on Linux
    shows a call made with an interrupt pending waiting for the lock with
    the GVL released and `Thread#raise` and `Thread#kill` ending a wait for
    the lock; `test_linux.rb` ports arboard's `wait` test with a Ruby
    thread as the replacer.
15. **Dependencies.** arboard `3.7.0` with `image-data` and
    `wayland-data-control`, every feature built in under ADR 002's sorting:
    `image-data` (the default) adds `ImageData` and the image methods and
    implies `core-graphics`, `image`, and `windows-sys`;
    `wayland-data-control` adds the Wayland clipboard and implies
    `wl-clipboard-rs`, whose client is pure Rust (wayland-backend's default
    leaves `wayland-sys` without its `client` feature, so its build script
    links nothing, `wayland-sys-0.31.11 build.rs:4-12`). Ruby reaches each,
    none excludes another, and none needs a system library, so none is
    dropped or offered: the crate declares no `[features]` and the gem no
    `FEATURES`, which ADR 002 (decision 5) gives only a gem with offered
    features. A dev-dependency on image `=0.25.10` with `png`, off macOS,
    the version and feature arboard already pulls there, lets a Rust test
    drive the panic decision 4 refuses; it adds no crate to the lockfile.
    Beside arboard, magnus `0.9.3` with `bytes` (its safe way to copy
    a String's bytes, which Tokra also enables) and `rb-sys` (its public
    `protect`, which turns a Ruby jump into an `Err`; the feature adds no

## Follow-up: CI

`.github/workflows/ci.yml` runs the gate, `bundle exec rake`, on
`ubuntu-latest`, `macos-latest`, and `windows-latest`, once per supported
Ruby (ADR 001, section 8; today 4.0). Every gem runs on every change: with
one gem, a run limited to the gems a change touches would save nothing.
The toolchains come from `mise.toml`, so CI and contributors build with the
same Rust.

- **Linux** runs the gate under Xvfb, then each gem's Ruby tests again
  under sway's headless Wayland compositor with `DISPLAY` unset, so arboard
  cannot fall back to X11 (`src/platform/linux/mod.rs:133-150`). weston
  would not do: it lacks the data-control protocols. arboard's X11 and
  Wayland clients are pure Rust, so no client libraries are installed.
- **Windows** builds with Rust's GNU toolchain, since RubyInstaller's Ruby
  is a MinGW build and rb-sys refuses the MSVC target for it. bindgen gets
  `--target=x86_64-pc-windows-gnu` and the MSYS2 sysroot setup-ruby
  installs, as oxidize-rb's `setup-ruby-and-rust` does. Git checks out
  symlinks as symlinks and converts line endings, as a contributor's
  checkout would; RuboCop's `Layout/EndOfLine` is native.

The first Linux run, in a Debian container, found four things:

- On X11, text outlives the last `Clipboard` only when a clipboard manager
  takes it over (`src/platform/linux/x11.rs:1106-1135`). Bare Xvfb has
  none, so the round-trip test failed; CI now runs xfce4-clipman, which
  speaks the ClipboardManager protocol, beside Xvfb.
- On Wayland, `get_text` after `set_html(html, nil)` returns the HTML:
  wl-clipboard-rs reads any `text/*` type as text (`src/paste.rs:441-443`,
  `src/utils.rs:33-39`). arboard's own test expects no text, but arboard
  never runs its tests on Linux. The test and `Set#html`'s RDoc now say so.
- The packaging tests resolve fixture crates with `cargo metadata
  --offline`, which needs every platform's crates in Cargo's cache. On a
  fresh cache only the host's were there, so `test:tooling` now depends on
  `package:fetch`.
- The packaging tests' fixture ignored only `*.bundle`, macOS's extension,
  so on Linux the fake `.so` counted as an untracked file.

With those fixed, the Linux gate passes and the gem's tests pass under
both X11 and Wayland (69 runs, 3 skips: the Windows exclusions, macOS's
concealed type, and the off-Linux GVL test). macOS and Windows run first on
GitHub's runners.

The first runs on GitHub's runners found four more:

- xfce4-clipman quits 60 seconds after it starts unless a system tray
  embeds its icon (xfce4-clipman-plugin 1.6.6
  `panel-plugin/main-status-icon.c:88-99`). The container's gem tests ran
  inside that minute; the runner's, after a cold compile, did not, so the
  round-trip test lost its text whenever its clipboard was the last one
  open. Reproduced in the container by starting the tests 70 seconds after
  the manager: seeds 12345 and 999 failed without a tray and passed with
  one. CI now starts stalonetray first, and
  `.github/ci/with-clipboard-manager` runs the gate only once the manager
  owns the `CLIPBOARD_MANAGER` selection. No retry or sleep: arboard's own
  handover is synchronous, with a 100 ms limit (`x11.rs:788-801`).
  That was not the end of it; see below.
- The Windows sysroot came from RbConfig's `host_os`, which says
  `mingw32` for a UCRT Ruby, so it pointed at MSYS2's `mingw64`, which has
  no C library headers. It now comes from `RI_DEVKIT` and
  `MSYSTEM_PREFIX`, which setup-ruby exports from RubyInstaller's `ridk
  enable`, and the step fails unless `include/stdio.h` is there.
- REUSE needs a module that detects file encodings. Its own dependency,
  python-magic, needs libmagic, which only the Linux image has, so CI and
  the README install `reuse[charset-normalizer]`, which is pure Python.
- dtolnay/rust-toolchain sets `CARGO_TERM_COLOR=always`, and a colored
  warning starts with an escape sequence instead of `warning`, so the
  gate's warning check would have passed any warning in CI. `CargoOutput`
  now strips terminal styles before it matches.

Even with the manager alive, the round-trip test failed on a later
runner (run 40196458935). In the container, 40 suite runs under load lost
the text in 7; an instrumented copy showed xfce4-clipman owning the
`CLIPBOARD` selection afterwards with no text in it, and once no owner at
all. That is arboard's handover working as written: it offers the
contents, waits at most 100 ms, and destroys the window that served them
(`x11.rs:788-801`, `:1106-1135`), so a manager that has not fetched them
by then has nothing. arboard attempts the handover; it does not promise
it. The manager also refilled a cleared clipboard (20 of 20 tries in the
container), which made the Ractor test that clears the clipboard fail in
2 of 40 runs.

So CI runs no clipboard manager, and the round-trip test asserts what
arboard does guarantee on X11: contents outlive a dropped clipboard while
another clipboard in the process stays open, since they share one X11
server thread. On macOS, Windows, and Wayland it still drops every
clipboard, as arboard's test does, without the 300 ms sleep that existed
for a manager. `Clipboard`'s RDoc names the 100 ms limit. 40 runs of the
suite on bare Xvfb, idle and loaded, never failed the round-trip test.

The GVL test that failed in the container, `test_linux_reads_let_other_threads_run`,
was not a binding defect. Counting in a scratch build showed every failing
read on the released path (no skipped tries, no fallback with the GVL
held), finishing in 0.3 to 2 ms with the spinner ready, while passing reads
waited out the spinner's whole time slice, about 110 ms. Ruby 4.0.6 added
a scheduler hint (`thread_pthread.c:846-867`, `:1055-1066` at v4.0.9): a
thread back from a short blocking region takes the GVL straight back when
the thread it woke has not started running yet. Ruby 4.0.1, on the
development Mac, lacks it, which is why the test never failed there. A
released lock never promised that another thread runs during a fast read,
so the spinner tests are gone. `gvl.rs` now counts each run with the GVL
released, `Clipboard#native_gvl_releases` (private) reads the count, and
`test_gvl.rb` asserts it: one release for a Linux read and for a write that
waits, none for a write that does not wait or for a read off Linux.
Reverting Linux's `BLOCKS_ON_READS` or macOS's fails them.
`test_linux.rb`'s wait test still shows a released lock at work. 40 suite
runs on X11 after the change: no failures.

The hunt also found a race in arboard 3.7.0 on X11, present on its main
branch too. `clear` gives up the selection, the X server answers with a
SelectionClear event, and arboard's server thread later drops the
process's data for that selection without checking whether a newer write
replaced it (`x11.rs:233-242`, `:835-856`). Set right after a clear, from
any clipboard in the process, and the process owns the selection with
nothing to serve: 197 of 200 tries in the container, none on Wayland.
`Clipboard#clear`'s RDoc says so. In the suite it hits whichever test runs
right after one that ends with a clear, a few runs in a hundred; the new
GVL test was first written that way and raised it to 5 runs in 40. It is
worth reporting to arboard.

A later Windows run (40205193172) stopped in
`TestRactor#test_another_ractor_opens_its_own_clipboard_and_rescues_arboards_errors`,
with the main thread in `Ractor#value`. The watchdog was right: the
previous test finished at 15:07:18.98 and the report came at 15:08:19.03,
60 seconds later. The report now prints how long the test had run, and a
tooling test checks that three 0.7-second tests under a one-second limit
all pass, so a limit that leaked between tests would fail it. Why that
Ractor stopped is not established. Its block can only block in arboard's
Windows calls, which retry opening the clipboard five times, 5 ms apart,
and then give up (`windows.rs:533-560`). 100 runs of the Ractor tests on
macOS with Ruby 4.0.9 never stopped, and the same test passed on Windows in
the run before. Each Ractor in `test_ractor.rb` now reports its steps to
stderr when `FERRO_TEST_TRACE` is set, as CI sets it, so the next stop
shows whether the Ractor was inside a clipboard call or had already
returned.

Traced, the next Windows hang came in the other order: the shared-clipboard
Ractor printed that it was setting text and nothing more for 60 s, then
went on the moment the watchdog's report walked `Thread.list`. Meanwhile
the probe, in fresh processes, finished 140 of 140. The difference is the
threads the main Ractor holds: in the test process, Minitest's ten
executor threads and the watchdog's thread, all asleep. That fits a Ruby
4.0.9 bug in the Windows VM barrier, which a GC inside a Ractor needs.
`rb_ractor_sched_barrier_start` (`thread_win32.c:932-963`) waits until
every Ractor counts as blocking, and a Ractor counts as blocking only when
all its threads are in blocking regions (`ractor.c:781-790`, called from
`thread.c:1535`). `Ractor#value` waits in `rb_nogvl`
(`ractor_sync.c:950-960`), so the main thread counts, but `sleep` and
`Queue#pop` wait through `native_sleep`'s `THREAD_BLOCKING_BEGIN`
(`thread_win32.c:341-370`, `thread.c:170-178`), which does not. The
barrier interrupts the main Ractor's running thread once
(`ractor.c:813-828`), and that thread sleeps in `rb_nogvl`, which a barrier
interrupt does not wake, so the main Ractor joins only when one of its
threads next takes the VM lock, as the watchdog's report did. POSIX counts
running threads instead (`thread_pthread.c:1439-1444`). Ruby's main branch
replaced the Windows scheduler with the POSIX one (commit 90e729c9bc,
first in 4.1.0-preview1).

CI run 40208256038 (commit ab4ab6e) confirmed it with no gem involved:
a sleeping thread, then `Ractor.new { GC.start }.value`, stopped in 3 of
3 Windows runs, while the same with no sleeping thread, or with the main
thread polling instead of waiting, finished 20 of 20, and the
shared-clipboard variant stopped only with the sleeping thread. The bug
is Ruby's. `test_ractor.rb` runs its scripts in a child process on
Windows, whose main Ractor has no other thread, and in process elsewhere;
the gem's README warns Windows users; the diagnostic step and its probe
script are gone, and a reproducer for bugs.ruby-lang.org lives outside
the repository.

`mise.toml` now pins Ruby 4.0.9, the release CI's `4.0` resolves to, so
local runs see the same scheduler (Ruby 4.0.6's hot-thread hint above).

## Follow-up: releases

`rake bump:<gem>:major`, `:minor`, `:patch` (each with an optional
prerelease label, as in `patch[pre]`), and `:exact[0.1.0.pre.2]` set a
gem's version in `version.rb`, the crate's `Cargo.toml`, the gem's
`Cargo.lock`, and the root `Gemfile.lock`; release the CHANGELOG's
Unreleased entries as a dated section and move its compare links; run the
gate; and commit `chore(<gem>): release X.Y.Z`. A failure before the gate
restores every file; a failed gate leaves the changes for inspection.
`rake release:<gem>:tag` tags that commit `ferro-<gem>/vX.Y.Z` and pushes
only the tag, refusing unless trunk is clean and matches origin's, neither
side has the tag, the CHANGELOG has the version's section, and trunk holds
the release commit. `rake release:<gem>` keeps the RubyGems push for the
maintainer, who is not publishing yet: Tokra uses Ferro gems from their
tags as git sources.

The bump logic is ported from ratatui_ruby-devtools 0.4.1 rather than
taken as a dependency. Its tasks assume one gem per directory: `RubyGem`
finds the only gemspec in the working directory, `Changelog` and
`Repository` work on `CHANGELOG.md` and git there, tags are `vX.Y.Z`, and
the release commit is `chore: release vX.Y.Z`. Scoping them to
`gems/arboard`, with `ferro-arboard/v` tags and scoped commits, would mean
changing directories around each task and replacing most classes. Its
`SemVer` also refuses RubyGems' `0.1.0.pre.1`, the form Ferro writes, and
the gem would bring nokogiri, rubycritic, and inch into Ferro's bundle.
`tasks/gem_version.rb` keeps its bump rules (a bump finishes a prerelease
it leads up to; a label counts up toward the same release) in RubyGems'
form, and `tasks/changelog.rb` its Unreleased and link handling.

Deferred: devtools' release branches from 1.0 on. No Ferro gem is near
1.0, and branching per gem in one repository needs its own decision, so a
bump to a stable 1.0 or later is refused until then.

## Follow-up: the GVL is never held

An audit of errors the gems make themselves, rather than their crates,
found that `gvl.rs` could run arboard with the GVL held. It released the
GVL with `rb_thread_call_without_gvl2`, which skips the work whenever any
interrupt is pending (`thread.c:320-327` at Ruby v4.0.9, `vm_core.h:2222`).
After three skips in a row the work ran with the GVL held, which stalled
every Ruby thread for as long as arboard took (a Linux read polls for up to
four seconds; a `Set` with `wait` lasts until another program takes the
clipboard), and `lock_for` refused a lock another thread held with
`ClipboardOccupied`, an error arboard never returned. Three skips are rare
by chance, but certain inside a user-defined `Exception#backtrace`: Ruby
calls it with the thread marked as raising (`eval.c:542-543`,
`error.c:1929`), and a thread so marked runs no interrupts
(`thread.c:2625`), so one made pending there stays pending.

`gvl.rs` now calls the plain `rb_thread_call_without_gvl`, which always
runs the work, inside magnus's public `protect` (magnus
`src/rb_sys.rs:186-191`, `src/error.rs:449-510`, behind its `rb-sys`
feature).
With no flags, Ruby runs pending interrupts before releasing the GVL, and
proceeds even when the thread is marked as raising (`thread.c:319-343`),
and runs them again after taking it back (`:1636-1638`). An interrupt that
raises jumps out with `longjmp`; `protect` catches the jump and returns it
as an `Err`, which magnus raises again after the method's Rust values are
dropped. The jump skips only the closure `protect` runs, which holds raw
pointers, as magnus's own `thread_check_ints` does (`src/thread.rs:404-410`).
An interrupt that arrives after arboard returned discards its value; before,
it fired as the method returned and discarded it the same way. Ruby's own
IO does the same: `rb_thread_io_blocking_call` checks interrupts after a
read or write returns (`thread.c:1986-1999`), and one that raises there
discards what it read. The passage on `rb_thread_call_without_gvl` calls
that check harmful for work that has finished and recommends
`rb_thread_call_without_gvl2` for such work (`thread.c:1685-1699`); this
follow-up rejects that function on purpose, because it skips the work
while any interrupt is pending, and the interrupt Ruby holds back stays
pending, which is what led to running the work with the GVL held. `Gvl::Held`, `lock_for`,
`drive`'s three tries, and the unreachable "the work had already run"
are gone.

The clipboard's `Mutex` became `lock::Lock`, a busy flag under a `Mutex`
and a `Condvar`, because a thread waiting its turn behind another thread's
`wait` could otherwise be ended by nothing but that wait. Its `Waiter` is
the unblocking function `rb_thread_call_without_gvl` passes to Ruby: it sets
a flag under the lock's mutex and wakes every waiter, and the waiter gives
up its wait, so `Thread#raise`, `Thread#kill`, Ctrl-C, and process exit
(`terminate_all`, `thread.c:400-417`) end it. An interrupt that raises
nothing, such as `Thread#wakeup` or a trap that returns, lets it wait again.
Ruby calls the function from another thread, perhaps another Ractor's,
under the waiting thread's interrupt lock (`thread.c:353-383`) and never
from a signal handler, since the call does not pass
`RB_NOGVL_UBF_ASYNC_SAFE` (`thread_pthread.c:2684-2686`); it touches only
std's `Mutex` and `Condvar`, so the extension stays Ractor-safe. arboard's
own call still cannot be cancelled once it starts.

`test_gvl.rb` gains four Linux tests, each in a child Ruby that holds the
clipboard in a `wait` on one thread, with the suite's watchdog process
setting the text after 120 seconds, which only bounds a failing run, and a mark that fails the test. The first
reads the clipboard from inside `Exception#backtrace` with `Thread#wakeup`
pending; a releaser thread frees the lock only once the reader sleeps in its
wait, so reading the releaser's text proves other threads ran during the
call. The other two end a waiter with `Thread#raise` and `Thread#kill` while
the holder still waits; the fourth wakes a waiter with `Thread#wakeup`,
waits for it to sleep in a second release, and reads the releaser's text. They ran in a throwaway container from Tokra's
`tokra-linux` image under Xvfb; there is no Wayland run of them yet.

## Follow-up: ADR 001's rulings of 2026-11-05 and ADR 002

ADR 001's amendment of 2026-11-05 and ADR 002 settle six questions the
first version answered its own way. arboard 3.7.0 meets them as follows.

- **`Debug`** (decision 9). `Error`, `ImageData`, and `LinuxClipboardKind`
  have `Debug`; `Clipboard`, `Get`, `Set`, and `Clear` do not. The three
  answer `debug`, which `Ferro::Arboard::Native` formats with Rust, and
  `LinuxClipboardKind` loses its `inspect`, which imitated a constant
  path. Rust tests pin each text against `format!("{:?}")`.
- **Consumed values** (decision 2). The builders' terminal methods take
  `self`, so a used builder raises `IOError`. No block form, since nothing
  in the gem is tied to a builder's scope.
- **Iterators.** None: arboard returns no iterator, and `file_list`'s
  `Vec<PathBuf>` stays an Array.
- **`Duration`** (decision 6). arboard takes no `Duration`; its one
  `Instant`, `wait_until`'s, already took a Numeric, and now says so when
  refusing anything else.
- **Hidden and deprecated items.** arboard 3.7.0 has none.
- **Errors the gem makes.** The verification's rows for the gem's own
  `ClipboardOccupied` and the GVL-held fallback were settled by the
  previous follow-up. A panic raises the gem's base `Error`, as before.
  The image guard keeps arboard's `ConversionFailure` and the deadline
  keeps `RangeError` with Rust's text, each now pinned by a Rust test
  that drives the real panic (decisions 4 and 6). The private methods'
  `ArgumentError`s for a tag the Ruby side never sends stay, as guards.
- **Cargo features** (decision 15). All six are built in; none is dropped
  or offered, so there is no `[features]` table, no `extconf.rb` change,
  and no `FEATURES`. ADR 002's install-time machinery lands with the gems
  that offer a feature.

The Linux tests ran in a throwaway container from Tokra's `tokra-linux`
image under Xvfb and D-Bus (X11; no Wayland run). The first run showed
the new Clear test meeting the X11 race above, text set right after a

## Follow-up: test hooks

ADR 001's second amendment of 2026-11-05 rules that a test hook exists
only in the repository's own build, and global-hotkey settled how (plan
004, Follow-up: ADR 001's rulings; the bind-crate skill, Test hooks).
arboard's one hook, the private `Clipboard#native_gvl_releases`, now
follows it. The crate declares an empty `test-hooks` feature, which
corrects the previous follow-up: there is now a `[features]` table and an
`extconf.rb` line, `enable_config("test-hooks", false)`, though neither
is an option an app chooses (ADR 002). The method, the `gvl::RELEASES`
counter, and its increment compile only with the feature, the counter
also under `cfg(test)` for the Rust test that reads it, so an installed
gem neither counts nor has the method. A build with the hook defines
`Native::TEST_HOOKS`; `tasks/ferro_gems.rb` says `test_hooks: true`, so
the packaging check compiles the extension again from the package and
the smoke script aborts if the marker is there. The hook stays a private
method of `Clipboard`, where it was, rather than moving to `Native`'s
singleton class as global-hotkey's are, so the tests reach it as before,
through `__send__` on a clipboard, and its signature leaves `sig/`. No
CHANGELOG entry: the method was private in 0.1.0.pre.2.

On macOS the Ruby tests that read the counter only assert that a call
did not release the lock, so a macOS run shows the hook is there but not
that it counts; with the increment deleted they still passed, and
`running_unlocked_counts_a_release` (Rust) failed. The Linux tests, which
expect one release, run on CI.
