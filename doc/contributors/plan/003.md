# Plan 003: Bind notify-rust

Tokra's notification plugin needs desktop notifications, and ADR 001 puts
notify-rust in Ferro's first phase as a one-native-home crate: on macOS it
swaps `NSBundle`'s `bundleIdentifier` and installs the notification
center's one delegate, so a second copy in the process would undo the
first's hook and steal its delegate. Nothing else links it, so Ferro is its
home. This plan adds `ferro-notify-rust` 0.1.0.pre.1, which binds
notify-rust 4.18.2, the latest release (crates.io, published 2026-10-07).
[ADR 001](../adr/001.md), [plan 001](001.md), and [plan 002](002.md) hold
the rules and lessons this plan follows.

It also fixes the release tooling first: a new gem starts at
`0.1.0.pre.1`, and the bump task could only move forward, so
ferro-arboard and ferro-rfd released `pre.2` first. `rake
bump:<gem>:current` now releases the version a gem already has, refusing
once a tag here or on origin, or a CHANGELOG section, has it
(`tasks/bump.rb`, `Bump#release_current!`, tested in
`test/tasks/test_bump.rb`).

## Naming

ADR 001's table shows a crate without a hyphen. notify-rust has one, and
Cargo names its library `notify_rust`. The gem keeps the crate's name,
`ferro-notify-rust`, as gem names keep hyphens. The require path and
module follow the Rust identifier, `require "ferro/notify_rust"` and
`Ferro::NotifyRust`: RubyGems' habit of turning a hyphen into a slash
would give `ferro/notify/rust` and `Ferro::Notify::Rust`, a nesting the
crate does not have. The folder, task names, and commit scope are
`notify-rust`, the crate's name; the extension is `ferro_notify_rust`.
ADR 001's table gains this row. `FerroGem#version_file` derived the
version file's path from the gem name; it now takes the extension's
directory, which works for both kinds of name.

## Design decisions

1. **Naming.** See Naming above.
2. **Cargo features.** `z` (zbus, the default) with `async`, `images`,
   and `chrono` are built. The rest are not, each for its reason:
   - `d` and `d_vendored` add dbus-rs beside zbus. With both, notify-rust
     picks one at run time by the `DBUSRS` environment variable
     (`src/xdg/mod.rs:410-449`), and its author means them to exclude each
     other in 5.0 (`:390-392`). `d` links the system's `libdbus-1`, so
     every Linux install would need its headers, and `d_vendored` builds
     libdbus from source. They buy a second transport and nothing a Ruby
     program can see except `dbus_stack`, and the dbus-rs handle panics on
     the async methods (`:189-191`, `:231-234`). Tier 2 says follow the
     crate; the crate's default and its stated direction are zbus alone.
   - `z-with-tokio` and `tokio` run zbus on tokio, which needs a tokio
     runtime around every call; Ruby code never runs inside one. They add
     no API.
   - `debug_namespace` replaces the bus name with `de.hoodie.Notifications`
     (`src/xdg/mod.rs:41-48`), so no real server would answer. It is for
     the crate's own tests.
   - `preview-macos-un` replaces the macOS backend rather than adding to
     it: `NotificationHandle`, `id`, `urgency`, `show_async`, and the
     errors change, and `set_application` stops working
     (`src/macos/mod.rs:13-18`). `UNUserNotificationCenter` needs a signed
     app bundle (`check_bundle`), which `ruby` is not, and the feature is
     a preview. A gem built both ways would need an install-time switch;
     that waits for a bundled Ruby app that needs it.
3. **`Notification` is a native object.** rfd's builders were Ruby objects
   that rfd replayed (plan 002, decision 1). notify-rust's is different:
   its handle dereferences to the notification it showed, so
   `handle.summary("x"); handle.update()` changes the shown copy
   (`src/xdg/mod.rs:290-317`), and hints live in a `HashSet` and a map
   keyed by name (`src/notification.rs:303-318`). So the native layer
   wraps notify-rust's `Notification` in a `Mutex`, and the Ruby class
   calls private methods that run notify-rust's own setter. A setter
   returns the notification, as Rust's `&mut Notification` does, and on a
   frozen notification raises Ruby's own `FrozenError` (magnus
   `check_frozen`). Every native method that changes the notification
   checks first, `initialize` included, since Ruby code can run it again
   through `send` on a frozen notification another Ractor shares, and so
   does a Linux handle's `update`, which takes `&mut self` as the setters
   do. The waits that take the handle by value (macOS, Windows) do not:
   Rust moves a value out of a binding that is not `mut` too, and a frozen
   object is that binding's counterpart. `dup` and `clone` are
   notify-rust's `Clone`, and `finalize` returns a copy as the crate's
   does. The public fields read and write through accessors:
   notify-rust's own test assigns them (`tests/realworld.rs:85-110`), and
   a field holds what its setter stored. `hints` returns a `Set` of the hints in the `HashSet`; as
   notify-rust warns, it leaves out `Custom` and `CustomInt`, which live
   in the map (`src/notification.rs:68-74`).
4. **`show`, the handle, and `Drop` on macOS.** On macOS `show` sends
   nothing: it returns a handle holding a copy of the notification, and
   the handle sends it when it drops, unless a wait method sends it first
   and waits (`src/macos/nsusernotifications.rs:142-162`, `:252-257`).
   Rust drops a handle you never bind at the end of the statement, so
   `Notification::new().show()?` shows at once. Ruby has no scope-based
   drop: a handle would drop when the garbage collector frees it, seconds
   or minutes later, inside the collector. Ruby's way to end something at
   a known point is a block, so (tier 1):
   - `show { |handle| ... }` yields the handle and drops it when the
     block ends, even by an exception, as Rust drops on unwinding. A wait
     inside the block sends and waits; otherwise the drop sends.
   - `show` without a block drops the handle at once, so the notification
     appears, and returns the handle, used up: every call on it raises
     `IOError` (Follow-up: ADR 001's rulings).
   - A wait takes the handle, as notify-rust's take `self`, so a second
     wait raises `IOError`.
   On Linux and Windows `show` sends before it returns
   (`src/xdg/mod.rs:414-416`, `src/windows.rs:14-48`), the handle's drop
   only frees a D-Bus connection or a channel, and the block yields the
   handle, returns the block's value, and uses the handle up at its end,
   where Rust drops it. `schedule` and `schedule_raw` return a handle
   with no notification, as notify-rust's do
   (`nsusernotifications.rs:259-275`), whose first wait returns at once
   without calling its block. An interrupt between `show`
   and its block's `ensure` can leave a handle holding a notification for
   the garbage collector; its free drops notify-rust's handle on a thread
   of its own, so the send never runs inside the collector with the GVL
   held, and a process that exits first may never send it. macOS's
   `NotificationHandle::new` is not bound: notify-rust plans to make it
   private ("TODO: make private in 5.0", `:16`), and `show` makes the same
   handle.
5. **Handles on Linux and Windows.** Rust's `wait_for_action`,
   `wait_for_response`, `on_close`, and `close` consume the handle, and
   since ADR 001's ruling of 2026-11-05 so do they here: each uses the
   handle up, and a later call raises `IOError` (Follow-up: ADR 001's
   rulings). On Linux they wait through notify-rust's borrowing async
   methods (decision 6), so they can be interrupted. The native handle
   takes Rust's borrows at run time, as a reader-writer lock does
   (`lock.rs`; Follow-up: the GVL is never held): `wait_for_action_async`,
   `close_async`, `id`, and the field readers take a shared turn, as
   notify-rust's `&self` methods do, so a `close_async` from another
   thread ends a `wait_for_action_async`, as notify-rust's own
   `close_async` example does (`src/xdg/mod.rs:155-178`); a consuming
   call takes one too, after it has used the handle up. A setter or `update` takes the exclusive
   turn and waits, with the GVL released and interruptibly, for the
   shared ones to end, as Ruby's `Mutex` makes a second thread wait (ADR
   001's rule for errors a gem makes), and every call waits while
   `update` runs. Readers go first: a first design held std's `RwLock`
   across the wait, which blocks new readers behind a queued writer, so a
   setter queued behind a wait would have kept a later `close` from
   ending it, with both threads uninterruptible. A setter on the thread
   whose own wait holds a shared turn (from a signal trap during the
   wait) would wait for itself, so it raises `ThreadError`. On Windows the
   native layer hands notify-rust the handle itself, so after a wait the
   handle holds nothing, and every call on it, Builder methods included,
   raises `IOError`, as on macOS. The handle answers every
   `Notification` method by acting on the notification inside it, as
   `Deref` and `DerefMut` do; setters return the handle, so
   `handle.summary("x").update` chains. On Linux the handle's own `id`
   (the server's id) shadows the setter `id(u32)`, as Rust's method
   resolution picks the inherent method first.
6. **The GVL, waits, and futures.** Every call that talks to D-Bus, the
   notification center, or a toast blocks, so it runs with the GVL
   released, and never with it held (ferro-arboard's `gvl.rs`). Which
   calls an interrupt can cancel depends on what notify-rust exposes:
   - Linux `show`, `wait_for_action`, `wait_for_response`, `on_close`,
     and `close` poll notify-rust's own futures (`show_async`,
     `wait_for_action_async`, `close_async`), which the sync methods only
     `block_on` (`src/xdg/mod.rs:118-127`, `:139-142`, `:219`, `:280-286`,
     `:414-416`). The wait has an unblocking function, so Ctrl-C,
     `Thread#raise`, and `Timeout` end it and drop the future.
     `wait_for_action`'s mapping from a response to a string is ported
     from `src/xdg/mod.rs:119-124`: `"default"`, the action's key, or
     `"__closed"`, and nothing for a reply.
   - Linux `update`, `get_capabilities`, `get_server_information`, and
     `handle_action` have no async form, and macOS and Windows have none
     at all, so they run with no unblocking function, as rfd's dialogs
     do. zbus sets no timeout on a method call (zbus 5.19.0
     `src/connection/builder.rs:101`, `:479-485`, `:660`), so a server
     that never answers blocks them, uninterruptibly, as it blocks
     notify-rust's own callers; a macOS fire-and-forget send ends within
     about two seconds (mac-notification-sys `objc/notify.m:161-180`). A wait for the user
     (`handle_action`, macOS and Windows waits) can last until the user
     acts, and Ctrl-C and process exit wait for it.
   - Every future polled across `gvl::wait`'s tries passes through
     `sendable`, which makes the compiler check it is `Send`: under the
     M:N scheduler a Ruby thread can resume on another native thread
     between tries. No std lock guard is held across a wait; a shared
     turn of the handle's lock is, and it is `Send` (decision 5).
   - No work ever runs with the GVL held (Follow-up: the GVL is never
     held). An interrupt that arrives just as the work returns raises and
     discards its result, such as an action the user just took.
   - Linux's async methods return a `Future`. notify-rust's are `async
     fn`s that borrow the notification or the handle, and like every Rust
     future they do nothing until polled. ferro-rfd's `Future` held rfd's
     future natively, because rfd starts work before the first poll on
     macOS; a borrowing future cannot be kept in a Ruby object, and
     nothing here starts early. So `Ferro::NotifyRust::Future` is Ruby:
     it holds the work and runs it, through the interruptible native
     calls above, when `value` is first asked, as the first poll does.
     `.await` takes a future, so the `value` that returns its result or
     raises its `Error` uses the `Future` up, and a later one raises
     `IOError`, as ferro-rfd's does (Follow-up: ADR 001's rulings); an
     interrupt drops the work, as dropping a Rust future does, and a later
     `value` starts it again. `show_async` and `show_async_at_bus` copy the
     notification when called, since the Rust future borrows it from that
     moment, and finish with a handle; `close_async` finishes with `nil`;
     `wait_for_action_async` calls its block with the
     NotificationResponse when `value` sees it.
   - On macOS, a wait off the main thread finishes only while the main
     thread runs its run loop (`nsusernotifications.rs:29-31`): ferro
     cannot tell whether something does, so it does not refuse, and the
     RDoc says so. On the main thread mac-notification-sys runs the run
     loop itself (`objc/notify.m:192-209`).
7. **Handlers are blocks, called with the GVL held.** notify-rust calls a
   closure inside the wait. Ruby code cannot run without the GVL, so the
   native layer records what the closure received, and Ruby yields it
   after the wait returns. `on_close` yields the CloseReason; a block that
   takes no argument ignores it, which covers both `CloseHandler` impls.
8. **Enums.** As plan 002, decision 8: unit variants are frozen
   instances (`Urgency::Low`, `Timeout::Never`, `CloseReason::Expired`,
   `NotificationResponse::Default`, `Hint::Invalid`, `DbusStack::Zbus`),
   and variants with data are `Data` classes. A variant's members take
   the names notify-rust binds its fields to: `Hint` single values are
   `value` (`src/hints.rs:181-205`), `Hint::Custom` and `CustomInt` are
   `key` and `value`; `NotificationResponse::Action` is `key`, `Reply` is
   `text`, and `Closed` is `reason` (`src/response.rs:53-62`);
   `CloseReason::Other` is `raw_reason` (`:36-37`);
   `ActionResponse::Custom` is `key`; `NotificationId` and
   `Timeout::Milliseconds` hold `value`. `Default` impls become
   `.default`, `Notification`'s too: `Notification.default` returns
   what `new` does, since `Notification::new` is `Notification::default()`
   (`src/notification.rs:123-125`). `PartialEq` and `Hash` become `==`,
   `eql?`, and `hash`, which `Data` gives by value.
9. **Conversions.** A `From` impl becomes a class method `from`,
   `TryFrom` becomes `try_from`, and `FromStr` becomes `from_str`; each
   raises where Rust returns `Err`. `From<Timeout> for i32` is `to_i`,
   Ruby's own conversion to an Integer. An error type that is not
   notify-rust's (`FromStr`'s `ParseIntError`, `from_key_val`'s `String`)
   raises `ArgumentError` with Rust's text, as Ruby's `Integer("x")` does
   for its own parse. `From<Duration> for Timeout` is bound since ADR
   001's ruling of 2026-11-05 makes a `Duration` any `Numeric` number of
   seconds. An Integer already means milliseconds, through `From<i32>`,
   so `Timeout.from` picks by class, as Rust picks by type: an Integer is
   `From<i32>`, as an integer literal is `i32` in Rust, and any other
   Numeric is a `Duration`, through `Float` and core's
   `Duration::try_from_secs_f64`, whose error text a negative, NaN, or
   too large count raises as `ArgumentError` where `from_secs_f64` would
   panic. So `from(5)` and `from(5.0)` are a thousand times apart, as
   `Timeout::from(5)` and `Timeout::from(Duration::from_secs(5))` are;
   the RDoc says so. `Notification#timeout` takes what `Timeout.from`
   takes, as Rust's takes anything `Into<Timeout>`, while the `timeout=`
   field writer takes only a Timeout, as the field holds one
   (`src/notification.rs:101`). `schedule` takes a
   `Time`, the Ruby value for chrono's `DateTime<Tz>`, and passes its
   `to_i`, as notify-rust passes `timestamp()` (`src/notification.rs:495`).
10. **Errors.** `Error < StandardError` is notify-rust's `Error`, with one
    subclass per `ErrorKind` variant built here: `Msg`, `Zbus` (Linux),
    `MacNotificationSys` (macOS), `Parse`, `SpecVersion`, `Conversion`,
    `Image` (Linux), and `ImplementationMissing`. The message is
    notify-rust's `Display` text. A class whose variant holds text builds
    that text as the variant's `Display` does: `Conversion.new(reason)`
    adds `Conversion Error: ` (`src/error.rs:68`), so the native layer
    passes the reason alone; `Msg` and `SpecVersion` display their text
    as it is. `Error` keeps its `kind` private and
    has no accessor (`src/error.rs:16-19`), so the native layer reads the
    variant's name from the derived `Debug` text (`Error { kind: Zbus(`),
    and a Rust test pins that text for every variant through the public
    `From<ErrorKind>`; a variant ferro does not know raises the base
    class (`ErrorKind` is `#[non_exhaustive]`). On macOS,
    mac-notification-sys's error is another enum of enums: each leaf is a
    class under the variant it sits in,
    `Error::MacNotificationSys::Application::AlreadySet` and
    `::CouldNotSet` (each with `name`), and
    `Error::MacNotificationSys::Notification::ScheduleInThePast`,
    `::UnableToSchedule`, `::UnableToDeliver`, so `rescue
    Error::MacNotificationSys::Application` catches both of its kinds.
    zbus's error is another crate's, so `Error::Zbus` carries its text and
    no subclasses. `ImageError` is a separate exception, as it is a
    separate type that `Image`'s constructors return; its `Display` ends
    with a newline (`writeln!`, `src/image.rs:153-163`), which the message
    keeps. A panic inside notify-rust raises the base `Error` with
    `notify-rust panicked: <message>` (plan 001, decision 5).
11. **Deprecations.** Since ADR 001's ruling of 2026-11-05, an item
    `#[doc(hidden)]` or `#[deprecated]` is unbound unless Tauri needs it,
    and Tauri's notification plugin (plugins-workspace,
    `plugins/notification/src/desktop.rs`) calls none of these: the
    `actions` setter (`src/notification.rs:442`), `Notification::at_bus`
    (`:129-130`), and `show_debug` (`:558`) are not bound. The `actions`
    field is public and not deprecated, so it reads and writes. On macOS
    the deprecation is on `Urgency`'s re-export (`src/lib.rs:218-222`),
    not on the type, which `Hint::Urgency` holds there
    (`src/hints.rs:84-85`), so the type stays bound and the constant is
    deprecated (`deprecate_constant`), as its export is. `ActionResponse`'s
    deprecation is in its doc only, and `handle_action` still hands one
    to its closure, so it stays bound and the RDoc says it.
12. **`SPEC_VERSION` is an autoloaded constant.** It is a lazy static that
    calls `get_server_information` the first time it is read, falling
    back to 1.1 when that fails or does not parse (`src/lib.rs:226-233`).
    Reading it at `require` would talk to D-Bus, but a Ruby constant can
    be lazy: `Module#autoload` loads `spec_version.rb` the first time the
    constant is named, and that file reads the crate's own static through
    `Native.spec_version`, with the GVL released, as notify-rust blocks on
    the call. The crate's static, not `get_server_information`, is the
    value its image hints use, and it differs from that call's answer
    when the call fails. On Ruby 4.0 a constant first named from
    another Ractor loads on the main Ractor, and the value, a frozen
    `Data` of two Integers, is shareable; a test names it first from a
    Ractor. Its type, `miniver::Version`, sits in a private module, so
    Rust code outside notify-rust cannot name it or call a constructor,
    only copy `SPEC_VERSION` (the type is `Copy` with public fields):
    `Version` is a `Data`
    with `major` and `minor`, `Comparable` in notify-rust's `Ord`, whose
    `new` and `[]` are private. `Version` is defined with the rest of the
    Linux API, so naming it does not talk to D-Bus; only `SPEC_VERSION`

## Follow-up: the GVL is never held

An audit of errors the gems make themselves found in `gvl.rs` the defect
ferro-arboard's commit 57f2a76 fixed (plan 001, Follow-up: the GVL is
never held). The gem released the GVL with `rb_thread_call_without_gvl2`,
which skips the work whenever any interrupt is pending (`thread.c:320-327`
at Ruby v4.0.9), and after three skips ran the work with the GVL held:
`Image.open`, `update`, `get_capabilities`, `get_server_information`,
`handle_action`, `spec_version`, and every macOS and Windows send and
wait, the last of which can wait for a person. Three skips are certain
inside a user-defined `Exception#backtrace`, where a thread runs no
interrupts (`eval.c:542-543`, `error.c:1929`, `thread.c:2625`). The Linux
future waits only polled once with the GVL held and then looped, but that
loop spun with the GVL held in the same case.

`gvl.rs` is now ferro-arboard's: the plain `rb_thread_call_without_gvl`,
which always runs the work, inside magnus's public `protect` (magnus
`src/rb_sys.rs:186-191`, `src/error.rs:449-510`, behind its `rb-sys`
feature, which adds no crate). Ruby runs pending interrupts before
releasing the GVL, proceeds even while the thread is marked as raising
(`thread.c:319-343`), and runs them again after taking it back
(`:1636-1638`); one that raises jumps out with `longjmp` over only the
closure `protect` runs, and magnus raises it again once the method's Rust
values drop. `without_gvl` passes no unblocking function, for calls
nothing can cancel; `wait_until` passes a waiter's, for a wait for the
handle's lock; `wait` passes the future waiter's, which unparks the
thread. An interrupt that arrives just after the work returned discards
its result, as Ruby's IO path does (`rb_thread_io_blocking_call`,
`thread.c:1986-1999`; the comment at `:1694-1699` recommends
`rb_thread_call_without_gvl2`, rejected above): a
response a wait received, a handle `show` made (the notification is
shown), an action `handle_action` saw. Before, the interrupt fired as the
method returned and discarded it the same way. `Gvl::Held`, `TRIES`, and
the unreachable "the work had already run" are gone.

The Linux handle's `Mutex<Option<Arc<_>>>`, which raised `Error`
("already borrowed", "already mutably borrowed") for a turn another
thread held, is now `lock::Lock`, the maintainer's choice among the
audit's options: a share count and an exclusive flag under a `Mutex`
with a `Condvar`, grown from ferro-arboard's one-turn lock. A setter or
`update` waits for every shared turn to end, and any call waits for
`update`; each wait runs through `wait_until` with an unblocking
function, so `Thread#raise`, `Thread#kill`, Ctrl-C, and process exit end
it. Readers go first, so a `close` is never kept out by a waiting
setter. A setter takes its turn with the GVL held when it is free, and
runs there, since it is short; `update` takes and gives back its turn
without the GVL, so no Ruby code runs while an exclusive turn is out.
A shared turn lasts across `gvl::wait`'s tries, and between them a
signal trap can run Ruby code on the waiting thread: a setter there
would wait for its own thread forever. Each shared turn therefore records
its Ruby thread by `object_id` (never a `VALUE`, which compaction could
move), and a setter or `update` on a thread that holds one raises
`ThreadError`, "already borrowed: this thread's own wait or close is
using this NotificationHandle", as `Mutex#lock` raises for a thread that
holds the lock. A setter called from a wait's block cannot re-enter: the
block runs after the native wait returns and its turn ends.

The audit's other notify-rust row, `Notification.allocate` reaching
"uninitialized" (`Error`), is not part of this change: undefining the
allocator also takes away `dup` and `clone`, which would need native
versions that keep Ruby's semantics (singleton classes, instance
variables, `clone(freeze:)`), a design of its own.

Tests: Rust tests cover `drive`, `run`, the unblocking function, and
every path of the lock (shared turns together, the exclusive one
waiting, readers first, an unblock ending a wait, poisoning).
`test_gvl.rb` runs on macOS and Linux. On Linux CI only, against dunst:
a setter on another thread waits for a wait while this thread runs and a
`close` still ends the wait; `Thread#raise` and `Thread#kill` end a
setter's wait while the wait goes on; and a setter from a signal trap on
the waiting thread raises `ThreadError`.

  `@debug`, since `Zbus`, `Parse`, `Image`, and `CantOpen` hold another
  crate's value that no Ruby value can rebuild. One Ruby code makes is
  rebuilt where the variant holds only text or nothing (`Msg`,
  `SpecVersion`, `Conversion`, `ImplementationMissing`, and
  `ImageError`'s `TooBig`, `WrongDataSize`, `CantConvert`), and otherwise
  answers `nil`, as does a panic, which is no value of the crate's. That
  includes the macOS leaves under `Error::MacNotificationSys` built in
  Ruby: the same class is raised for `set_application`'s
  mac-notification-sys error and for notify-rust's error around one, two
  `Debug` texts, and which one a Ruby-made leaf stands for waits on the
  `MacOsError` question plan 011 leaves to the maintainer.
- **Consumed values.** notify-rust's waits and the Linux `close` take
  `self` (`src/xdg/mod.rs:101`, `:134`, `:214`, `:269`;
  `src/macos/nsusernotifications.rs:32`, `:73`, `:113`;
  `src/windows.rs:111`, `:123`, `:136`), and Rust drops a handle at the end
  of its scope, which `show`'s block already stood for (decision 4). The
  native handle keeps a `Slot` (`slot.rs`): live until a consuming call
  takes it, then the name of that call, which every later call's
  `IOError` names, as a closed IO's does. The end of `show`'s block takes
  it on every platform, unless a wait did; on macOS that drop sends, as
  before. Without a block, `show` uses the handle up only on macOS, where
  that drop is what sends; on Linux and Windows it returns the live
  handle the crate's `show` returns (`src/xdg/mod.rs:414-416`,
  `src/windows.rs:14-48`). `wait_for_action_async` and `close_async` borrow the handle
  (`src/xdg/mod.rs:183`, `:229`), so they now call borrowing native
  methods instead of the consuming ones and leave it usable; the reader
  and writer turns of decision 5 now matter only for them, and a setter
  during a consuming wait raises `IOError` at once. A consuming call
  marks the handle used up before it waits, as Rust moves it into the
  call, so an interrupted or failed wait uses it up too; a call already
  under way on another thread finishes. On Linux a consuming call, or the
  end of `show`'s block, also retires the handle's lock (`Lock::retire`),
  so the crate's handle, and its D-Bus connection (a socket and zbus's
  executor thread, `src/xdg/zbus_rs.rs:61`; zbus 5.19.0
  `src/connection/builder.rs:785-797`), drops when that call returns, as
  Rust drops a moved value, not when the garbage collector frees the Ruby
  object. The lock lets go of its own reference under its mutex, which is
  never held across a wait, so retiring never blocks with the GVL held.
  A shared turn already out keeps a reference, so a borrowing call on
  another thread finishes first and the value drops when the last turn
  ends, as no Rust borrow outlives a move; an exclusive turn out drops it
  instead of putting it back; and a setter or `update` waiting for a turn
  wakes and raises `IOError` naming the consuming call, where the first
  version left it waiting for a value that would never come back, which
  is why it left the drop to the collector. The drop runs where the last
  turn ends, with the GVL held when that is a Ruby method's end, which is
  sound because it never waits: zbus's `ConnectionInner` drop only
  notifies its listeners (`src/connection/mod.rs:86-93`), the socket and
  reader task close without blocking, and the executor thread ends on its
  own (`builder.rs:792-797`).
  `.await` takes a future, so `Future#value` answers once and raises
  `IOError` after, and `dup` and `clone` raise `TypeError`, as
  ferro-rfd's do. `Notification` is consumed by nothing: `show`,
  `finalize`, and the async shows borrow it.
- **Iterators.** None: notify-rust's one `impl Iterator`, `get_hints`, is
  `pub(crate)` (`src/notification.rs:321`). `get_capabilities` returns a
  `Vec`, which stays an Array, and `hints` a `HashSet`, which stays a
  `Set`.
- **`Duration`.** `From<Duration> for Timeout` is bound (decision 9). No
  bound item returns one.
- **Hidden and deprecated items.** `at_bus`, the `actions` setter, and
  `show_debug` are unbound; the macOS `Urgency` type stays (decision 11).
  The hidden statics `NOTIFICATION_DEFAULT_BUS`, `NOTIFICATION_INTERFACE`,
  and `NOTIFICATION_OBJECTPATH` (`src/xdg/mod.rs:41-55`) and the hidden
  `bail!` and `ensure!` macros were never bound.
- **Errors the gem makes.** Each now raises Ruby's class: `IOError` for a
  used-up handle or future, where Windows raised `Error` ("consumed by a
  wait") and macOS and Windows waits returned silently; `TypeError` for a
  notification only allocated, where it raised `Error`; `ArgumentError`
  for a wait without its block, now checked before the wait on every wait
  and `handle_action`, as `wait_for_action_async` already did, so the
  handle is not used up and no answer is lost. `ThreadError` for a setter
  in a trap during its own thread's borrowing wait (Follow-up: the GVL is
  never held) and Ruby's own `ThreadError` for a `Future` awaited from its
  own block stay. The class lookups in `error.rs` that raise `TypeError`
  or `ArgumentError` cannot be reached from public code and stay
  assertions.
- **Cargo features (ADR 002).** Not done here: install-time options need
  machinery no gem has yet, and the build stays as decision 2 says.
