# Plan 003: Bind notify-rust

Tokra's notification plugin needs desktop notifications, and ADR 001 puts
notify-rust in Ferro's first phase as a one-native-home crate: on macOS it
swaps `NSBundle`'s `bundleIdentifier` and installs the notification
center's one delegate, so a second copy in the process would undo the
first's hook and steal its delegate. Nothing else links it, so Ferro is its
home. This plan adds `ferro-notify-rust` 0.1.0.pre.1, which binds
notify-rust 4.18.2, the latest release (crates.io, published 2026-10-07).
[ADR 001](../adr/001.md), [plan 001](001.md), and [plan 002](002.md) hold
the rules and lessons this plan follows.

It also fixes the release tooling first: a new gem starts at
`0.1.0.pre.1`, and the bump task could only move forward, so
ferro-arboard and ferro-rfd released `pre.2` first. `rake
bump:<gem>:current` now releases the version a gem already has, refusing
once a tag here or on origin, or a CHANGELOG section, has it
(`tasks/bump.rb`, `Bump#release_current!`, tested in
`test/tasks/test_bump.rb`).

## Naming

ADR 001's table shows a crate without a hyphen. notify-rust has one, and
Cargo names its library `notify_rust`. The gem keeps the crate's name,
`ferro-notify-rust`, as gem names keep hyphens. The require path and
module follow the Rust identifier, `require "ferro/notify_rust"` and
`Ferro::NotifyRust`: RubyGems' habit of turning a hyphen into a slash
would give `ferro/notify/rust` and `Ferro::Notify::Rust`, a nesting the
crate does not have. The folder, task names, and commit scope are
`notify-rust`, the crate's name; the extension is `ferro_notify_rust`.
ADR 001's table gains this row. `FerroGem#version_file` derived the
version file's path from the gem name; it now takes the extension's
directory, which works for both kinds of name.

## Design decisions

1. **Naming.** See Naming above.
2. **Cargo features.** `z` (zbus, the default) with `async`, `images`,
   and `chrono` are built. The rest are not, each for its reason:
   - `d` and `d_vendored` add dbus-rs beside zbus. With both, notify-rust
     picks one at run time by the `DBUSRS` environment variable
     (`src/xdg/mod.rs:410-449`), and its author means them to exclude each
     other in 5.0 (`:390-392`). `d` links the system's `libdbus-1`, so
     every Linux install would need its headers, and `d_vendored` builds
     libdbus from source. They buy a second transport and nothing a Ruby
     program can see except `dbus_stack`, and the dbus-rs handle panics on
     the async methods (`:189-191`, `:231-234`). Tier 2 says follow the
     crate; the crate's default and its stated direction are zbus alone.
   - `z-with-tokio` and `tokio` run zbus on tokio, which needs a tokio
     runtime around every call; Ruby code never runs inside one. They add
     no API.
   - `debug_namespace` replaces the bus name with `de.hoodie.Notifications`
     (`src/xdg/mod.rs:41-48`), so no real server would answer. It is for
     the crate's own tests.
   - `preview-macos-un` replaces the macOS backend rather than adding to
     it: `NotificationHandle`, `id`, `urgency`, `show_async`, and the
     errors change, and `set_application` stops working
     (`src/macos/mod.rs:13-18`). `UNUserNotificationCenter` needs a signed
     app bundle (`check_bundle`), which `ruby` is not, and the feature is
     a preview. A gem built both ways would need an install-time switch;
     that waits for a bundled Ruby app that needs it.
3. **`Notification` is a native object.** rfd's builders were Ruby objects
   that rfd replayed (plan 002, decision 1). notify-rust's is different:
   its handle dereferences to the notification it showed, so
   `handle.summary("x"); handle.update()` changes the shown copy
   (`src/xdg/mod.rs:290-317`), and hints live in a `HashSet` and a map
   keyed by name (`src/notification.rs:303-318`). So the native layer
   wraps notify-rust's `Notification` in a `Mutex`, and the Ruby class
   calls private methods that run notify-rust's own setter. A setter
   returns the notification, as Rust's `&mut Notification` does, and on a
   frozen notification raises Ruby's own `FrozenError` (magnus
   `check_frozen`). `dup` and `clone` are notify-rust's `Clone`, and
   `finalize` returns a copy as the crate's does. The public fields read
   and write through accessors: notify-rust's own test assigns them
   (`tests/realworld.rs:85-110`), and a field holds what its setter
   stored. `hints` returns a `Set` of the hints in the `HashSet`; as
   notify-rust warns, it leaves out `Custom` and `CustomInt`, which live
   in the map (`src/notification.rs:68-74`).
4. **`show`, the handle, and `Drop` on macOS.** On macOS `show` sends
   nothing: it returns a handle holding a copy of the notification, and
   the handle sends it when it drops, unless a wait method sends it first
   and waits (`src/macos/nsusernotifications.rs:142-162`, `:252-257`).
   Rust drops a handle you never bind at the end of the statement, so
   `Notification::new().show()?` shows at once. Ruby has no scope-based
   drop: a handle would drop when the garbage collector frees it, seconds
   or minutes later, inside the collector. Ruby's way to end something at
   a known point is a block, so (tier 1):
   - `show { |handle| ... }` yields the handle and drops it when the
     block ends, even by an exception, as Rust drops on unwinding. A wait
     inside the block sends and waits; otherwise the drop sends.
   - `show` without a block drops the handle at once, so the notification
     appears, and returns the handle, now holding nothing: its waits
     return without calling the block, as notify-rust's do for a handle
     with no notification (`:39-41`, `:80-82`, `:114-116`).
   - A wait takes the notification out of the handle, as notify-rust's do,
     so a second wait returns without calling the block.
   On Linux and Windows `show` sends before it returns
   (`src/xdg/mod.rs:414-416`, `src/windows.rs:14-48`), the handle's drop
   only frees a D-Bus connection or a channel, and the block just yields
   the handle and returns the block's value. `schedule` and
   `schedule_raw` return a handle with no notification, as notify-rust's
   do (`nsusernotifications.rs:259-275`). An interrupt between `show`
   and its block's `ensure` can leave a handle holding a notification for
   the garbage collector; its free drops notify-rust's handle on a thread
   of its own, so the send never runs inside the collector with the GVL
   held, and a process that exits first may never send it. macOS's
   `NotificationHandle::new` is not bound: notify-rust plans to make it
   private ("TODO: make private in 5.0", `:16`), and `show` makes the same
   handle.
5. **Handles on Linux and Windows.** Rust's `wait_for_action`,
   `wait_for_response`, `on_close`, and `close` consume the handle; ADR
   001 drops `self` consumption. On Linux they wait through notify-rust's
   borrowing async methods (decision 6), so the Ruby handle stays usable:
   a second `wait_for_action` waits for the next signal about the same
   notification. The native handle follows Rust's borrow rules at run
   time, as a `RefCell` does: a wait, `close`, `id`, and the field
   readers borrow it shared, each through its own `Arc` clone, as
   notify-rust's `&self` methods do, so a `close` from another thread
   ends a wait, as notify-rust's own `close_async` example does
   (`src/xdg/mod.rs:155-178`). A setter needs `&mut`, which `Arc::get_mut`
   grants only when no share is out: while a wait or close runs it raises
   `Error` ("already borrowed: ...") at once, as Rust would refuse it at
   compile time. `update` takes the handle out of its slot while it runs,
   so every other call raises ("already mutably borrowed: ..."). No call
   ever waits for another. A first design held an `RwLock` across the
   wait; std's lock blocks new readers behind a queued writer, so a setter
   queued behind a wait would have kept a later `close` from ending it,
   with both threads uninterruptible. On Windows the native layer must
   hand notify-rust the handle itself, so after a wait the handle holds
   nothing: its waits return without calling the block, as on macOS, and
   every Builder method on it, setters and field readers alike, raises
   `Error` ("this NotificationHandle was consumed by a wait"), a state
   Rust code cannot reach. The handle answers every
   `Notification` method by acting on the notification inside it, as
   `Deref` and `DerefMut` do; setters return the handle, so
   `handle.summary("x").update` chains. On Linux the handle's own `id`
   (the server's id) shadows the setter `id(u32)`, as Rust's method
   resolution picks the inherent method first.
6. **The GVL, waits, and futures.** Every call that talks to D-Bus, the
   notification center, or a toast blocks, so it runs with the GVL
   released (plan 002's `gvl.rs`). Which calls an interrupt can cancel
   depends on what notify-rust exposes:
   - Linux `show`, `wait_for_action`, `wait_for_response`, `on_close`,
     and `close` poll notify-rust's own futures (`show_async`,
     `wait_for_action_async`, `close_async`), which the sync methods only
     `block_on` (`src/xdg/mod.rs:118-127`, `:139-142`, `:219`, `:280-286`,
     `:414-416`). The wait has an unblocking function, so Ctrl-C,
     `Thread#raise`, and `Timeout` end it and drop the future.
     `wait_for_action`'s mapping from a response to a string is ported
     from `src/xdg/mod.rs:119-124`: `"default"`, the action's key, or
     `"__closed"`, and nothing for a reply.
   - Linux `update`, `get_capabilities`, `get_server_information`, and
     `handle_action` have no async form, and macOS and Windows have none
     at all, so they run with no unblocking function, as rfd's dialogs
     do. zbus sets no timeout on a method call (zbus 5.19.0
     `src/connection/builder.rs:101`, `:479-485`, `:660`), so a server
     that never answers blocks them, uninterruptibly, as it blocks
     notify-rust's own callers; a macOS fire-and-forget send ends within
     about two seconds (mac-notification-sys `objc/notify.m:161-180`). A wait for the user
     (`handle_action`, macOS and Windows waits) can last until the user
     acts, and Ctrl-C and process exit wait for it.
   - Every future polled across `gvl::wait`'s tries passes through
     `sendable`, which makes the compiler check it is `Send`: under the
     M:N scheduler a Ruby thread can resume on another native thread
     between tries. No lock guard is held across a wait (decision 5).
   - Linux's async methods return a `Future`. notify-rust's are `async
     fn`s that borrow the notification or the handle, and like every Rust
     future they do nothing until polled. ferro-rfd's `Future` held rfd's
     future natively, because rfd starts work before the first poll on
     macOS; a borrowing future cannot be kept in a Ruby object, and
     nothing here starts early. So `Ferro::NotifyRust::Future` is Ruby:
     it holds the work and runs it, through the interruptible native
     calls above, when `value` is first asked, as the first poll does.
     `value` keeps the result or the `Error`, as `Thread#value` does; an
     interrupt drops the work, as dropping a Rust future does, and a later
     `value` starts it again. `show_async` and `show_async_at_bus` copy the
     notification when called, since the Rust future borrows it from that
     moment, and finish with a handle; `close_async` finishes with `nil`;
     `wait_for_action_async` calls its block with the
     NotificationResponse when `value` sees it.
   - On macOS, a wait off the main thread finishes only while the main
     thread runs its run loop (`nsusernotifications.rs:29-31`): ferro
     cannot tell whether something does, so it does not refuse, and the
     RDoc says so. On the main thread mac-notification-sys runs the run
     loop itself (`objc/notify.m:192-209`).
7. **Handlers are blocks, called with the GVL held.** notify-rust calls a
   closure inside the wait. Ruby code cannot run without the GVL, so the
   native layer records what the closure received, and Ruby yields it
   after the wait returns. `on_close` yields the CloseReason; a block that
   takes no argument ignores it, which covers both `CloseHandler` impls.
8. **Enums.** As plan 002, decision 8: unit variants are frozen
   instances (`Urgency::Low`, `Timeout::Never`, `CloseReason::Expired`,
   `NotificationResponse::Default`, `Hint::Invalid`, `DbusStack::Zbus`),
   and variants with data are `Data` classes. A variant's members take
   the names notify-rust binds its fields to: `Hint` single values are
   `value` (`src/hints.rs:181-205`), `Hint::Custom` and `CustomInt` are
   `key` and `value`; `NotificationResponse::Action` is `key`, `Reply` is
   `text`, and `Closed` is `reason` (`src/response.rs:53-62`);
   `CloseReason::Other` is `raw_reason` (`:36-37`);
   `ActionResponse::Custom` is `key`; `NotificationId` and
   `Timeout::Milliseconds` hold `value`. `Default` impls become
   `.default`; `PartialEq` and `Hash` become `==`, `eql?`, and `hash`,
   which `Data` gives by value.
9. **Conversions.** A `From` impl becomes a class method `from`,
   `TryFrom` becomes `try_from`, and `FromStr` becomes `from_str`; each
   raises where Rust returns `Err`. `From<Timeout> for i32` is `to_i`,
   Ruby's own conversion to an Integer. An error type that is not
   notify-rust's (`FromStr`'s `ParseIntError`, `from_key_val`'s `String`)
   raises `ArgumentError` with Rust's text, as Ruby's `Integer("x")` does
   for its own parse. `Timeout` from a `Duration` is not bound: Ruby has
   no `Duration`, the value Ruby code uses for one is seconds as a Float,
   and an Integer already means milliseconds here, so one method taking
   both would read `5` and `5.0` a thousand times apart. `Notification#timeout`
   takes a Timeout or an Integer, through `From<i32>`. `schedule` takes a
   `Time`, the Ruby value for chrono's `DateTime<Tz>`, and passes its
   `to_i`, as notify-rust passes `timestamp()` (`src/notification.rs:495`).
10. **Errors.** `Error < StandardError` is notify-rust's `Error`, with one
    subclass per `ErrorKind` variant built here: `Msg`, `Zbus` (Linux),
    `MacNotificationSys` (macOS), `Parse`, `SpecVersion`, `Conversion`,
    `Image` (Linux), and `ImplementationMissing`. The message is
    notify-rust's `Display` text. `Error` keeps its `kind` private and
    has no accessor (`src/error.rs:16-19`), so the native layer reads the
    variant's name from the derived `Debug` text (`Error { kind: Zbus(`),
    and a Rust test pins that text for every variant through the public
    `From<ErrorKind>`; a variant ferro does not know raises the base
    class (`ErrorKind` is `#[non_exhaustive]`). On macOS,
    mac-notification-sys's error is another enum of enums: each leaf is a
    class under the variant it sits in,
    `Error::MacNotificationSys::Application::AlreadySet` and
    `::CouldNotSet` (each with `name`), and
    `Error::MacNotificationSys::Notification::ScheduleInThePast`,
    `::UnableToSchedule`, `::UnableToDeliver`, so `rescue
    Error::MacNotificationSys::Application` catches both of its kinds.
    zbus's error is another crate's, so `Error::Zbus` carries its text and
    no subclasses. `ImageError` is a separate exception, as it is a
    separate type that `Image`'s constructors return; its `Display` ends
    with a newline (`writeln!`, `src/image.rs:153-163`), which the message
    keeps. A panic inside notify-rust raises the base `Error` with
    `notify-rust panicked: <message>` (plan 001, decision 5).
11. **Deprecations.** Rust's `#[deprecated]` warns at compile time. Ruby's
    counterpart is a warning in the `:deprecated` category, shown when
    `Warning[:deprecated]` is on: `Notification#actions` and
    `Notification.at_bus` warn with notify-rust's note, and on macOS
    `Urgency` is a deprecated constant (`deprecate_constant`), as its
    re-export is there (`src/lib.rs:218-222`). `ActionResponse`'s
    deprecation is in its doc only, so the RDoc says it. `show_debug` is
    not bound: its own note says it "was never meant to be public API",
    and it prints with Rust's `println!`, past Ruby's `$stdout`; `show`
    and `inspect` do the same.
12. **`SPEC_VERSION` is not bound.** It is a lazy static that calls
    `get_server_information` the first time an image hint is sent
    (`src/lib.rs:226-233`); a Ruby constant cannot be lazy, and reading it
    at `require` would talk to D-Bus. Its type, `miniver::Version`, sits in
    a private module. `get_server_information.spec_version` gives the same
    fact.
13. **Process-wide state on macOS.** mac-notification-sys swizzles
    `-[NSBundle bundleIdentifier]` once per process, the first time
    `set_application` runs or a notification is sent, and makes its
    delegate the notification center's one delegate
    (mac-notification-sys `src/lib.rs:131-158`, `objc/notify.h`,
    `objc/notify.m:303-316`). The gem does not change that: the first call
    to `set_application` wins, a second raises `AlreadySet`, and sending a
    notification first claims the default (`com.apple.Finder`, found by
    AppleScript, `src/lib.rs:119-138`) so a later `set_application`
    raises `AlreadySet` too. No other gem in the process may link
    notify-rust or mac-notification-sys (ADR 001); the README says so.
14. **Ractors (ADR 001, section 7).** notify-rust's `Notification` and its
    handles are `Send`, and every call builds or locks its own values, so
    the extension is marked Ractor-safe. `Notification` and the value
    classes are frozen-shareable; a handle and a `Future` stay with their
    Ractor. Windows runs the Ractor tests in a child process, for the Ruby
    4.0.9 barrier bug plan 001 found.
15. **No panic reaches Ruby.** Every notify-rust call runs under
    `catch_unwind`. Known panics are refused first with notify-rust's own
    error: `at_bus` unwraps `NotificationBus::custom` (`:132-134`), which
    `show_async_at_bus` returns as `Error::Msg("invalid subpath")`
    (`:531`), so `at_bus` raises that. `handle_action` unwraps the session
    connection (`src/xdg/zbus_rs.rs:118`); that panic is caught and raises
    `Error` with `notify-rust panicked: ...`, since notify-rust has no
    error to refuse it with. `exe_name` unwraps the executable's path,
    its file name, and its UTF-8 text (`src/notification.rs:24-33`),
    which fails without `/proc` on Linux or for a non-UTF-8 path to
    `ruby`. Ruby's allocator therefore makes an empty notification, and
    `initialize`, which magnus guards, builds notify-rust's under
    `capture`, so that panic raises `Error`; a notification only allocated
    raises `Error` ("uninitialized ...") from every method. `auto_icon`
    and `at_bus` call `exe_name` under `capture` too.
    `Image::from_raw_data` multiplies `i32`s (`src/image.rs:45`), which
    panics on overflow in a debug build and wraps in a release one; the
    gem builds release, so it behaves as notify-rust does there.
16. **Strings and paths.** `&str` takes a String, converted to UTF-8 by
    magnus; a wrong type raises `TypeError`. `Image.open` and `image` take
    a String or an object with `to_path`, through `File.path`. A NUL byte
    in a string reaches D-Bus, whose daemon drops the connection, which
    zbus reports as `Error::Zbus`; nothing panics.
17. **Dependencies.** notify-rust `=4.18.2` with `images` and `chrono`
    beside its default. chrono `0.4` on macOS, notify-rust's own, to build
    the `DateTime` that `schedule` takes. magnus `0.9.3` with `bytes` and
    rb-sys `0.9.130`, the pins every gem shares. zbus `5`, notify-rust's
    own, as a Linux dev-dependency, so a Rust test can build the error
    notify-rust wraps. The tests use Fiddle, a gem Ruby bundles, in macOS
    child processes, and dunst, dbus-daemon, dunstctl, and dbus-send on
    Linux, which CI installs.
18. **Tooling.** `FerroGem#version_file` took the version file's path
    from the gem's name, which for `ferro-notify-rust` gave
    `lib/ferro/notify/rust/version.rb`; it now sits beside the extension.
    `platform_sigs` takes a list of files per platform, and a file may
    serve two platforms: `deref.rbs` declares what Linux and Windows
    share, the handle's `Deref` and `urgency`, which one declaration must
    describe, since Steep reads every file at once.

## Tests

Tests run against the real crate and, on Linux, a real notification
server: the helper starts a private session bus (`dbus-daemon`) and
`dunst` on it, so nothing touches the user's own session, and drives the
server with `dunstctl` (invoke the default action, close a
notification). dunst offers other actions only through a menu, so a
named action arrives as the `ActionInvoked` signal a server sends, through
`dbus-send` on the same bus; notify-rust's wait reads it as it would
dunst's. Tests that need the server skip, saying so, where `dbus-daemon`,
`dunst`, or a display is missing. On macOS a notification sent from a
process the notification center does not know is never confirmed
delivered, so mac-notification-sys reports it auto-dismissed after two
seconds; the macOS waits run in a child that also removes delivered
notifications through AppKit every half second, so a Mac that does show
one still ends the wait.

The first Linux run found what the plan's first design got wrong: a
`Mutex` held across a wait made `close` from another thread wait for the
wait it was meant to end, which notify-rust's own `close_async` example
does; the handle's lock now follows Rust's borrows (decision 5). A macOS
probe found that `set_application` with an installed app makes later
notifications really show, which is why the tests never send after it.

A review then found, and this session fixed: `Notification::new` ran in
magnus's `extern "C"` allocator, where `exe_name`'s panic would abort the
process (decision 15); a setter queued behind a wait on the first
design's `RwLock` blocked a later `close` (decision 5); no compile-time
check that polled futures are `Send` (decision 6); the README and plan
claimed D-Bus calls time out; a macOS handle freed by the garbage
collector would send inside the sweep (decision 4); the image inside
`hints` was not frozen; `wait_for_action_async` without a block failed
only at `value`; `set_application` re-read its name from `Display`; the
macOS sweeper removed every delivered notification of the faked app, not
only the tests'; the Linux tests fired signals before the waiter's match
rules existed, and slept instead of waiting for them (they now read
dbus-daemon's `GetAllMatchRules`); the deprecation category was untested;
and `bump:<gem>:current` now also refuses a version below one already
released. A wrong expectation in the Linux tests surfaced on the way:
a test-sent NotificationClosed leaves dunst's notification on screen, so
`dunstctl close` dismissed that one, and the next notification expired
after dunst's ten-second default; the test now closes it first.
