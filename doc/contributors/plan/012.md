# Plan 012: The gate runs before a push, not at each commit

Ferro's commit hook ran the whole gate. A commit took as long as the gate
does, across seven gems, so the only practical unit of work was one large
commit a session, which is the opposite of small steps on a trunk. The
maintainer's decision, on 2026-11-13, is that Ferro works trunk-based, as
Tokra now does (its plan 061): small complete commits on `trunk`, each
pushed once the gate passes. This plan moves the gate from each commit to
each push, and gives the repository a setup script anyone, or any CI
runner, can run.

## The hook

`.githooks/pre-push` runs `bundle exec rake` when a push moves a branch.
It reads the remote side of each line git gives it, which is always a
full ref, and skips tags and deletions, so `rake release:<name>:tag`,
which pushes only a tag, runs no gate.

The gate tests the working tree, so the hook refuses a push unless every
branch in it gets the commit that is checked out, with nothing
uncommitted and nothing untracked. Untracked files count because the
tests and the compiler read them: a file you forgot to add would pass
here and be missing on CI. An ignored file does not count.

On Linux it runs the gate as ci.yml's first pass does, under `xvfb-run`,
and a test pins both commands to ci.yml's. It also unsets
`WAYLAND_DISPLAY`: arboard takes a Wayland desktop before the X display
`xvfb-run` gives it, and the clipboard tests would then write the
desktop's own clipboard. CI's second pass, each gem's Ruby tests under
Wayland, stays CI's.

From a worktree, git hands a hook `GIT_DIR`. The hook unsets it and its
kin once it has found the working tree, or every git the gate runs would
act on that worktree, the ones in tests that make repositories of their
own included. `test/test_helper.rb` still drops `GIT_INDEX_FILE`, for a
run from any other hook.

## bin/setup

Ferro had no setup script. `bin/setup` installs the tools `mise.toml`
pins, the REUSE tool at CI's version, and the bundle, then writes a stub
into the clone's shared hooks folder that runs the hook from whichever
worktree pushes. It writes the stub only where none exists or the one
there is its own, by a marker line, so a hook you keep there yourself
survives. A stub was chosen over `core.hooksPath` because pre-commit
refuses to install under one.

Every step does nothing when it is already satisfied, it asks nothing,
and it runs no sudo, so a CI runner or a build machine can run it before
every check. With `CI=true` it installs the bundle as ci.yml's setup-ruby
does, locked to `Gemfile.lock` in `vendor/bundle`, and skips the commit
hook.

Where `core.hooksPath` is set, git runs the hooks in that folder and
never the clone's own. `bin/setup` still writes the stub, and says what
follows: a push runs the gate only if the pre-push hook in that folder
hands off to the stub, and pre-commit, which refuses to install there,
is left out.

The README's "Contributing" now says to run `bin/setup`, where it listed
the same steps by hand.

`.pre-commit-config.yaml` keeps the `bundle check` and loses the gate.

## The rules

AGENTS.md's "Committing" now describes small commits on `trunk`, each
complete, with the gate before the push, and the `commit-session` skill
follows it. `rake bump:<name>:*` still runs the gate itself before it
commits, and tags and RubyGems pushes keep their rules.

One release step changes order. `rake release:<name>` tagged the commit
and then pushed `trunk`. That push now runs the gate when `trunk` is
ahead of origin, and a push the gate refused would have left the tag
behind, so that the next try stopped at "already exists" and only
hand-run git could clear it. It now pushes `trunk` first and tags after.

## Tests

`test/tasks/test_pre_push_hook.rb` drives the real hook in a real
repository, with stand-ins for `bundle` and `xvfb-run`: a branch that
moves to the checked-out commit runs the gate, by any local name; a tag, a
deletion, and an empty push do not; another commit, in any line of the
push, uncommitted changes, staged or not, and an untracked file are
refused before the gate; an ignored file is not; and a gate that fails
fails the push with its status. One test pushes for real from a worktree
to a bare repository, so the hook gets the environment git gives it, and
checks that the gate's command inherits no `GIT_DIR`. On Linux another
checks that the gate is kept off a Wayland desktop. The last checks that
git tracks the hook as executable.

`test/tasks/test_setup.rb` runs the real `bin/setup` in a real
repository with a stand-in `mise`: what it installs for a person, for a
CI runner, and where `core.hooksPath` is set, with what it says there;
that its stub runs the hook of whichever worktree pushes, and lands in
the clone's shared hooks folder when a worktree runs the script; that it
replaces an earlier stub of its own, makes the hooks folder when there
is none, and leaves a hook that is not its own, even one that quotes the
marker. One test goes the whole way: `bin/setup`'s stub, the hook as
shipped, and a real `git push`, whose refs reach the hook only through
the stub's standard input. It also holds the REUSE tool's version to
ci.yml's.

`test/tasks/test_release.rb` checks the release's new order, and that a
branch push that fails stops it before any tag.

## Left for later

- Windows has no `bin/setup.ps1`, and the hook and `bin/setup` are
  untested there.
- `bin/setup` does not check Linux's system packages; a missing one fails
  the compile, which names it.
- The REUSE tool's version is written in ci.yml and in `bin/setup`. A pin
  in `mise.toml` that both read would leave one.
- `rake package:install` gives `gem install` only an empty gem home and
  Ruby's default one. After a `CI=true` setup the bundle is in
  `vendor/bundle`, so it would likely not find `rb_sys` there. It is not
  in the gate, and this was read from the code, not run.
- On a Mac the gate still shows real notifications and dialogs in the
  session that runs it. Sorting those tests from the rest, as Tokra's
  `test:core` does, would let someone run everything else at their own
  desk.
