# Plan 014: The desktop tests run apart from the rest

Ferro's gems bind the clipboard, dialogs, notifications, and global
hotkeys, and their tests drive the real thing. Run on a Mac, the gate
wrote your clipboard, showed notifications and file panels, and
registered hotkeys for the whole session, in the session of whoever ran
it, and AGENTS.md did not say so. Nothing let you run the rest at your
own desk without that. Plan 012 left it for later.

The maintainer's decision: the tests that use the desktop go in tasks of
their own, which run them only when a variable the gate sets says they
may, and which skip each one, naming the reason, where there is no
desktop session. This plan sorts the tests, shapes the tasks, the
variable, and the probe, and says what the runs showed.

## Which tests use the desktop

A test uses the desktop when it changes what the session's person has or
sees: it writes or opens the session's clipboard, shows a notification,
a dialog, or a window, registers a hotkey with the session, or presses
keys in it. A test that does these things on a display, a bus, or a
server the suite starts for itself, such as the private Xvfb of
ferro-global-hotkey's Linux tests, does not. Nor does a test that only
makes an app or a window that never shows, as ferro-rfd's AppKit parent
tests do.

That is a matter of what each test calls, not of its gem, so every gem's
tests were read, and run on a Mac with no desktop session, where any test
that reaches the clipboard, the notification center, or a file panel
cannot (see "What the runs showed").

- ferro-arboard: every test that makes a `Clipboard`, which opens the
  session's clipboard, and most of its tests do. The rest check values,
  errors, Debug text, the platform's API, the gem's metadata, and, on
  Linux, a clipboard with no display server at all, in a child.
- ferro-global-hotkey: `test_manager.rb`, which registers hotkeys with a
  manager made in the test process; `test_macos_events.rb`, which
  registers one in a child; and `test_windows_events.rb`, which presses
  keys with `SendInput`. On Linux the manager's tests use the private
  Xvfb, but the same file registers with the session on macOS and
  Windows, so the whole file is a desktop test. `test_linux_events.rb`
  uses only the private Xvfb, and stays.
- ferro-notify-rust: `test_linux.rb`'s `TestLinux`, whose dunst draws on
  the display the suite runs under, which at your desk is yours;
  `test_windows.rb`, whose toasts show; and the three tests in
  `test_macos.rb` that show a notification. The rest of `test_macos.rb`
  asks Launch Services and AppleScript about bundles and shows nothing.
  `test_gvl.rb` asks AppleScript on macOS and a bus nobody serves on
  Linux.
- ferro-rfd: `test_macos_dialogs.rb`, which opens real panels and aborts
  them. Every other dialog test is refused before rfd opens anything,
  answered by a stand-in zenity, or makes an app with the Prohibited
  activation policy and a window it never orders front.
- ferro-idna, ferro-time, and ferro-url touch nothing of the desktop:
  they compute, and their child processes exist to catch panics.
- The Rust unit tests (`cargo test`) touch nothing either. rfd's macOS
  tests make an `NSApplication` and panic, as rfd does, before any
  dialog is built.

The desktop tests move into each gem's `test/desktop/`. A file whose
tests are all desktop tests moves whole, with `git mv`. A file that mixes
the two splits: its desktop tests move to a file of the same name under
`test/desktop/`, in a class whose name says what it uses
(`TestClipboardError` beside `TestError`), so no two classes in a gem
share a name. A test changes only where it moves.

## The tasks

`tasks/test.rake` finds each gem's desktop tests by their directory and
makes, for each gem:

- `test:core:<name>`: the gem's Rust tests, then its Ruby tests outside
  `test/desktop/`.
- `test:desktop:<name>`, for a gem that has any: its Ruby tests in
  `test/desktop/`.
- `test:<name>`: both, as before.

and across every gem `test:core` (the tooling's tests too), `test:desktop`,
`test` (both), and `test:ruby`, which CI runs again under Wayland, as
before. The Minitest tasks behind them are `test:ruby:core:<name>` and
`test:ruby:desktop:<name>`, and `test:ruby:<name>` runs both.

A directory over a list in `tasks/ferro_gems.rb`, or a marker in each
file: the path says what a test file is wherever you meet it, in a diff or
a stack trace, and a new file joins its kind by where it is written, with
nothing else to update.

## The variable

`FERRO_DESKTOP=1` lets a test process use the desktop.

- A desktop task runs its tests only when `FERRO_DESKTOP` is 1 in the
  rake that runs it, and gives it to the test process. Otherwise it runs
  nothing and prints
  `test:desktop:<name>: skipped, since its tests would use this session's desktop (set FERRO_DESKTOP=1 to run them; the gate does)`.
- A core task removes it from its test process, whatever your shell
  exported.
- The gate sets it: the Rakefile's default task and each `gate:<name>`
  run `test:allow_desktop` first. The pre-push hook and CI run the gate,
  so they run the desktop tests. CI's Wayland pass runs `rake test:ruby`,
  not the gate, and sets the variable in its step.

So `bundle exec rake test`, `test:<name>`, and every core task open
nothing, wherever you run them, and only the gate, or a task you give
`FERRO_DESKTOP=1` yourself, uses your desktop. The variable could
instead have been set by each desktop task for its own process, as
Tokra's real-window tasks set theirs. Then every `rake test:<name>` at
your desk would write your clipboard again, which is the surprise this
plan removes.

## No desktop session

A Mac can run a process outside any login session, as a build machine's
daemon does: `launchctl managername` prints `System` there, not `Aqua`.
There is no window server, so arboard answers every clipboard call with
`ClipboardNotSupported`, and a file panel never opens.
`Desktop.session_unavailable_reason` (`tasks/desktop.rb`) asks launchd
once, on macOS only, as Tokra's `Desktop` does (its plan 061), and names
the session when it is not Aqua.

The desktop tasks load `Desktop.skip_each_test_without_a_session`, which
makes every test in the process skip there with that reason, before its
setup runs, so a teardown that needs what setup made does not run either.
A Mac with a GUI session, a person's or CI's runner, gets `nil` and skips
nothing.

Some desktop tests would pass with no session: global-hotkey registers
its hotkeys with nobody to press them, and mac-notification-sys reports
an undelivered notification auto-dismissed after two seconds. They skip
there too, since what they check is the session's, and the session is
not there.

Off macOS the probe finds nothing missing. On Linux the gate brings its
own display, under `xvfb-run`, and a missing one is a broken setup that
the tests report as they always have. Windows is left as it is: nothing
here changes what its tests do.

## The tripwire

A desktop test filed among the others would reach your desktop the first
time someone ran the core tasks. So each gem's test helper calls
`Desktop.guard` on the gem's own ways onto the desktop, and in a process
without `FERRO_DESKTOP=1` each raises `Desktop::Outside`, naming what it
would have done and where the test belongs:

- ferro-arboard: `Clipboard.new`.
- ferro-global-hotkey: `GlobalHotKeyManager.new`.
- ferro-notify-rust: `Notification#show`, and on Linux `#show_async`,
  `#show_async_at_bus`, and the suite's notification server.

The guard wraps a method in the test process only: it calls nothing of
the crate in its place, and in a desktop process it is never installed.
It does not reach a child process a test starts. ferro-rfd has none: its
core tests call its terminal methods on purpose, where rfd refuses them
or a stand-in zenity answers, and its one desktop file opens its panels
in children.

## Saving the clipboard

ferro-arboard's helper saved the clipboard's text when it loaded and put
it back after the run. It now does so only in a desktop process with a
session, since a core process never opens the clipboard, and with no
session there is none to save.

## Tests

`test/tasks/test_desktop.rb` checks the variable, the guard (it refuses
outside a desktop run and names what it refused, and leaves the method be
inside one), the skip (every test of a throwaway suite skips with the
reason and runs neither setup nor teardown, and nothing skips with a
session), and launchd's answer, as Tokra's `test_desktop.rb` does.

`test/tasks/test_desktop_tasks.rb` loads the real Rakefile in a child rake
whose `sh` records commands instead of running them: each core task runs
every test file of its gem but the desktop ones, and each desktop task
only those; nothing `test:core` reaches is a desktop task; a desktop task
runs nothing without the variable and says so, and with it gives its test
process the variable and the skip; a core task takes the variable away;
and the gate's tasks set it before anything else.

Each gem's tests check that its helper guards what the list above names,
by the method's owner, without calling it.

## What the runs showed

Before any change, each gem's `rake test:<name>` ran on a Linux machine,
set up as the hook sets it up, under `xvfb-run`:

| Gem | Rust tests | Ruby runs | Skips |
|---|---|---|---|
| ferro-arboard | 32 | 94 | 6 |
| ferro-global-hotkey | 36 | 129 | 8 |
| ferro-notify-rust | 37 | 115 | 13 |
| ferro-rfd | 32 | 124 | 19 |
| ferro-idna | 11 | 44 | 0 |
| ferro-time | 55 | 1753 | 0 |
| ferro-url | 33 | 130 | 2 |

Every skip names its reason, and all but four are another platform's
tests: arboard's Wayland-only test, and its test of a lock only Linux
reads release; global-hotkey's test of a Windows error code; rfd's test
of a handle its portal backend ignores. An earlier run, on a machine
with no xdotool or dunst, skipped 21 more of global-hotkey's and 27 more
of notify-rust's, by name: the private X server asked for xdotool though
`TestManager` presses no key.

On a Mac with no desktop session (`launchctl managername` printed
`System`), nothing hung. arboard failed 53 of its 94 tests with
`ClipboardNotSupported`, among them tests that expected another error
from a clipboard they could not open; rfd failed the 3 tests of
`test_macos_dialogs.rb`, whose children ended without an answer; and
global-hotkey's 129 tests, notify-rust's 115, and rfd's other 121 passed,
as did every Rust test and idna's tests.

After the change, the gate's runs on Linux split each gem's Ruby tests
into core and desktop, and together they are the runs above with one
more test each in arboard, global-hotkey, and notify-rust, the check of
the helper's guard; the skips are the same. ferro-idna, ferro-time, and
ferro-url have no desktop tests.

| Gem | Core runs | Desktop runs |
|---|---|---|
| ferro-arboard | 23 | 72 |
| ferro-global-hotkey | 114 | 16 |
| ferro-notify-rust | 84 | 32 |
| ferro-rfd | 121 | 3 |

`rake test:core` also passed on Linux with no `DISPLAY`, no
`WAYLAND_DISPLAY`, a session bus that does not exist, and
`FERRO_DESKTOP=1` in the shell, with the same counts: no core test needs
a display or a bus, so none can reach yours.

On a Mac with no desktop session, `test:core` passed, with only other
platforms' skips, and each of the 123 desktop tests skipped with
`no macOS GUI session (launchctl managername is "System", not "Aqua")`.
On a Mac with a GUI session, both passed, and the desktop tests skipped
only other platforms' tests and arboard's two shapes macOS draws.

## Left for later

- The private X server of global-hotkey's tests asks for xdotool, which
  only the event tests use, so on a machine without it `TestManager`'s
  Linux tests skip with them.
- notify-rust's Linux tests start their own bus, but dunst draws on the
  display they run under. A private Xvfb for dunst, as global-hotkey's
  tests have, would let `TestLinux` leave your screen alone and join the
  core tasks.
- The packaging check's load test for ferro-arboard still opens the
  clipboard, to prove the extension loads, and reads and writes nothing.
