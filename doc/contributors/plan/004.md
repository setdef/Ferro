# Plan 004: Bind global-hotkey

Tokra's global-shortcut plugin needs system-wide hotkeys, and ADR 001 puts
global-hotkey in Ferro's first phase as a one-native-home crate: on macOS
each copy installs a Carbon event handler that returns `noErr`, so the last
copy loaded swallows every hotkey; on Windows each copy registers its own
window class; on Linux each runs its own X11 thread. Nothing else links it,
so Ferro is its home. This plan adds `ferro-global-hotkey` 0.1.0.pre.1,
which binds global-hotkey 0.9.0, the latest release (crates.io; the tag
`global-hotkey-v0.9.0` of https://github.com/tauri-apps/global-hotkey).
[ADR 001](../adr/001.md) and plans [001](001.md), [002](002.md), and
[003](003.md) hold the rules and lessons this plan follows.

## Naming

ADR 001's row for a hyphenated crate applies: the gem is
`ferro-global-hotkey`, the folder, tasks, and commit scope are
`global-hotkey`, and the require path and module follow Cargo's library
name, `global_hotkey`: `require "ferro/global_hotkey"`,
`Ferro::GlobalHotkey`, extension `ferro_global_hotkey`. global-hotkey's
public module `hotkey` (`src/lib.rs:57`) becomes `Ferro::GlobalHotkey::Hotkey`,
since the crate does not re-export `HotKey`, `Code`, or `Modifiers` at its
root: Rust code names them `global_hotkey::hotkey::HotKey`.

## Bound API

no platform-only public item: its three backends sit behind one
`platform_impl` (`src/platform_impl/mod.rs:5-33`), so the gem has no
platform signature file. Only two values differ by platform, `CMD_OR_CTRL`
and the meaning of `CmdOrCtrl` in a parsed hotkey.

## Design decisions

1. **Naming.** See Naming above.
2. **Cargo features.** Both are built, as ADR 001 asks. Neither adds Ruby
   API. `serde` derives `Serialize` and `Deserialize`; Ruby has no serde,
   and a Ruby program serializes with its own tools. The strings serde
   would write for a `HotKey` are `HotKey#to_s` and `HotKey.from_str`
   (`src/hotkey.rs:61-82`), and for a `Code` they are its name. `tracing`
   logs one thing: why the Linux X11 thread stopped, such as no X server
   (`x11/mod.rs:34-37`). With no tracing subscriber in the process, which
   a Ruby program never has, the log goes nowhere, so the RDoc says what
   that failure looks like: `register` returns as if it had worked.
3. **The manager.** `GlobalHotKeyManager` is a Ruby class holding a native
   `Native::Manager` that owns global-hotkey's manager. The native object
   is made by a native function, never by Ruby's allocator, so a panic in
   `new` is caught. Rust drops a manager at the end of its scope, which
   unregisters every macOS hotkey and removes the Carbon handler, destroys
   the Windows window and with it its hotkeys, or ends the Linux thread
   (rows 5). Ruby has no scope-based drop; the garbage collector frees the
   manager instead, at some later point, so the RDoc says to call
   `unregister_all` when you are done. The drop runs under
   `catch_unwind`, as a panic in a GC sweep would abort the process.

   The collector frees an object on whichever thread sweeps, and the
   macOS and Windows drops belong to the thread that made the manager:
   Carbon's `RemoveEventHandler` and `UnregisterEventHotKey`, which the
   crate expects on the main thread (`src/lib.rs:15-18`), and Win32's
   `DestroyWindow`, which cannot destroy a window another thread created
   (Microsoft's `DestroyWindow` documentation). Run elsewhere, the Windows
   drop would fail silently and leave the window and all its hotkeys
   registered system-wide, still delivering events, for as long as its
   thread lives. So the native manager sits in an `Owned` (`owned.rs`),
   after Tokra's `ThreadBound`: it records the owner thread, drops on it
   at once, and when dropped on any other thread moves the value to a
   graveyard that the owner drains on its next native manager call
   (`GlobalHotKeyManager.new` or any method). Until then the hotkeys stay
   registered, the price of never calling those APIs off their thread. A
   manager whose owner thread ended stays in the graveyard and is never
   dropped, so no stale `HWND` is ever used: a `ThreadId` is never reused.
   Posting `WM_CLOSE` to the window instead was rejected: global-hotkey
   keeps its `HWND` private, so the gem would have to find it by
   enumerating the thread's windows, and a reused handle could close
   another window. Linux's drop only sends its X11 thread a message, which
   any thread may, so it is not deferred.

   Windows' manager holds an `HWND`, so it is not `Send`, which magnus
   requires of every wrapped type; the wrapper asserts `Send` with a
   SAFETY comment. Moving the handle is sound: another thread's
   `register` fails, since `RegisterHotKey` "cannot associate a hot key
   with a window created by another thread" (Microsoft's documentation),
   and arrives as `Error::OsError`; its `unregister` fails as
   `Error::FailedToUnRegister` (UNVERIFIED, Windows never ran here);
   neither touches the window; and the destructor never runs off the
   owner (above). Clippy's `non_send_fields_in_send_ty` names the same
   field, so the impl carries the repository's first approved Clippy
   exception (`clippy_exceptions.rb`), which the deferred drop does not
   remove, since the wrapper still has to be `Send`. On macOS only one
   manager can live at a time: Carbon's `InstallEventHandler` refuses the
   same handler and user data twice (`macos/mod.rs:55-69`), so a second
   `GlobalHotKeyManager.new` raises `Error::OsError` with the text
   `std::io::Error::last_os_error` gives, "Undefined error: 0 (os error 0)"
   here. The RDoc and README say to keep one manager.
4. **The receiver.** global-hotkey's channel is a process-wide static
   whose sender never drops (`src/lib.rs:87-88`), so `receiver` always
   returns the same channel. `GlobalHotKeyEventReceiver` is a frozen Ruby
   object with no state: every instance reads that static channel, so
   `dup` and `clone` behave as crossbeam's `Clone` does, `same_channel` is
   true for any two receivers, and a receiver is Ractor-shareable, as
   crossbeam's `Receiver` is `Sync`. `capacity` is `nil` (unbounded) and
   `is_full` is false. Rust's `iter` and `try_iter` return iterators; Ruby's
   return Enumerators, lazy as Rust's are: `iter` blocks for each event and
   never ends, `try_iter` ends at the first empty read.
5. **The event handler.** global-hotkey calls the handler on whatever
   thread saw the key: its X11 thread on Linux, the main thread inside the
   run loop on macOS, the window's thread and a polling thread of its own
   on Windows (`x11/mod.rs:256-294`, `macos/mod.rs:304-339`,
   `windows/mod.rs:147-175`). Ruby code cannot run on a thread Ruby did not
   start, or on a Ruby thread without the GVL, so the native handler runs
   no Ruby. It pushes each event into a second static channel, and
   `set_event_handler` starts one Ruby thread that waits on that channel
   (with the GVL released, decision 6) and calls the handler with each
   event. The handler therefore runs on that thread, when it can take the
   GVL, not on the thread that saw the key. global-hotkey keeps the
   handler in a `OnceCell` (`src/lib.rs:89`, `:118-124`), and the Ruby side
   follows it: the first call decides for the life of the process, and
   later calls change nothing; and once global-hotkey has sent any event,
   its cell holds "no handler" (`:127`), so a later call changes nothing
   either. `set_event_handler(nil)`, or a call with neither handler nor
   block, is `None`: events keep going to the receiver. The handler is a
   block or any object that responds to `call` (Rust's `Fn`), not both. An
   exception the handler raises ends the handler thread, and Ruby reports
   it as it reports any thread's; later events are dropped rather than
   kept in memory nobody reads, since global-hotkey sends them to the
   handler, never back to the receiver.
6. **The GVL.** `recv` and `recv_timeout` wait for a person to press a key,
   so they run with the GVL released and with an unblocking function, using
   ferro-rfd's retry loop (`gvl.rs`). crossbeam has no way to cancel a
   `recv` from outside, so the wait is a crossbeam `select!` over the event
   channel and a one-slot cancel channel that the unblocking function
   fills; Ctrl-C, `Thread#raise`, `Thread#kill`, and `Timeout` end it. An
   event that arrives during the wait usually stays in the channel for the
   next read, but when the event and the interrupt are ready together
   `select!` picks one at random, and if it picks the event, the
   interrupt's exception replaces the call's return value in Ruby, so that
   event is lost. global-hotkey keeps its sender private, so the gem cannot
   put it back; the RDoc says "usually". `recv_timeout` takes seconds, Ruby's measure of time, as an
   Integer or Float, converted with `Duration::try_from_secs_f64`; a
   negative or NaN value raises `ArgumentError` with Rust's text, where
   `Duration::from_secs_f64` would panic. A timeout too long for an
   `Instant` waits forever, as crossbeam's does (`channel.rs:884-889`).
   `recv_deadline` is not bound: Ruby has no `Instant`, and `recv_timeout`
   covers it. Every other call keeps the GVL, as plan 001, decision 14
   found faster for short calls: registering talks to Carbon or Win32
   directly, and on Linux it waits for the X11 thread, which looks at its
   queue every 50 ms (`x11/mod.rs:42-53`, `:326`), so a Linux `register`
   holds the GVL for up to about 50 ms plus a round trip to the X server.
   It cannot be interrupted, and if the X connection hangs it blocks with
   no limit, as global-hotkey's does; the RDoc and README say so. A Linux
   `unregister` returns before the X server releases the keys:
   global-hotkey sends its ungrabs with `ignore_error`, waiting for no
   answer (`x11/mod.rs:210-214`), and x11rb keeps requests in its write
   buffer until a request that waits for a reply flushes it, which its
   event poll never does (x11rb 0.13.2 `src/rust_connection/mod.rs`,
   `poll_for_raw_event_with_sequence`, `flush_impl`). The keys stay
   grabbed until that manager's next `register`, which waits for the
   keyboard mapping, or until the manager is freed and its connection
   closes; meanwhile another client's grab of them is `AlreadyRegistered`.
   That is global-hotkey's behavior, so the gem keeps it, and a test pins
   it and the RDoc and README say it.
7. **Errors.** `Error < StandardError` is global-hotkey's `Error`, with a
   subclass per variant: `OsError`, `HotKeyParseError`,
   `UnrecognizedHotKeyCode`, `EmptyHotKeyToken`, `UnexpectedHotKeyFormat`,
   `FailedToRegister`, `FailedToUnRegister`, `AlreadyRegistered`, and
   `FailedToWatchMediaKeyEvent`. The message is global-hotkey's `Display`
   text, built by global-hotkey itself, so the Ruby side copies only
   `FailedToWatchMediaKeyEvent`'s fixed text, which a Rust test pins. The
   two variants that carry a `HotKey` expose it as `hotkey`. `OsError`
   carries `std::io::Error`'s text and nothing more. Four variants
   (`HotKeyParseError`, `UnrecognizedHotKeyCode`, `EmptyHotKeyToken`,
   `UnexpectedHotKeyFormat`) are never built by 0.9.0, whose parser returns
   `hotkey::HotKeyParseError` instead; they exist because the enum has
   them. A variant ferro does not know raises the base class (the enum is
   `#[non_exhaustive]`), and a panic inside global-hotkey raises the base
   class with `global-hotkey panicked: <message>`. `hotkey::HotKeyParseError`
   is a separate exception class, as it is a separate type, with
   `UnsupportedKey`, `EmptyToken`, and `InvalidFormat`. keyboard-types'
   `UnrecognizedCodeError` sits beside `Code` in `Hotkey`. crossbeam's
   receive errors sit under `GlobalHotKeyEventReceiver`, the type whose
   methods return them; the `Disconnected` errors exist but cannot happen,
   since the static sender never drops.
8. **Enums.** As plans 002 and 003: unit variants are frozen instances
   (`HotKeyState::Pressed`, `Code::KeyA`), whose `inspect` is the constant.
   `Ord` is `<=>` with `Comparable`, in declaration order, as Rust derives
   it; `Code`'s order is its discriminant, which a test checks against
   keyboard-types for every variant. keyboard-types' 216 `Code` variants
   are generated into `code.rb` from its `src/code.rs`, each with its
   rustdoc as RDoc, by `tasks/keyboard_types_codes.rb`
   (`rake codes:global-hotkey`), which reads the keyboard-types that the
   gem's `Cargo.lock` pins; a tooling test fails when the committed file is
   not what the generator writes. Only the constants and their docs sit in
   the keyboard-types snippet; the class's prose and methods are Ferro's.
   A test checks that the Ruby constants are exactly
   keyboard-types' variants in order, through keyboard-types' `FromStr`
   and the last variant's discriminant. `Code::Hyper`, `Super`, and
   `Turbo` are deprecated constants, as keyboard-types deprecates them, so
   naming one warns when `Warning[:deprecated]` is on; the gem itself
   never names them, so parsing `"Super"` does not warn. A `Code` and a
   `HotKeyState` dump to Marshal as their names and load as the same
   constants, so a copy from a child process keeps its identity, order, and
   hash.
9. **HotKey is `Data`.** Its three fields are public in Rust, so a struct
   literal can set any `id` (`src/hotkey.rs:52-59`); Ruby's counterpart is
   `HotKey.new` with an `id`, positional or keyword, as Data's own
   constructor takes it. Rust's `HotKey::new(mods, key)` is
   `HotKey.new(mods, key)` without one, which runs global-hotkey's `new`:
   it turns the deprecated `SUPER` into `META` and computes the id
   (`:87-101`). The override is `HotKey.new` itself, not `initialize`,
   since Steep mis-checks `initialize` on a Data class (AGENTS.md); it
   builds the value through Data's `initialize`. `mods` is a
   `Modifiers` (or `nil` without an `id`), `key` a `Code`, and `id` a
   `u32`; anything else raises `TypeError` or `RangeError`, on both paths,
   as a Rust literal of the wrong types would not compile. Fields given
   both positionally and by keyword raise `ArgumentError`. Every method that reaches global-hotkey rebuilds the Rust
   value from the three fields, so a hand-built `HotKey` behaves as the
   same Rust literal would. `with` is Rust's struct update syntax. `Debug`
   is not ported to `inspect`, which stays Data's; global-hotkey's `Debug`
   text appears verbatim in the messages of `FailedToUnRegister` and
   `AlreadyRegistered`.
10. **Conversions.** `FromStr` is `HotKey.from_str`; both `TryFrom` impls
    are `HotKey.try_from`, taking a String; each raises
    `Hotkey::HotKeyParseError`'s subclass. `Display` and `into_string` are
    `to_s` and `into_string`. Code's `FromStr` is `Code.from_str`, raising
    `UnrecognizedCodeError`.
11. **Modifiers.** keyboard-types' `Modifiers` is a bitflags type over a
    `u32`. Ruby's is a frozen value holding `bits`, with a constant per
    flag; a test checks the constants against bitflags' own flag table.
    bitflags' methods keep their names and meanings
    (`src/public.rs`): `from_bits` returns `nil` when a bit is unknown,
    `from_bits_truncate` drops unknown bits, `from_bits_retain` keeps them,
    `complement` truncates, `difference` is `self & !other`. Rust's
    operators are Ruby's: `|`, `&`, `^`, `-`, and `~` for `Not`, Ruby's
    bitwise complement, since Ruby's `!` is boolean. `iter` and
    `iter_names` return Arrays, since a set of flags is finite. `inspect`
    is bitflags' `Debug` text with Ruby's class path,
    `Ferro::GlobalHotkey::Hotkey::Modifiers(SHIFT | CONTROL)`, made by
    bitflags. The mutating methods (`insert`, `remove`, `toggle`, `set`,
    `|=` and the other `*Assign` operators) are not bound: a Ruby value is
    frozen and shareable, and `|`, `-`, and `^` give the same result as a
    new value. `Extend` and `FromIterator` are `flags.inject(:|)`, and the
    hex and binary formatters are `bits.to_s(16)`. `HYPER` and `SUPER` are
    deprecated constants (keyboard-types `src/modifiers.rs:28-31`).
12. **What a host runs.** global-hotkey's own note is a contract: "On
    Windows a win32 event loop must be running on the thread. It doesn't
    need to be the main thread but you have to create the global hotkey
    manager on the same thread as the event loop. On macOS, an event loop
    must be running on the main thread so you also need to create the
    global hotkey manager on the main thread." (`src/lib.rs:15-18`). On
    macOS the Carbon handler runs only when the main thread dispatches
    events, as an `NSApplication` loop (Tokra's tao loop) or Carbon's
    `RunCurrentEventLoop` does; on Windows `WM_HOTKEY` reaches the hidden
    window only when its thread runs `GetMessage` and `DispatchMessage`, as
    tao's loop does. Without that loop, registering works and no event
    ever arrives: the receiver stays empty and the handler is never called.
    On Linux global-hotkey runs its own thread, so events arrive with no
    loop at all, but only from an X server: under Wayland without
    XWayland the thread cannot connect, stops, and every later call
    returns as if it had worked (decision 2). The gem does not refuse a
    manager made off the main thread, since global-hotkey does not; the
    README and RDoc say what happens.
13. **Ractors (ADR 001, section 7).** Every global-hotkey value the gem
    keeps is `Send` and `Sync` except the Windows manager (decision 3),
    and every call builds its own Rust values or reads the static channels,
    so the extension is marked Ractor-safe. `HotKey`, `Modifiers`, `Code`,
    `HotKeyState`, `GlobalHotKeyEvent`, and the receiver are shareable; a
    manager stays with its Ractor. `set_event_handler` keeps its state on
    the module, so it works from the main Ractor only, and Ruby raises
    `Ractor::IsolationError` elsewhere. Windows runs the Ractor tests in a
    child process, for the Ruby 4.0.9 barrier bug plan 001 found.
14. **No panic reaches Ruby.** Every global-hotkey call runs under
    `catch_unwind`. Nothing reachable from Ruby is known to panic: the
    `Mutex` unwraps in the macOS backend panic only on a lock poisoned by
    an earlier panic; `HotKey::new` shifts a `u32` left by 16, which drops
    high bits rather than panicking; integers convert through magnus, which
    raises `RangeError` outside a `u32`.
15. **Dependencies.** global-hotkey `=0.9.0` with `serde` and `tracing`;
    crossbeam-channel `0.5`, global-hotkey's own, for the cancelable wait

    installs.

## Tests

Registering a hotkey takes it from every other program while it is
registered, so the tests that register one use combinations nobody uses:
Control, Alt (Option), Shift, and Meta (Command, Windows) with F19 or F24,
and they always unregister. On Linux every test that talks to X runs
against a private Xvfb server the suite starts (`-displayfd`), never the
desktop's display, so synthesized keys and keymap changes reach nothing of
the user's; the suite maps F17 to F19 and F24 to spare keycodes there,
since Xvfb's default keymap stops at F12, and starts it with `-noreset`,
since an X server that resets when its last client leaves forgets the
mapping. Tests that need it skip, saying so, where Xvfb, xdotool, or
xmodmap is missing.

- Values (`test_hotkey.rb`, `test_modifiers.rb`, `test_code.rb`,
  `test_event.rb`): global-hotkey's own tests (`src/hotkey.rs:460-577`)
  ported; the module doc's ordering example (`:18-27`); ids; `matches`;
  `to_s`/`into_string` and parsing round trips; every parse error; every
  `Code` against keyboard-types; every flag against bitflags; bitflags'
  operations; `HotKeyState` and `GlobalHotKeyEvent` order; the literal's
  type checks and mixed positional and keyword fields; Marshal round
  trips.
- Errors (`test_errors.rb`): each class and its message from the native
  layer's classification of every variant.
- Manager (`test_manager.rb`): `new`, `register` and `unregister` of a real
  hotkey, `register_all`/`unregister_all`, an unsupported key's
  `FailedToRegister` (F24 on macOS, which has no scancode for it,
  `macos/mod.rs:412-528`; `Fn` on Windows and Linux), a second
  registration's error, unregistering an unknown hotkey, macOS's one
  manager at a time, another X client's grab, and Linux with no X server.
  A child checks that a manager the collector frees makes room for a new
  one on macOS, freed on the main thread and on another, and on Linux
  that it releases its grab.
- Receiver (`test_receiver.rb`): `try_recv` raising `Empty`; `recv_timeout`
  timing out while another thread runs; an interrupt ending `recv`, in a
  child, since a wait nothing can end would also keep Ruby from exiting;
  a timeout too long for the clock still waiting until interrupted, also
  in a child; a bad timeout; Enumerators; shareability.
- Linux delivery (`test_linux_events.rb`): a child process on the private
  Xvfb registers Ctrl+Alt+Shift+F24, presses it with xdotool, and reads
  `Pressed` then `Released` from the receiver; in other children the
  handler, a block or a callable, receives them instead and the receiver

  raises ends its thread and later events are dropped; an unregistered

- Windows delivery (`test_windows_events.rb`): a child process registers

- Platform, gem, Ractors (`test_platform.rb`, `test_gem.rb`,

- Rust (`cargo test`): panic capture, the error classification and every

- Tooling (`test/tasks/test_keyboard_types_codes.rb`): the generator's

The first runs found what the first design missed: Carbon refuses a
second manager while one lives (decision 3), so the macOS tests share one
manager; an X server resets its keymap when its last client leaves, so the
private Xvfb runs with `-noreset`; an interrupt test whose wait cannot end
also keeps Ruby from exiting, so it runs in a child; `HotKey.new` cannot
be an `initialize` override, which Steep mis-checks on Data; and Clippy
for Windows names the manager's `HWND` field (decision 3).

An independent review then found, and this session fixed: the first
SAFETY comment called a Windows drop off the window's thread an error
"rather than misbehaving", when `DestroyWindow` failing there leaves the
window and its hotkeys registered, so `Owned` now defers that drop, and
the macOS one, to the owner (decision 3); a timeout too long for the
clock had no test, and `+` in place of `checked_add` would have reached
Ruby as `fatal`; neither the drop nor its absence had a test; the literal
skipped the constructor's type checks, and fields given both ways dropped
one silently (decision 9); Marshal copies of a `Code` or `HotKeyState`
were new objects with their own hashes (decision 8); the claim that an
event arriving with an interrupt always survives (decision 6); the Code
generator lived only in a scratch directory, and Ferro's prose sat inside
the keyboard-types snippet (decision 8); the Linux `register`'s
uninterruptible, unbounded wait was undocumented (decision 6); and a
Windows runner that injects input but delivers no `WM_HOTKEY` would have
failed the delivery test rather than skipped it with that reason.

CI on Linux then failed `test_linux_a_freed_managers_grab_is_released` in
0.06 s, before its retry ran: the child's first grab of
Ctrl+Alt+Shift+Super+F19 met `AlreadyRegistered`. The suite's shared
in-process manager had just unregistered that combination, and the
ungrab was still in its unflushed write buffer (decision 6). A container
run with the committed test file and CI's seed, 35560, failed the same
way; it had passed before only by test order. The test now uses a
combination no test in the process grabs, and
`test_linux_an_unregister_reaches_the_x_server_with_the_next_register`
pins the behavior: a second manager's grab fails after `unregister` and a
half-second wait, and succeeds after the first manager's next `register`.
Six seeds, CI's among them, pass in the container.
