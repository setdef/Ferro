# Plan 008: Parent Windows on macOS, and Handles from Any Gem

ferro-rfd 0.1.0.pre.2 binds only the parent handles rfd never follows as
pointers: Win32, Xlib, and Xcb ([plan 002](002.md), decision 6). A macOS
app cannot give its dialog a parent at all, and Tokra, whose windows now
answer raw-window-handle's traits with values of its own
(`Tokra::RawWindowHandle`, Tokra's ADR 013), has to copy each one into
ferro-rfd's classes, because `set_parent` checks the class of each handle.
ADR 013 records three follow-ups for Ferro: a sound AppKit parent, a
sound Wayland parent, and a shared home for the handle values. This plan
settles all three for ferro-rfd 0.1.0.pre.3, still binding rfd 0.17.2.

## What rfd does with a parent

`set_parent` copies both raw handles out of the parent at once, keeping
each only if reading it succeeds (`src/file_dialog.rs:96-103`). On macOS
rfd reads only the window: `window_from_raw_window_handle` retains the
`ns_view` pointer as an `NSView` and asks it for its window, panicking if
it has none, and panics with "unsupported window handle, expected: MacOS"
for any other kind (`src/backend/macos/utils.rs:34-45`). It calls that
inside its main-thread hop for sync dialogs (`backend/macos/file_dialog.rs:18-31`,
`message_dialog.rs:155-167`, through `utils.rs:20-32`), and on the calling
thread for async ones, before `ModalFuture::new` (`file_dialog.rs:50-51`,
`message_dialog.rs:172-183`), which retains the window for the sheet
(`modal_future.rs:67-103`). An `ns_view` that is not a live `NSView` is
undefined behavior the moment rfd retains it.

## Design decisions

1. **`AppKitWindowHandle` names its window by number.** raw-window-handle's
   `AppKitWindowHandle` holds `ns_view: NonNull<c_void>`, a pointer whose
   validity a `WindowHandle<'a>` borrow promises for its lifetime
   (raw-window-handle `src/appkit.rs:46-110`, `src/borrowed.rs:200-257`).
   Ruby has no lifetime to hold an Integer to, and no way to check that
   an address is an `NSView` (ADR 001's table drops lifetimes, "documented
   where they change behavior"; here dropping it would make the handle
   unsound). So ferro-rfd's `AppKitWindowHandle` is `Data.define(:window_number)`:
   the window's `-[NSWindow windowNumber]`, an `NSInteger` that names a
   window without pointing at it. The class keeps raw-window-handle's name,
   since the kind is the variant rfd matches on (`RawWindowHandle::AppKit`),
   and translates the field, tier 1 of the precedence: what Ruby can
   express soundly. The gem builds raw-window-handle's handle itself, from
   the window it looks up (decision 3), so rfd still receives exactly the
   `AppKitWindowHandle { ns_view }` it would in Rust: the window's content
   view, which is what tao, winit, and Tokra answer
   (Tokra ADR 013's table). A Rust caller gets the same dialog.
2. **`AppKitDisplayHandle` is bound,** an empty `Data` like
   `WindowsDisplayHandle` (raw-window-handle `src/appkit.rs:6-24`). rfd's
   macOS backend reads no display, but a parent returns one, and rfd keeps
   it (`parent_display`, which `inspect` shows).
3. **The window is looked up when the dialog runs, on the main thread.**
   `-[NSApplication windowWithWindowNumber:]` answers `nil` for a number
   that names none of this app's windows, so a wrong or stale number
   cannot reach rfd as a pointer. `NSApplication` and `NSWindow` belong to
   the main thread (objc2-app-kit marks them `MainThreadOnly`), so the
   gem looks the window up there, takes its `contentView`, holds both
   retained while rfd runs, and releases them there. Each terminal call
   with an AppKit parent runs, together with rfd's call, in one closure:
   - on the main thread, directly;
   - on another thread, when an `NSApplication` runs, through
     `dispatch2::run_on_main`, the hop rfd itself makes for a sync dialog
     from another thread (`utils.rs:20-27`). rfd then finds itself on the
     main thread and runs as it would there. For an async dialog this
     moves rfd's own window lookup, which rfd does on the calling thread
     against its own `MainThreadMarker::new_unchecked` (`utils.rs:35-36`,
     "TODO: Move this requirement up"), onto the main thread, and
     `ModalFuture::new` there starts the sheet just as its own
     `run_on_main` would (`modal_future.rs:79-103`);
   - on another thread with no running app, never: rfd's existing
     refusals for that case fire first (plan 002, decision 5), with rfd's
     messages.
   The closure returns Rust values only, and the GVL is released for the
   whole of it (plan 002, decision 4; plan 005, decision 20: nothing of
   Ruby's while a native wait holds the thread). The window is read when
   the dialog runs rather than when `set_parent` is called, as rfd reads
   a handle; deviation, tier 1, since no Ruby value can keep an `NSView`
   alive, on the main thread, until the call. It is sounder than Rust's,
   where the pointer copied at `set_parent` can dangle by the call.
4. **Refusals raise `Ferro::Rfd::Error`.** A number that names no window
   of this app raises "no window of this app has window number 42"; a
   window without a content view raises "window number 42 has no content
   view", where rfd would panic ("NSView to be inside a NSWindow",
   `utils.rs:41`) or worse. With no `NSApplication` at all, the gem reads
   AppKit's `NSApp` global as plan 002, decision 5 does, and answers "no
   window" without creating one. These are the gem's own messages: rfd
   has none for a lookup it never makes.
5. **`inspect` looks the window up too,** as a terminal call would and
   with the same errors, so its text is rfd's `Debug` of the builder rfd
   would get (plan 002, decision 2), `ns_view` included. From another
   thread with no running app, it raises "an AppKitWindowHandle is looked
   up on the main thread, and no NSApplication runs to reach it from this
   one". Like a dialog from another thread, an `inspect` there waits for
   the main thread's run loop with the GVL released, and with no
   unblocking function (`gvl.rs`, `without_gvl`): if the main thread is
   blocked in Ruby, say joining this thread, the wait never ends and
   cannot be interrupted, as with rfd's own hop. The RDoc says so.
6. **Other platforms.** On Windows an AppKit handle is refused with rfd's
   "unsupported window handle, expected: Windows" (`dialog_ffi.rs:157`), as
   every non-Win32 kind is. On Linux the portal ignores a kind it cannot
   use (`window_identifier/mod.rs:41`), so an AppKit window becomes no
   parent, without a lookup. On macOS every kind but AppKit is still
   refused with rfd's "expected: MacOS".
7. **Wayland stays unbound: rfd 0.17.2 has no sound route.** The portal
   names a Wayland parent `wayland:<handle>`, an exported xdg-foreign
   handle (`window_identifier/mod.rs:70-83`), but rfd builds that handle
   itself: `from_raw_handle` takes only a `RawWindowHandle::Wayland`
   surface with a `RawDisplayHandle::Wayland` display
   (`window_identifier/mod.rs:24-43`), wraps the display pointer as a
   foreign `wl_display` (`wayland.rs:33-34`), reads the surface pointer
   as a proxy (`wayland.rs:35-41`), and exports it through
   `zxdg_exporter_v2` on its own queue (`wayland.rs:134-165`).
   `WindowIdentifierType::Wayland(String)` exists, but is constructed only
   there and lives in a private module (`src/lib.rs:131`, `mod backend`),
   so no public rfd API takes an exported handle string. A binding would
   have to hand rfd two raw pointers, and Wayland has no call that checks
   that an address is a live `wl_display` or `wl_surface`; a wrong one is
   undefined behavior inside libwayland-client. Taking an exported handle
   and passing it to the portal ourselves would bypass rfd, which a
   one-to-one binding does not do. Wayland handles keep raising
   `TypeError`; a later rfd that takes an exported handle reopens this.
8. **Handles are read by kind, from any gem (duck typing).** A handle
   value's kind is the name of the raw-window-handle struct it mirrors,
   which is also the variant rfd matches on (Tokra ADR 013: "in Ruby the
   struct is the variant"). `set_parent` finds the kind as the last
   segment of the name of the handle's class or nearest named ancestor,
   among `Win32WindowHandle`, `XlibWindowHandle`, `XcbWindowHandle`,
   `AppKitWindowHandle`, `WindowsDisplayHandle`, `XlibDisplayHandle`,
   `XcbDisplayHandle`, and `AppKitDisplayHandle`, and reads that struct's
   fields by raw-window-handle's names. So `Tokra::RawWindowHandle::Win32WindowHandle`
   works as is, as does a subclass of ferro-rfd's own value. A value of
   another kind still raises `TypeError`, and a value missing a field
   raises Ruby's own `NoMethodError` naming it (Tokra's AppKit value
   answers `ns_view` and would add `window_number`). The kind cannot come
   from the fields alone: Xlib and Xcb windows both have `window` and
   `visual_id`. Rejected alternatives: a `ferro-raw-window-handle` gem of
   plain `Data` classes would bind a crate with nothing Ruby lacks (ADR
   001, section 1) only to share a namespace, and every consumer would
   depend on it; checking classes, as pre.2 did, makes Tokra copy every
   handle. Soundness does not rest on the value's class: every bound kind
   is either validated by the platform or never followed (plan 002,
   decision 6, and decision 3 here).
9. **Dependencies.** `dispatch2` 0.3.1, already in the lock as rfd's
   macOS dependency, becomes a direct one for `run_on_main`. The lookup
   sends three messages through objc2's `msg_send!` with `AnyObject`
   rather than adding objc2-app-kit's typed classes, as plan 002's `NSApp`
   check does.
10. **Native shape.** Ruby still passes tagged Arrays, now with
    `[:AppKit, window_number]` and `[:AppKit]`. The native layer turns
    them into a `Send` description of the parent (numbers only) under the
    GVL, refusing zeroes and kinds the platform cannot take, and builds
    raw-window-handle's handles from it inside the closure that calls rfd.

## Tests

macOS tests that need AppKit run in a child Ruby (the suite's `in_child`)
that makes an `NSApplication` with the Prohibited activation policy and
an `NSWindow` it never orders front, through Fiddle, so no window, Dock
icon, or menu bar appears. Only the refusal tests run a terminal call,
and each refuses before rfd opens anything.

- `inspect` on the main thread shows `AppKit(AppKitWindowHandle { ns_view: ... })`
  with the window's content view address, and `parent_display:
  Some(AppKit(AppKitDisplayHandle))` (decisions 1-3, 5).
- From another thread while `-[NSApplication run]` runs on the main
  thread, `inspect` shows the same address (decision 3's hop).
- An unknown number raises the decision 4 error from `inspect`,
  `pick_file`, `MessageDialog#show`, and the async `pick_file` and `show`;
  a window whose content view was removed raises the content view error;
  with no `NSApplication`, the unknown-window error, and `NSApp` stays
  null afterward.
- From another thread with no running app, `inspect` raises decision 5's
  error and `pick_file` rfd's existing one.
- On Windows the AppKit handle is refused with rfd's message; on Linux it
  leaves `parent: None` (decision 6); off macOS no lookup runs.
- A handle of another class named for a bound kind, and a subclass,
  reach rfd; an unnamed class or another kind raises `TypeError`; a
  missing field raises `NoMethodError` (decision 8).

## Results

Every decision is done except Wayland, deferred under decision 7 because
rfd 0.17.2 takes no exported handle. The clean gate passes (ferro-rfd: 89
Ruby runs, 345 assertions, 12 skips for other platforms; 23 Rust tests),
and `package:install` builds the gem from its packaged sources.

Checked by hand: each mutation below made the named tests fail, and the
tests passed again once it was reverted.

- On macOS, `refused_handle` refuses `AppKit` too: every
  `TestAppkitParent` test that sets a parent fails with rfd's "expected:
  MacOS".
- `on_main` never hops through the running app:
  `test_another_thread_looks_the_window_up_through_the_running_app`
  fails.
- `handle_kind` accepts only `Ferro::Rfd::` classes:
  `test_handles_from_another_gem_are_read_by_kind` and
  `test_a_handle_missing_a_field_of_its_kind_raises_no_method_error`
  fail.
- `handle_kind` reads only the handle's own class, not its ancestors: the
  subclass case of `test_handles_from_another_gem_are_read_by_kind`
  fails.
- `describe` never releases the GVL (its condition `|_| false`), so
  `inspect` hops to the main thread holding it:
  `test_waiting_for_the_main_thread_releases_the_gvl` blocks the main
  queue on a mutex that only a second Ruby thread unlocks, after
  `inspect` starts, so with the GVL held the child hangs and is killed.
  The test proves the release by order, not by rate, so a loaded
  machine cannot fail it.

The non-macOS build was linted with Clippy on Linux in a container,
which caught (and now passes) the `unnecessary_wraps` that the
always-successful non-macOS `Parent::build` and `on_main` raised there;
both are now macOS-only. Not checked here: the Windows and Linux branches (the AppKit refusal on
Windows, and no parent on Linux). They run in CI on those platforms.
