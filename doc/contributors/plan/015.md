# Plan 015: Precompiled gems of ferro-url for Ruby 4.1

## Context

Installing ferro-url compiles its Rust extension, so the source gem needs
Rust and libclang wherever it installs. Tokra depends on
`ferro-url = 0.1.0`, released as the tag `ferro-url/v0.1.0`. Fledge
packages Ruby apps with a Ruby of their own, and keeps an example Rails
and Tokra app: it takes built gems from GitHub Releases, puts them in the
app's `vendor/cache`, and pins them by SHA-256. Tokra builds precompiled
gems of itself
([its plan 072](https://github.com/setdef/Tokra/blob/trunk/doc/contributors/plan/072.md)),
so while ferro-url is a source gem only, every Fledge build of that app
still needs Rust.

Fledge embeds Ruby 4.1.0-preview1 on macOS and Linux. Ferro's gate runs
on the Ruby `mise.toml` pins, 4.0.9.

## Problem

Ferro had no way to build a gem with its extension already compiled, and
nothing that showed such a gem installs without a compiler and loads.

## Decided

### Built from the source gem, natively on each platform

`rake package:native:<gem>` (`tasks/precompiled.rake`) builds
`pkg/<name>-VERSION-PLATFORM.gem` with `PlatformGem`
(`tasks/platform_gem.rb`), on the platform and Ruby it runs on. It builds
the source gem, unpacks it, runs its `extconf.rb` with no options and
then `make`, as RubyGems does when it installs the source gem, and packs
the same files with the extension added, with no extension to compile and
no `rb_sys` dependency, which only `extconf.rb` loads.

Two ways to compile were weighed:

- **The repository's compile**, as Tokra's `PlatformGem` takes it. Ferro's
  compile tasks pass `--enable-test-hooks` to every gem that has test
  hooks (`FerroGem#test_hooks`), ferro-url among them, so a gem built
  that way would carry hooks no installed gem may have, unless the tasks
  grew a second compile mode.
- **The source gem's own compile.** The hooks stay off because
  `extconf.rb` gets no options, the same way they stay off when an app
  installs the source gem, and the packaging check's fast mode already
  compiles a gem with hooks this way (`PackageCheck#build_extension`).
  The precompiled gem holds exactly the source gem's files plus one.

The second is taken. The compile runs with `RB_SYS_CARGO_TARGET_DIR`,
`CARGO_TARGET_DIR`, and `RB_SYS_CARGO_PROFILE` unset, so it builds in a
directory of its own, in rb-sys's default release profile, as an install
does, and not in the repository's shared target directory.

Cross-compiling (rb-sys-dock, oxidize-rb/actions' cross-gem) was not
taken. ferro-url links nothing of the system's, so it could, but a cross
build is a second way to build, in images of their own, beside the one
the gate already proves on each platform, and Tokra's precompiled gems,
which Fledge takes beside these, are built natively for the same reason
its plan gives.

### A released version's gems come from its tag

`rake "package:native:url[ferro-url/v0.1.0]"` builds the source gem from
a clean checkout of the tag under `tmp/native/`, as `release:<gem>:push`
builds from a checkout of its tag (the gemspec lists its files with git),
and compiles that. The tooling is the checkout's own; the sources are the
tag's. A precompiled gem must match a released version exactly, and its
files then are the release's files.

Between `ferro-url/v0.1.0` and this plan, `gems/url` changed only in
comments, the README, and tests (`git diff ferro-url/v0.1.0 --
gems/url`): references to ADR 001 and ADR 002 became references to the
design documents. The code, the crate, and `Cargo.lock` are the same, so
0.1.0's precompiled gems are built from the tag, and no patch release is
needed for them.

### Platform names and the Ruby requirement

As in Tokra's plan 072, and for its reasons:

- `arm64-darwin`, with no darwin version, which RubyGems would otherwise
  match only on the build machine's macOS.
- `x86_64-linux-gnu` and `aarch64-linux-gnu`: a plain `x86_64-linux`
  gem also matches on musl, where an extension built against glibc does
  not load.
- Windows keeps Ruby's own platform.
- A gem built on a Ruby release requires `>= X.Y, < X.(Y+1).dev`. A gem
  built on a preview or on master requires exactly that Ruby
  (`= 4.1.0.preview1`), because those define `RUBY_ABI_VERSION`
  (`include/ruby/internal/abi.h`) and Ruby off Windows refuses an
  extension built for another (`dln.c`, `dln_load_and_init`). The source
  gem's `>= 4.0` stays, so 0.1.0's gems for Fledge require
  `>= 4.0, = 4.1.0.preview1`; Bundler skips them on any other Ruby and
  compiles the source gem.

### Which Ruby builds them

The gems are built on Ruby 4.1.0-preview1 without moving Ferro's pin.
`mise.precompiled.toml` names that Ruby, and mise lays it over
`mise.toml` when `MISE_ENV=precompiled`, so

```sh
MISE_ENV=precompiled bin/setup --gate
MISE_ENV=precompiled mise x -- bundle exec rake "package:native:url[ferro-url/v0.1.0]"
MISE_ENV=precompiled mise x -- bundle exec rake package:deliver:url
```
<!-- SPDX-SnippetEnd -->

builds and checks them (on Linux, run the rake commands under
`bin/linux-env`, as `bin/setup` runs `bundle install`). The workflow
reads the same file for setup-ruby. The gate stays on 4.0.9.

mise finds no precompiled Ruby among jdx/ruby's prereleases, so it
compiled 4.1.0-preview1 with ruby-build, and on a Mac with no libyaml that
build failed at psych. The file takes Tokra's and Fledge's mise settings,
which point mise at jdx/ruby's own asset and forbid the compile, and only
under `MISE_ENV=precompiled`, so the gate's Ruby installs as before.
Passing `MISE_RUBY_VERSION` on each command line instead would have
named the Ruby in every command and in the workflow, and left the
compile to fail on such a Mac.

That needed one change to the bundle. Ruby runs the Bundler that
`Gemfile.lock` names under `BUNDLED WITH`, and it named 4.0.4. Bundler
4.0.11 and older read `Pathname::SEPARATOR_PAT` when they resolve a path
source (`bundler/source/path.rb`), Ruby 4.1 removed it, and every gem in
Ferro's Gemfile is a path source, so the first `bundle install` on Ruby
4.1 raised `NameError`. The lockfile now names Bundler 4.0.24, the newest
4.0 release, which reads `Pathname#absolute?` and runs on Ruby 4.0 too.
Setting Bundler's `version` to `system` for the build instead would have
built on Ruby 4.1's own beta Bundler and left the lockfile unusable on
Ruby 4.1.

rb-sys writes Ruby's inline C helpers in Rust only for the Rubies it
knows, up to 4.0 at 0.9.130; on 4.1 it compiles the C helpers instead,
through its `stable-api-compiled-fallback` feature, which is among the
defaults ferro-url's crate takes.

### The check

`rake package:deliver:<gem>[GEM,...]` (`PackageCheck#precompiled`)
refuses a gem that is for every platform, has an extension to compile, or
lacks its compiled extension; installs it into an empty `GEM_HOME` with
every directory that holds `cargo` or `rustc` taken off `PATH`, failing
if RubyGems built anything; and runs the packaging check's require-all
and smoke scripts against the installed gem. ferro-url's smoke script
parses, joins, raises url's error, refuses a backward slice, and fails if
the extension has test hooks. Neither task is in the gate.

### Where they are built

The Platform gems workflow (`.github/workflows/platform-gems.yml`) runs
on a manual dispatch, which may name a release tag whose sources to
build, and on each `ferro-url/v*` tag. It builds on `macos-15`,
`ubuntu-22.04`, and `ubuntu-22.04-arm`, with Ruby 4.1.0-preview1, runs
`package:deliver:url` on each, and keeps each gem and its SHA-256 as an
artifact. It creates no release, pushes no tag, and pushes nothing to
RubyGems.org. Ubuntu 22.04 is the oldest runner, and a Linux gem needs
at least the glibc of the system it was built on.

## Other gems

The tasks are defined for every gem in `FERRO_GEMS`, and nothing in them
is ferro-url's own, but only ferro-url's gems are built and proven, and
the workflow builds only ferro-url's. A gem that links system libraries
(ferro-rfd's libwayland, say) would need them named in the workflow, and
`PackageCheck#precompiled` installs no runtime dependencies, which no
Ferro gem has once `rb_sys` is dropped.

## Windows

Left out: Ferro has no Windows setup, and nothing here has run there.
On a Windows Ruby 4.1 that builds the extension, `package:native:url`
names the gem `x64-mingw-ucrt`; the workflow would need a Windows entry
with what ci.yml's Windows job sets for Rust and bindgen (the GNU host
toolchain, `BINDGEN_EXTRA_CLANG_ARGS`, `LIBCLANG_PATH`), and the Ruby
must be the RubyInstaller build Fledge embeds. Windows has no ABI check,
so a gem for `4.1.0.dev` there would load on any master build.

## Proof

On 2026-11-22, each from an empty workspace, `MISE_ENV=precompiled
bin/setup --gate`, then RuboCop on the changed tasks and
`rake test:tooling` for `TestPlatformGem` and `TestPackageCheck` (41
runs, no failures, on Ruby 4.1.0-preview1), then
`package:native:url` given the commit `ferro-url/v0.1.0` tags, and
`package:deliver:url`:

- **arm64-darwin**, macOS on Apple silicon, jdx/ruby's Ruby
  4.1.0-preview1 (`arm64-darwin25`): `ferro-url-0.1.0-arm64-darwin.gem`,
  for `>= 4.0, = 4.1.0.preview1`, 55 files, the 54 of the tag's source
  gem and `lib/ferro/url/ferro_url.bundle`. The extension links only
  libSystem, not libruby, with a minimum macOS of 11.0. It installed with
  no Rust on `PATH`, nothing compiled, and the smoke script passed,
  without test hooks.
- **x86_64-linux-gnu**, x86_64 Linux, jdx/ruby's Ruby 4.1.0-preview1:
  `ferro-url-0.1.0-x86_64-linux-gnu.gem`, the same requirement and files
  with `ferro_url.so`. `DT_NEEDED` is libgcc_s, libc, and ld-linux, no
  libruby, and the newest glibc symbol it needs is `GLIBC_2.34`. It
  installed with no Rust on `PATH` and loaded.

aarch64-linux-gnu has no machine but GitHub's arm runner, so the
workflow's first dispatch is its proof.
