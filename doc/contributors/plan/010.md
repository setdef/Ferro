# Plan 010: time's last deferred groups

[Plan 009](009.md) bound the format-item tree, `Parsed`, and `Timestamp`,
and deferred four groups whole (its rows 31 to 34, decision 18): std's
unsigned `Duration` and every operation that takes it; the `unit` module
and the deprecated `convert`; the `iter` module with `Date::iter_to`,
`Month::iter_from`, and `Weekday::iter_from`; and `SignedDuration`'s
`Display` with a precision. This plan takes decision 18's objections as
the starting point, settles a Ruby design for each group, and binds the
groups that have one, in the order users meet them. It binds two: `iter`
and `unit`. It defers two, each whole, for a reason of design rather than
size: std's `Duration`, whose Ruby value is a decision for the whole
repository, and the precision `Display`, which needs a translation of
Rust's formatter that Ruby has no protocol for.

The order follows use. A Rubyist who reads time's book walks a month of
dates with `date.iter_to(end)` before anything else here, and a port of a
Rust program that cycles through `Month::iter_from` or `Weekday::iter_from`
meets the other two iterators next. std's `Duration` comes up when Rust
code adds `Duration::from_secs` to a date. `unit` answers "how many
nanoseconds in a second", which `SignedDuration`'s constants already
answer. The precision `Display` is a formatting nicety.

A note from plan 011: its fixes bound the precision `Display` after all, as
`SignedDuration#to_s(precision)`, so only std's `Duration` stays deferred
of the two this plan left whole.

The crate, its version, its license, and the Rust-to-Ruby rules are plan
007's. Citations are `file:line` in time 0.3.55's `src/` unless they name
another crate; `unit` lives in time-core 0.1.9, which time re-exports
(`lib.rs:139`), and its citations are `time-core-0.1.9/src/unit.rs:line`.

## Design decisions

1. **Iterators are mutable classes.** time's iterators advance through
   `&mut self`, so a Ruby iterator changes in place, as a Rust `let mut
   iter` does. Each is a wrapped native value behind a `Mutex`, as
   `Parsed` is (plan 009, decision 12): the lock is held only to copy the
   iterator out or back, so no Ruby code and no crate code runs under it.
   Every iterator is `Clone`, so `dup` and `clone` copy it through
   `initialize_copy`, which refuses to overwrite a frozen one. A frozen
   iterator raises Ruby's `FrozenError` from every method that would
   advance it, worded as Ruby words it ("can't modify frozen
   Ferro::Time::Iter::DateIter: DateIter { ... }", with the receiver),
   which the Ruby side checks first, as `Parsed` does, since magnus's own
   check leaves the `inspect` out; the native check stays as a net. No
   iterator is Ractor-shareable. Each class has an allocator, which Ruby's
   `dup` needs; what it allocates is a value the public API also builds
   (an empty `DateIter` from `Date::MAX` to `Date::MIN`, a `MonthIter`
   from January, a `WeekdayIter` from Monday), and `initialize` or
   `initialize_copy` replaces it at once; a test compares each `allocate`
   with the public value. `Rev` and its two subclasses (decision 10) keep
   the inherited allocator for `dup` but undefine `allocate`, since a
   placeholder there would be a `Rev` of one kind in the other's class,
   and `Rev`'s `initialize_copy` refuses an original of the other kind
   with Ruby's own "initialize_copy should take same class object". time's
   derived `PartialEq` is `==`, comparing state as Rust's derive does, so
   two `DateIter`s from the same dates are `==` until one advances. time
   derives no `Hash`, so `eql?` and `hash` stay Ruby's identity.
   `inspect` is time's derived `Debug`:
   `DateIter { front: 2019-01-01, back: Some(2019-01-03) }`,
   `Rev { iter: MonthIter { current: January } }`.
2. **Constructors.** `DateIter::new(start, end)` is `DateIter.new(start,
   end_date)`, since `end` is a Ruby keyword; `Date#iter_to(end_date)`
   calls the same, as Rust's does. `MonthIter.new(start)` and
   `WeekdayIter.new(start)` are public, as Rust's `new` is;
   `Month.iter_from(start)` and `Weekday.iter_from(start)` are class
   methods, as Rust's are associated functions that take the start.
   Arguments are checked as Rust's type checker would: a `Date`, a
   `Month`, a `Weekday`, or `TypeError`.
3. **`next` is Rust's `next`.** `next`, `next_back`, `nth(n)`, and
   `nth_back(n)` return the item or `nil` (Rust's `Option`), never Ruby's
   `StopIteration`: these are time's iterators, not Ruby's Enumerator,
   and the table maps `None` to `nil`. They are the only methods that
   advance the iterator, as they are the only time methods that take
   `&mut self` and change it. `n` is a `usize`, so magnus raises
   `RangeError` for a negative or oversized Integer. Once a `DateIter`
   answers `nil` it answers `nil` from both ends forever, which is what
   `FusedIterator` promises; the ported `fused` test pins it.
4. **Enumerable, over a copy.** Every iterator includes Enumerable.
   Rust's `for` loop and every adapter take an iterator by value (`self`),
   which Ruby cannot move, so `each` walks a copy of the iterator from its
   current place and leaves the receiver where it was, as a Rust caller
   who writes `iter.clone()` first. That gives every Rust program the same
   items, and lets Ruby code call `first(3)` twice and get the same three
   dates. Enumerable's methods stand for Rust's provided methods (`map`,
   `filter`, `take`, `find`, `fold`). `DateIter`'s `rev`, core's adapter
   over time's `DoubleEndedIterator`, is `DateIter#reverse_each`, which
   walks a copy through `next_back` one date at a time, as core's `Rev`
   does, rather than gathering every date first as Enumerable's would;
   without a block it returns an Enumerator sized by `len`. The one difference is that Rust's provided `&mut self`
   methods (`find`, `position`, `by_ref`) advance a Rust iterator and
   Enumerable's never do; to advance, call `next` or `nth`. An infinite
   iterator's `each` runs until the block breaks, as Rust's `for` loop
   does; `first(n)`, `take(n)`, `lazy`, and `each_slice(n).first` stop.
   It loops with `while true`, not `Kernel#loop`, which would swallow a
   `StopIteration` the block raises and return as if the cycle ended.
5. **time's overrides keep Rust's names.** time overrides `size_hint`,
   `count`, `last`, `nth`, `max`, `min`, `is_sorted`, `all`, and `any`,
   and each is bound under its own name, calling time's implementation.
   `count`, `max`, and `min` share their names with Enumerable's, which
   take an argument or a block Rust's do not: called with neither, each is
   time's (and `max(nil)` and `min(nil)` count as neither, as Enumerable
   treats a `nil` count as none) (so `MonthIter#max` answers December at once, where Enumerable's
   would run forever); called with either, it is Enumerable's, over a
   copy, so Ruby code keeps the methods it knows. `last`, `is_sorted`,
   `all`, `any`, `size_hint`, `nth`, `nth_back`, `next_back`, and `len`
   have no Enumerable namesake. `count`, `last`, `max`, `min`, and
   `is_sorted` take `self` by value in Rust, so in Ruby they leave the
   receiver unchanged. `size_hint` returns `[lower, upper]`, with `nil` for
   an unknown upper bound: `[usize::MAX, nil]` for the infinite iterators,
   as Rust's `(usize::MAX, None)`.
6. **Exact size.** `ExactSizeIterator::len` is `len`. Ruby has its own
   way to carry an iterator's size: the block of `enum_for`, which
   `Enumerator#size` answers. So `each` without a block returns
   `enum_for(:each) { len }` for a `DateIter`, and Ruby's
   `Float::INFINITY` for the infinite iterators, the size Ruby gives its
   own infinite enumerators (`loop.size`, `(1..).each.size`). The gem
   defines no `size` of its own: time has none, and `len` is its name.
7. **`Rev`.** time's `Rev<I>` is a struct with a private field and no
   constructor; `MonthIter::rev` and `WeekdayIter::rev` make one, taking
   the iterator by value. In Ruby, `rev` returns a new `Iter::Rev` holding
   a copy and leaves the receiver unchanged, and `Rev.new` is private.
   Rust has two types, `Rev<MonthIter>` and `Rev<WeekdayIter>`; in Ruby
   both are `Rev`, the public class, each of a private subclass,
   `Rev::Months` or `Rev::Weekdays`, which the native layer wraps with
   magnus's safe `obj_wrap_as`. They differ where Rust's do (decision 10).
   `DateIter`'s `rev` is core's provided method, returning core's `Rev`,
   not time's; `DateIter#reverse_each` stands for it (decision 4).
8. **The two panics are refused.** `count` and `last` on `MonthIter`,
   `WeekdayIter`, and both `Rev`s panic: "`MonthIter` is infinite and
   cannot be counted", "`Rev<WeekdayIter>` is infinite and has no last
   element" (`iter/month_iter.rs:73-79`, `:136-142`;
   `iter/weekday_iter.rs:72-78`, `:119-125`). The native layer refuses
   them before calling time, with `RangeError` and time's message, as
   plan 007's decision 7 refuses every panic, and as Ruby's own
   `(1..).last` raises `RangeError`. A Rust test drives each of the eight
   real panics and asserts that the message the gem builds, from the
   name each iterator gives the refusal, is the panic's. No other input
   reaches a panic: `DateIter`'s `unsafe` steps rest on its own
   invariants (`iter/date_iter.rs:74-77`, `:112-137`), which every pair of
   valid dates keeps, and the ports cover both ends of the range.
9. **`all` and `any` call time's.** For `MonthIter`, `WeekdayIter`, and
   both `Rev`s, time's `all` and `any` test every month or weekday once,
   in calendar order from January or Monday, whatever the iterator's
   place, and stop (`iter/month_iter.rs:81-95`). In Ruby they take a
   block and run time's own methods: the native closure yields each item
   to the block through magnus's `yield_value`, which runs the block under
   `rb_protect`, so a block that raises or breaks stops time's loop and
   the exception or `break` resumes in Ruby once the native call has
   returned. Nothing of Ruby's is held in Rust between yields: the closure
   yields a month's number and the Ruby side turns it into the `Month`.
   time's `all` and `any` leave these iterators unchanged, so the gem
   runs them on a copy and writes nothing back. Enumerable's `all?` and
   `any?` remain Ruby's and walk the infinite sequence, stopping only at
   their answer; the RDoc says to use `all` and `any` for time's.
   `DateIter` overrides neither, so it has Enumerable's only.
10. **What `Weekday` cannot do.** `Weekday` has no order ("order is
    dependent on context", `weekday.rs:14-15`), so Rust's `max`, `min`,
    and `is_sorted` do not compile on a weekday iterator, and time defines
    none. `WeekdayIter` has no `max`, `min`, or `is_sorted` of its own:
    Enumerable's `max` and `min` raise Ruby's `ArgumentError`,
    "comparison of Ferro::Time::Weekday with Ferro::Time::Weekday failed",
    at the first comparison, and `is_sorted` is undefined. `Rev::Months`
    defines time's `max`, `min`, and `is_sorted`; `Rev::Weekdays` defines
    none, so on a reversed `WeekdayIter` `max` and `min` are Enumerable's,
    as on `WeekdayIter`, `is_sorted` is undefined, and `respond_to?`
    answers as Rust's types do.
11. **Unit structs are frozen values, not classes.** A Rust unit struct
    is a type with one value, named alike. `WellKnown::Rfc2822` passes the
    class itself for one (plan 007, decision 11), but time-core orders its
    units (`Nanosecond < Second`), and a Ruby class's `<` and `<=>` already
    mean "is a subclass of", which Ruby the language gives every class.
    So each unit is a frozen, shareable instance, like `Month::January`:
    `Unit::Second` is the value, `Unit::Second.per(Unit::Minute)` calls
    Rust's `Second::per(Minute)`, and `inspect` is the constant. The eight
    share one private class (`Unit::Value`, `:nodoc:`, as `Modifier::Enum`
    is private), since Ruby cannot name eight classes and eight values the
    same. `Unit::Unit` is the enum, with eight frozen variants of its own;
    Rust keeps the struct `Second` and the variant `Unit::Second` apart,
    and so does the gem: different objects, `==` to each other as Rust's
    `PartialEq` says, but not `eql?`, as Rust's `Eq` and `Hash` are per
    type. Neither derives anything Ruby lacks: no `Display`, so `to_s` is
    Ruby's.
12. **The `N` parameter is dropped.** Every unit and `Unit` take a const
    `N: u128` that defaults to 1. `per` and `per_t` exist only for `N =
    1` (`impl $t<1>`, `unit.rs:38`), and every `MultipleOf` is implemented
    for the `<1>` types only (`:75-85`), so a `Second::<60>` has no
    conversion at all. What `N` changes is which comparisons compile: a
    `Second::<60>` compares with a `Minute::<60>` and a `Unit::<60>`, never
    with a `Second`, and its `Debug` is "Second", the same as `Second`'s.
    A Ruby `N` would be a value that prints, compares, and hashes like the
    `N = 1` unit while refusing to compare with it, a distinction no
    method acts on. The gem binds `N = 1`, the default, which every Rust
    caller of `per` writes. Decision 18 of plan 009 counted the
    const-generic parameter as a reason to defer; it is the part of `unit`
    that has no behavior to bind.
13. **`per` and `per_t`.** `per` returns the number of the receiver in
    `larger` as an Integer: Rust's return type is "the smallest unsigned
    integer type that can represent the value" (`unit.rs:42-43`), and Ruby
    has one Integer. `per_t::<Output>` lets the caller choose the type;
    its Ruby form takes the type first, as plan 007 took a const parameter
    as `parse_borrowed`'s first argument: `per_t(Integer, larger)` is the
    same Integer through time-core's `u128` impl, and `per_t(Float,
    larger)` is the `f64` impl's Float. Ruby has one Integer, so time's
    twelve integer impls are one (each holds the same number), and one
    Float, so the `f32` impls have no counterpart, as plan 007's decision
    8 left `Mul<f32>`. Any other first argument raises `TypeError`. A
    `larger` that is smaller than the receiver does not compile in Rust:
    time-core's `#[diagnostic::on_unimplemented]` says "`{Self}` is not
    an integer multiple of `{T}`" (`unit.rs:167`), so `Unit::Second.per(Unit::Nanosecond)`
    raises `TypeError` with "`Nanosecond` is not an integer multiple of
    `Second`", the template filled with the type names. rustc prints the
    types with paths that depend on how they were imported
    (`time::convert::Nanosecond<_>` in a scratch build that imported
    `time::unit::*`), so the gem uses the bare names. The same build gives
    "`time::convert::Unit<_>` is not an integer multiple of
    `time::convert::Second`" for `Second::per(Unit::Minute)`, and
    "`time::convert::Minute<_>` is not an integer multiple of
    `time::convert::Second`" for `Second::per_t::<String>(Minute)`: a
    wrong output type names the larger unit, not the output, so the gem's
    `per_t(String, Unit::Minute)` says "`Minute` is not an integer
    multiple of `Second`" as well. The units and `Unit::Unit` undefine
    `allocate`, so the constants stay the only instances. A `Unit::Unit` variant
    or anything else as `larger` raises `TypeError`, as a type without
    `MultipleOf` would. The native layer calls time-core's `per` and
    `per_t` for each of the 36 pairs; a Rust test asserts every pair
    against time-core's own constants.
14. **Comparisons.** time-core orders every unit struct after the smaller
    ones (`impl_partial_eq_ord`, `unit.rs:256-287`), derives `Ord` on each
    (one value, always `Equal`), derives `Ord` on `Unit` in declaration
    order, and compares a `Unit` with a struct as `Unit` compares with the
    matching variant (`:130-161`). In Ruby each unit and each variant is
    Comparable, and `<=>` calls the native layer, which calls the real
    impls for every pair; `==` is Comparable's, which agrees with Rust's
    `PartialEq` because time-core's `eq` and `partial_cmp` agree, as a
    Rust test checks for all 256 pairs. Anything else compares as `nil`.
15. **`convert`.** time deprecates `convert` ("import from `time::unit`
    instead", `lib.rs:93-97`), so `Ferro::Time::Convert` is the same module
    as `Unit` and `deprecate_constant` makes naming it warn, in the
    `:deprecated` category, as plan 009's decision 6 treats `FormatItem`.
16. **std's `Duration` waits for an ADR.** The parity checklist maps a
    std type Ruby lacks "to the value Ruby code already uses for it", and
    Ferro has used Integer or Float seconds for std's `Duration` wherever
    one appears: ferro-arboard's `wait_until` and ferro-global-hotkey's
    `recv_timeout` take seconds through `Duration::try_from_secs_f64`
    (plans 001 and 004), and ferro-notify-rust deferred `From<Duration>
    for Timeout` for want of a value (plan 003, decision 9). That mapping
    does not survive time's operators. `Add<StdDuration> for Date` adds
    whole days of the span (`date.rs:1675-1687`), so `date + 86_400` would
    add one day and `date + 1` none, where Ruby's own `::Date + 1` adds a
    day. `SignedDuration` already takes an Integer as a count in `*` and
    `/` (plan 007, decision 8), so `duration + 1` would take the same
    Integer as seconds, and `2 + duration`, which `coerce` refuses today,
    would become std's `Add<SignedDuration> for StdDuration`, returning a
    std `Duration`. And a std `Duration` returned to Ruby (`unsigned_abs`,
    `TryFrom<SignedDuration>`, std's side of `Add` and `Sub`) must be some
    Ruby value: a Float loses nanoseconds past 2**53 of them (104 days),
    and a Rational is a type no Ruby API returns for a span. The other
    road, a frozen value class with seconds and nanoseconds, binds a type
    that is std's, not time's: `core::time::Duration`. Every Ferro gem that
    touches std's `Duration` would want the same class, and ADR 001's first
    limit keeps one gem's wrapped value out of another gem's Rust API, so
    the class would be plain Ruby, owned by one gem or by a shared one,
    and would change what arboard, global-hotkey, and notify-rust take.
    That is a decision for the repository, an ADR, not for one gem's
    plan; this group waits for it, whole. The follow-up is a Ferro ADR
    that settles one shared value for std's `Duration` across the gems,
    which awaits the maintainer; once it is accepted, a later plan binds
    this group against it. Most operations have a `SignedDuration` twin
    bound already; the conversions, the comparisons, and `unsigned_abs`
    do not (plan 007, decision 9).
17. **The precision `Display` waits with Rust's formatter.** `{:.3}` is not
    a parameter of `Display`; it is a field of `fmt::Formatter`, which
    also carries width, fill, alignment, and sign, and time hands the
    whole formatter to `f64`'s `Display` (`value.fmt(f)`,
    `signed_duration.rs:1364`), so `{:>8.1}` pads the number before
    the unit is written. Ruby has no protocol that reaches it: `format("%.3s",
    duration)` calls `to_s` and cuts the result to three characters.
    Binding the precision alone would take an argument time's `Display`
    does not have, `to_s(precision)`, and drop the rest of the
    formatter; binding all of it would take a format-spec String, an API
    neither time nor Ruby has. Plan 007 left the width and fill of every
    type's `Display` unbound for the same reason (its decision 12, and the
    unported `display_time_padding` and `display_offset_padding`), so the
    precision waits with them for one translation of Rust's formatter that
    serves every type at once.

    Corrected under plan 011: that framing was wrong. Every other type's
    `Display` ends in `f.pad` (`date.rs:1650`, `time.rs:1075`, and the
    rest), which applies width, fill, alignment, and precision to the
    whole string, so Ruby's own `ljust`, `rjust`, `center`, and
    `format("%-10.3s", x)` already reproduce Rust's output from `to_s`;
    no translation of the formatter is needed for them. Only
    `SignedDuration` differs, and only its precision changes what is
    written, so `to_s(precision)` binds it: `nil` is `{}`, and an Integer
    calls `format!("{:.*}", precision, value)`. Rust's formatter keeps a
    runtime precision in a `u16` and panics past it ("Formatting argument
    out of range", core's `fmt/rt.rs`), so the gem refuses a larger one
    with `RangeError` and that message, and magnus refuses a negative one.
    The width and fill of a `SignedDuration` stay unbound: time hands the
    formatter to each number it writes (`value.fmt(f)`, `:1365`, `:1392`),
    so `{:5}` pads every component, which no padding of the whole string
    reproduces, and binding them would take a format-spec argument
    neither time nor Ruby has.
18. **Concurrency.** Units and their variants are frozen Ruby data and
    shareable. Iterators are mutable and stay in their Ractor (decision 1):
    `Ractor.make_shareable` refuses one, frozen or not, moving one is
    refused ("can not move Ferro::Time::Iter::MonthIter object."), and
    passing one to `Ractor.new` gives the other Ractor its own copy,
    through `initialize_copy`, which advances apart from the original.
    So each object, and its `Mutex`, is reached from one Ractor only;
    `lib.rs`'s `SAFETY` comment says so too.
    The extension stays Ractor-safe: the iterators hold Rust values only,
    and no native function keeps a Ruby value past its call.

## Results

Batches 1 and 2 are bound: every row from 1 to 28 is bound or translated,
and row 29, the `N` parameter, is dropped (decision 12). Rows 30 and 31
are deferred, each whole, for the reasons of decisions 16 and 17.

What the session found:

- **`nth` that takes the last date leaves the front where it was.** time's
  `DateIter::nth` exhausts the iterator by clearing its back only
  (`iter/date_iter.rs:130-131`), so after `nth(4)` on five days its
  `Debug` is `DateIter { front: 2019-01-01, back: None }`, not the fifth
  date. `==` sees the difference, as Rust's derive does; `test_iter.rb`
  pins it.
- **The infinite iterators' `all` and `any` ignore their place.** They
  test January to December (or Monday to Sunday) whatever the iterator's
  current item, and never move it (`iter/month_iter.rs:81-95`), so the
  gem runs them on a copy and writes nothing back.
- **time's `Rev` is not core's.** `MonthIter::rev` and `WeekdayIter::rev`
  return time's own `Rev`, which implements `Iterator` but not
  `DoubleEndedIterator`; `DateIter` has no `rev` of its own, and core's
  `Iterator::rev` gives core's `Rev`, which Enumerable's `reverse_each`
  stands for.
- **rustc words the unit diagnostic with paths.** A scratch build with
  `use time::unit::*` printed "`time::convert::Nanosecond<_>` is not an
  integer multiple of `time::convert::Second`" for `Second::per(Nanosecond)`,
  and the same template for `Second::per_t::<String>(Minute)`; the gem
  fills the template with the bare names (decision 13).
- **magnus's `check_frozen` drops the `inspect`.** Its `FrozenError` reads
  "can't modify frozen Ferro::Time::Iter::DateIter" and has no receiver,
  where Ruby's own adds both, so the Ruby side checks first (decision 1).
- **No `unsafe` was added.** The block-yielding `all` and `any` use
  magnus's `yield_value`, which wraps `rb_yield` in `rb_protect` itself;
  the gem holds nothing of Ruby's in Rust across a yield but the
  `magnus::Error` a stopped block returns, on the stack.
