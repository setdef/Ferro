# Plan 016: ferro-url builds soundly on Windows' Ruby 4.1

## Context

Fledge, which packages Tokra apps with a Ruby of their own, embeds Ruby
4.1. On Windows that Ruby is RubyInstaller's build of Ruby's master of
2026-11-10 (`ruby 4.1.0dev (2026-11-10 master 0e25874222)
[x64-mingw-ucrt]`), which Fledge keeps as a release of its own because
RubyInstaller replaces its head build every day. Tokra reads its URLs
with ferro-url, so a Tokra app on Windows compiles ferro-url there, or
takes a precompiled gem of it. Plan 015 built ferro-url's precompiled
gems for macOS and Linux and left Windows out, since Ferro had no
Windows setup and nothing had run there.

Tokra met the fault this plan fixes in its own extension and traced it
([Tokra's plan 071](https://github.com/setdef/Tokra/blob/trunk/doc/contributors/plan/071.md),
and its `doc/contributors/upstream/`, which hold the changes Tokra would
send to magnus and rb-sys, unfiled). Every Ferro gem has it too. This
plan fixes ferro-url alone.

## The fault

Ruby 4.1 adds `rb_len_t`, the type of String's, Array's, and
MatchData's lengths and indices in the C API (ruby/ruby 03e3376643). It
is `int64_t` when `SIZEOF_RB_LEN_T` is defined wider than `long`, and
`long` otherwise (`include/ruby/internal/value.h`). RubyInstaller's head
build puts `-DSIZEOF_RB_LEN_T=8` in `RbConfig::CONFIG["CPPFLAGS"]`, not
in `config.h`, where `SIZEOF_LONG` is 4. There every length is 64 bits
and `long` is 32.

- **rb_sys's Makefile**, which `gem install` and `rake compile` run,
  hands rb-sys's build script each RbConfig entry as an `RBCONFIG_<key>`
  variable, which rb-sys reads before RbConfig itself. RbConfig has
  `CPPFLAGS` and an empty `cppflags`, Windows' variable names ignore
  case, and the build script got `RBCONFIG_CPPFLAGS` empty. bindgen then
  bound `rb_len_t` as `c_long`, magnus compiled, and the extension passed
  every length and index to Ruby as 32 bits where Ruby reads 64.
- **Plain cargo**, which the Rust tests and Clippy run, gives bindgen
  RbConfig's `CPPFLAGS`, binds `rb_len_t` as `i64`, and magnus 0.9.3
  does not compile: it casts each length `as c_long`.

Fixing only the Makefile makes magnus stop compiling; fixing only magnus
leaves a gem install mistyped. Both change here.

## Decided

### magnus, patched and vendored in the gem

`gems/url/vendor/magnus` is magnus 0.9.3 as crates.io serves it (the
`.crate` whose SHA-256 is the one `Cargo.lock` recorded,
40ef4244...c713), with Tokra's change: a crate-private alias `Len`,
which is `rb_sys::rb_len_t` on Ruby 4.1 and newer and `c_long` before,
and each length or index cast to it where magnus cast to `c_long`, in
`debug.rs`, `lib.rs`, `r_array.rs`, `r_hash.rs`, `r_regexp.rs`,
`r_string.rs`, `range.rs`, and `value.rs`. It is byte for byte the
folder Tokra carries. Where `rb_len_t` is `long`, which is everywhere
but RubyInstaller's 4.1 and 64-bit mswin, `Len` is `c_long`, so nothing
changes on Linux, macOS, or Ruby 4.0.

The gem's `Cargo.toml` takes it with `[patch.crates-io]` and excludes
`vendor` from the workspace, so it is never a member: Clippy, rustfmt,
and the Rust tests treat it as a dependency. `Cargo.lock` names it as a
path package, with no source or checksum, so `--locked` holds. The
gemspec ships `vendor`, so an installed gem, and a precompiled gem built
from the source gem, build the same. `vendor/REUSE.toml` gives the
folder magnus's MIT license and copyright, and ships with it, so the
package passes `reuse lint` on its own. RuboCop leaves it alone.

How a gem takes the patched magnus was weighed with all seven gems in
mind, since each needs it later:

- **A copy in each gem**, taken. An installed gem holds only its own
  folder, and Cargo resolves the `[patch]` path from the gem's own
  `Cargo.toml`, so whatever the gem builds from must sit inside
  `gems/<name>/` in the gem. A copy there is what the gem builds from,
  in the repository and installed, with nothing to generate and nothing
  that differs between a checkout and a package.
- **One copy at the root, linked from each gem.** A git symlink,
  `gems/url/vendor/magnus` to `../../../vendor/magnus`, would keep one
  copy in git, and RubyGems packs the files under a linked folder as
  plain files. Git for Windows checks a symlink out as a text file
  unless `core.symlinks` is set and the account may make links. Tokra
  takes ferro-url from its release tag as a Bundler git source, and
  Bundler checks that out with the machine's own git settings, so on
  such a Windows machine Cargo would find a file where the crate should
  be, and ferro-url would not build at all. A gem's build should not
  rest on a checkout setting.
- **One copy at the root, copied into each gem when it builds.** The
  copy would be git-ignored, and every path that builds a gem would
  have to make it first: each compile task, the Rust tests and Clippy,
  the packaging check, `release:<gem>:push`'s and `package:native`'s
  clean checkouts of a tag, Bundler's checkout of a git source, and a
  person's plain `cargo test`. Missing any of them builds against a
  stale copy or fails.
- **Patching Cargo's registry copy at build time**, which an installed
  gem cannot do without the network, and which `--locked` would not
  see. Tokra weighed and refused it for the same reasons.
- **A fork, or a git dependency on an unmerged branch**, refused: the
  change is carried, not forked, until magnus releases it.

So each gem that takes the fix carries its own copy, the same files. The
pin check (`tasks/pin_check.rb`) already fails when two gems lock
different magnus versions; it now lets a gem lock a path copy of the
version the others take from crates.io, and still fails a path copy of
another version, or two different registry or git sources. When magnus
releases the change, each gem's `vendor/` and `[patch]` go.

### rb_sys's Makefile, worked around in `extconf.rb`

`ext/ferro_url/extconf.rb`, on Windows, leaves every `RBCONFIG_` key
that differs from another only in case out of the Makefile, by setting
it to `nil` in `create_rust_makefile`'s `env` (rb_sys 0.9.130 writes no
line for a `nil` value: `mkmf.rb`, `env_line`). rb-sys then reads those
keys from RbConfig, as plain cargo does. The workaround ships in the
gem, so a gem install is sound too. It is Tokra's `ext/tokra/extconf.rb`
workaround as it stands. When an rb_sys release lists such keys itself
(Tokra's drafted rb-sys change), it goes.

`test/tasks/test_rbconfig_env.rb` writes ferro-url's real Makefile with
its real `extconf.rb` and reads the keys it exports: on Windows, none
that differs from another only in case; elsewhere, every RbConfig key,
as before.

### Windows, set up for the precompiled build

Ferro had no Windows setup. This adds the least a Windows machine needs
to build and test ferro-url and build its precompiled gem on the Ruby
Fledge embeds, ported from Tokra (plan 071) and through it from Fledge:

- `mise.precompiled.toml` pins, on Windows only, RubyInstaller's head
  build of 2026-11-10 from Fledge's copy, by its SHA-256, through mise's
  http backend; the MSYS2 packages of the two DLLs that build lacks; the
  MSYS2 with its UCRT64 compiler that ruby/setup-msys2-gcc built on
  2026-11-12; and `MSYS2_PATH`, `RI_DEVKIT`, `RUBY_DLL_PATH`, and the
  rest of what `ridk enable` sets (`.config/mise/windows-x64.env`).
  Linux and macOS keep 4.1.0-preview1. It needs mise 2026.10.11, since
  the `[env]` is a template.
- `bin/setup`, on Windows, installs mise.toml's Rust as the GNU host
  toolchain, libclang from PyPI's wheel, and clang's own headers
  (`bin/clang-headers`), and installs the bundle through
  `bin/windows-env`, which sets what CI's Windows job sets for Rust and
  bindgen. `mise.toml` leaves pre-commit off Windows, where mise
  installs it only through pipx.

Run there, from MSYS2's bash:

The gate stays on Ruby 4.0 on Windows, in CI, through setup-ruby.
Ferro's own `bin/setup` without `MISE_ENV=precompiled` still installs no
MSYS2 with a compiler on Windows, and `.githooks/pre-push` still runs
the gate there without `bin/windows-env`.

### What the workaround changes on Ruby 4.0

On RubyInstaller's Ruby 4.0, `CPPFLAGS` holds `-D_WIN32_WINNT=0x0600
-D__MINGW_USE_VC2005_COMPAT -D_FILE_OFFSET_BITS=64`, which bindgen lost
the same way. With the workaround bindgen gets them, as Ruby builds its
own extensions with them. CI's Windows job on Ruby 4.0 is the standing
check of that.
