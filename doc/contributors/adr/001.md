# ADR 001: Bind Each Crate in a Ferro Gem of Its Own, One to One

## Context and Problem Statement

Tokra ports Tauri to Ruby. Its plugins once carried their own Rust:
`tokra-clipboard` shipped a magnus binding over arboard. That put two jobs
in one gem. The binding answers to the crate: its types, errors, and edge
cases. The plugin answers to Tauri: its commands, wire formats, and
messages. Mixed together, neither had a clean answer key, and Tokra's
clipboard audit ([its plan 016](https://github.com/setdef/Tokra/blob/trunk/doc/contributors/plan/016.md))
found bugs in exactly that seam: a zero-size image reached arboard's macOS
backend unchecked and panicked the VM.

Where does the binding of a Rust crate live, and what does it answer to?

## Decision Drivers

* One answer key per layer: the crate for a binding, Tauri for a plugin.
* Rubyists who want a crate's binding and nothing of Tokra, such as a
  clipboard in a command-line tool.
* Two technical limits: a Rust value cannot enter another gem's Rust API,
  and some crates break when two copies share a process.

## Considered Options

1. A Ferro gem per crate, binding it one to one, with no Ruby-isms and no
   functionality the crate lacks; Tokra's plugins become pure Ruby over
   these gems.
2. Each Tokra plugin carries its own binding of the crate it wraps, as
   Tokra's ADR 006 had it before this decision.

## Decision Outcome

Chosen: option 1, because it alone gives each layer one answer key, and
it makes each binding usable outside Tokra. The record weighs option 2
only by the seam bugs the clipboard audit found.

Confidence: high that it works. Seven gems are bound, and Tokra's
clipboard, dialog, global-shortcut, and notification plugins build on
them.

The decision is staged. Crates that keep no process-wide state come
first. tao and wry stay in Tokra's own extension, and muda and tray-icon
wait with them, until a later decision settles where the windowing stack
lives. Until then, a crate that breaks as a second copy gets exactly one
native home.

### Consequences

* Good, because each gem has one answer key, its crate: a reviewer checks
  a binding against the crate's source at the locked version and nothing
  else.
* Good, because Tokra's plugins carry no Rust.
* Bad, because Tokra's plugins depend only on released Ferro versions, a
  published gem or a pushed release tag, so Ferro work comes first when a
  plugin needs a binding, and one change can span two repositories.
* Bad, because Ferro needs its own gate, docs, and agent instructions.
* Bad, because a window crosses from Tokra to a Ferro gem only as a raw
  handle, an Integer that nothing ties to the window's lifetime and that
  works only on the thread owning the window.

### Confirmation

The `audit-parity` skill reviews each change against the crate's source.
Each gem's tests run against the real crate, never a stub. The packaging
check loads each built gem outside the repository, on its own.
