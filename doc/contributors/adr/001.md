# ADR 001: What Ferro Is and How a Crate Becomes a Gem

## Status

Accepted. Restates, for Ferro's readers, the Ferro side of Tokra's
[ADR 011: Crate Bindings Move to Ferro](https://github.com/setdef/Tokra/blob/trunk/doc/contributors/adr/011.md),
accepted 2026-10-24. Where the two differ, ADR 011 governs until a later
Ferro ADR amends this one.

## Date

2026-10-24

## Context

Tokra ports Tauri to Ruby. Its plugins once carried their own Rust:
`tokra-clipboard` shipped a magnus binding over arboard. That put two jobs
in one gem. The binding answers to the crate: its types, errors, and edge
cases. The plugin answers to Tauri: its commands, wire formats, and
messages. Mixed together, neither had a clean answer key, and Tokra's
clipboard audit ([its plan 016](https://github.com/setdef/Tokra/blob/trunk/doc/contributors/plan/016.md)) found bugs in exactly that seam: a zero-size
image reached arboard's macOS backend unchecked and panicked the VM.

Ferro takes the first job. Each Ferro gem binds one Rust crate to Ruby one
to one, adding no Ruby-isms and no functionality the crate lacks. Tokra's
plugins become pure Ruby over Ferro gems, and Ferro stands on its own for
Rubyists who want a clipboard in a command-line tool and nothing of Tokra.

Two technical limits shape how far this goes.

1. **A Rust value cannot enter another gem's Rust API.** magnus checks every
   wrapped object against its own gem's type record, so handing one gem's
   wrapped object to another gem's method raises `TypeError` (magnus
   `r_typed_data.rs:380-400`). Plain Ruby values and byte strings cross
   freely, and so do raw window handles passed as Integers, which several
   crates take by design (wry and rfd take any `HasWindowHandle`; muda takes
   an `isize` HWND or a GTK window). A raw handle is unsafe, though: nothing
   tracks the window's lifetime, and it works only on the thread that owns
   the window.
2. **Some crates keep process-wide state.** Each extension keeps its Rust
   symbols private (rustc exports only `Init_*` and `ruby_abi_version`), so
   two copies of a crate never share code. The danger is state the
   operating system keeps once per process:

   | Crate | A second copy in the process |
   |---|---|
   | tao, every version | crashes: fixed Objective-C class names, and NSApp's one delegate |
   | tray-icon, every version | crashes: the fixed `TaoTrayTarget` class |
   | wry before 0.54.3 | crashes: fixed class names |
   | muda, with objc2 0.6.3 in either lockfile | crashes; on Windows, menu IDs also clash on a shared window |
   | global-hotkey | misroutes: on macOS the last copy swallows every hotkey |
   | notify-rust (macOS) | misroutes: each copy undoes the other's bundle hook and steals its delegate |
   | crossterm | misroutes: two copies race on stdin and terminal mode |

   arboard, rfd, open, os_info, sys-locale, auto-launch, keyring, image, and
   dirs keep no such state. A second copy of them, even at another version,
   is harmless.

Two pairs only work together: tray-icon takes muda's menu objects, and
ratatui takes crossterm's backend and shares its terminal state. muda's
keyboard accelerators on Windows also need the loop that owns the window to
call `TranslateAcceleratorW`.

## Decision

### 1. Standalone crates first; the windowing stack waits

Ferro binds crates with no colliding state and no coupling first: arboard,
rfd, and similar. global-hotkey and notify-rust also qualify, because
nothing else links them: Ferro becomes their one native home. tao and wry
stay in Tokra's own extension, and muda and tray-icon wait with them, until
a later decision settles where the windowing stack lives.

A crate in the table above gets exactly one native home: no two gems that
one app might load link it. The one-native-home crates are tao, tray-icon,
wry, muda, global-hotkey, notify-rust, and crossterm. tray-icon and muda
share one gem, as do ratatui and crossterm. RatatuiRuby links both today, so
a Ferro gem for them waits until RatatuiRuby can build on it instead.

Ferro binds crates that add something Ruby lacks. It skips crates that
duplicate the standard library or a popular gem, such as `serde_json`.

### 2. A gem mirrors its crate

Ruby the language comes first, then fidelity to the crate, then Ruby
culture. Rust constructs with no Ruby meaning are translated, never ported.

| Rust | Ruby |
|---|---|
| crate `arboard` | gem `ferro-arboard`, `require "ferro/arboard"`, module `Ferro::Arboard` |
| crate with a hyphen, `notify-rust` | gem `ferro-notify-rust`, `require "ferro/notify_rust"`, module `Ferro::NotifyRust`: the require path and module follow Cargo's library name, `notify_rust`, not RubyGems' hyphen-to-slash habit, which would invent a nesting the crate lacks ([plan 003](../plan/003.md)) |
| type, method, and variant names | kept: `Clipboard#get_text`, `ImageData`, `Error::ContentNotAvailable` |
| `Result<T, E>` | returns `T`, or raises |
| an error enum | an exception class per variant under the crate's `Error < StandardError`, with the crate's `Display` text as the message |
| `Option<T>` | `T` or `nil` |
| `String`, `&str`, `Cow<str>`, `impl Into<Cow<str>>` | `String` |
| `Vec<u8>`, `&[u8]`, `Cow<[u8]>` | binary `String` |
| `PathBuf`, `&Path`, `impl AsRef<Path>` | `String` |
| a struct with public fields | `Data.define` |
| a borrowing builder (`clipboard.get().text()`) | an object that holds its clipboard: `clipboard.get.text` |
| lifetimes, `self` consumption, `Send`/`Sync` bounds | dropped; documented where they change behavior |
| a Cargo feature | supported, built in |
| a `#[cfg(target_os)]` item or platform trait | defined only on that platform, so `respond_to?` answers |

The crate's rustdoc, examples, and tests are the answer key. Tests run
against the real crate, never a stub. A deviation the table does not cover
is a design call and gets written down in the gem's docs.

### 3. Each gem builds alone and links the same pins

Each gem is its own Cargo workspace with a committed `Cargo.lock`, built
with `--locked`. An installed gem compiles from its packaged files alone,
so `workspace = true` inheritance and a root lockfile would not ship.
During development the root Rakefile points every gem at one shared target
directory through `RB_SYS_CARGO_TARGET_DIR`, which rb-sys's generated
Makefile honors, so a dependency compiles once. A root check fails the gate
when two gems pin different magnus or rb-sys versions.

### 4. One repository of plain folders

Ferro is one repository with one gem per folder under `gems/`. Submodules
would split the history without making a gem clonable on its own, since
each gem still needs the root tooling. Commits use scoped Conventional
Commits, such as `fix(arboard): ...`, so `git log -- gems/arboard` reads
like the gem's own history.

### 5. Each gem versions and releases on its own

A gem's version answers to its own API, not the crate's, and the crate
version it binds appears in its README and gemspec metadata. Release tags
carry the gem name: `ferro-arboard/v0.1.0`. A root release task replaces
`bundler/gem_tasks`, whose `v0.1.0` tags would collide between gems.
Releasing stays a human step.

### 6. Each gem takes its crate's license; the shared code takes the copyleft one

A gem's Ruby and Rust code takes the license of the crate it binds:
`ferro-arboard` is `MIT OR Apache-2.0` because arboard is. That keeps a
binding as reusable as the code it binds.

Code that belongs to no crate follows RatatuiRuby's split. Shared code that
apps link at runtime is `LGPL-3.0-or-later`, so an app may use it without
taking on copyleft. Tooling that apps never link, such as the root
Rakefile, the gate's tasks, and any devtools gem, is `AGPL-3.0-or-later`.
Docs are `CC-BY-SA-4.0`, code snippets in docs are `MIT-0` so readers can
paste them freely, and lockfiles are `CC0-1.0`.

Tokra stays AGPL-3.0-or-later and depends on Ferro gems the way it depends
on any permissively licensed library.

### 7. Ferro owns no Ractor design

A Ferro gem exposes the crate's types as plain Ruby objects. It marks the
extension Ractor-safe only where the crate's types allow calls from any
thread, and it freezes and shares objects only where the crate's types are
`Sync`. Tokra's Ractor rules stay in Tokra's plugins, which decide where a
Ferro object lives.

### 8. Ferro supports every Ruby that still gets fixes, from 4.0 on

Ferro gems require Ruby 4.0 or later, and CI runs on each supported
release. When a new Ruby ships, Ferro adds it and keeps the older ones
until they reach end of life. Only then does the floor rise. Ferro uses no
Ruby 4.0 feature, so the floor could drop to 3.x later; dropping it never
breaks anyone, while raising it does.

### 9. How the repository carries this out

These follow from the decisions above and are recorded so a contributor
need not rediscover them.

- **Ruby owns the public API.** A gem's classes are Ruby, with RDoc and RBS;
  the native layer defines the wrapped types and private methods that reach
  the crate. Steep and RDoc can read Ruby, not Rust.
- **Panics never reach Ruby.** magnus turns a panic in a bound method into
  `fatal`, which no `rescue` catches. Every call into a crate runs under
  `catch_unwind`, and inputs the crate is known to panic on are refused
  with the crate's own error, as `ferro-arboard` refuses an image arboard
  would panic on with `ConversionFailure`.
- **Platform items follow the extension's `cfg`.** The native layer reports
  the platform it was built for, so the Ruby side defines a platform trait's
  module exactly where the crate compiles the trait.
- **The gate runs per gem and across all of them.** `rake gate:<gem>` while
  working, `rake` before a commit.

## Consequences

- Each gem has one answer key: its crate. A reviewer checks a binding
  against the crate's source at the locked version and nothing else.
- Tokra's plugins depend only on released Ferro versions, a published gem or
  a pushed release tag, so Ferro work comes first when a plugin needs a
  binding.
- `unsafe` beyond what magnus wrapping needs, such as marking an extension
  Ractor-safe or releasing the GVL, is allowed where a `SAFETY` comment
  cites the source that justifies it and a test fails without it.
- Any windowing option that splits crates across gems first needs Tokra on
  wry 0.54.3 or later and objc2 0.6.4 or later, the releases that stopped
  panicking on a second copy.
