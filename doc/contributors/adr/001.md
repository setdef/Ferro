# ADR 001: Bind Each Crate in Ferro, One to One, and the Windowing Stack in One Gem

## Context and Problem Statement

Tokra ports Tauri to Ruby. Its plugins once carried their own Rust:
`tokra-clipboard` shipped a magnus binding over arboard. That put two jobs
in one gem. The binding answers to the crate: its types, errors, and edge
cases. The plugin answers to Tauri: its commands, wire formats, and
messages. Mixed together, neither had a clean answer key, and Tokra's
clipboard audit ([its plan 016](https://github.com/setdef/Tokra/blob/trunk/doc/contributors/plan/016.md))
found bugs in exactly that seam: a zero-size image reached arboard's macOS
backend unchecked and panicked the VM.

Tokra's own extension grew the same seam. It binds tao, wry, muda, and
tray-icon, and it also holds Tauri's runtime logic, written in Rust. Tokra
is to ship no native extension: Tauri's logic becomes Ruby there, and the
crates under it need a binding somewhere.

Where does the binding of a Rust crate live, and what does it answer to?

## Decision Drivers

* One answer key per layer: the crate for a binding, Tauri for a plugin
  and for Tokra's runtime.
* Rubyists who want a crate's binding and nothing of Tokra, such as a
  clipboard in a command-line tool.
* Two technical limits: a Rust value cannot enter another gem's Rust API,
  and some crates break when two copies share a process.
* Tokra carries no Rust of its own.

## Considered Options

For a crate that stands alone:

1. A Ferro gem per crate, binding it one to one, with no Ruby-isms and no
   functionality the crate lacks; Tokra's plugins become pure Ruby over
   these gems.
2. Each Tokra plugin carries its own binding of the crate it wraps, as
   Tokra's ADR 006 had it before this decision.

For the windowing stack, tao, wry, muda, tray-icon, and window-vibrancy,
which hand each other Rust values, and of which tao and tray-icon crash as
a second copy:

* a. One Ferro gem with one native library, and a module per crate inside
  it.
* b. One native gem, and over it a Ruby gem per crate.
* c. The stack stays in Tokra's own extension, as the first stage of this
  decision left it.
* d. A gem per crate, each with its own native library, passing a window
  from one to the next as a raw handle.

## Decision Outcome

Chosen: option 1, with option a for the windowing stack.

Option 1, because it alone gives each layer one answer key, and it makes
each binding usable outside Tokra. The record weighs option 2 only by the
seam bugs the clipboard audit found.

Option a, because it is the only one that is sound, leaves Tokra without
Rust, and costs one release for a change. Option d is unsound: wry and
muda follow the window's pointer, and a stale or forged Integer crashes
the process. Option c keeps Rust in Tokra, and with it the seam between
the crates and Tauri's logic. Option b gives each crate a gem's name and
no independence: none of the five can be used from Ruby without tao out of
the same native library, installing any one compiles them all, and six
gems would release in lockstep. In option a each crate still has its own
module and its own answer key, which is what the first driver asks for.
What is given up is a gem named for each crate.

A Ferro gem holds none of Tauri's own behavior, the windowing gem
included.

Confidence: high that option 1 works. Seven gems are bound, and Tokra's
clipboard, dialog, global-shortcut, and notification plugins build on
them. Medium for option a: Tokra's extension already links the five crates
as one native library, which shows they work as one, but the gem is not
built, and options a and b were compared by reasoning, not by trial.

### Consequences

* Good, because each gem, and each module of the windowing gem, has one
  answer key, its crate: a reviewer checks a binding against the crate's
  source at the locked version and nothing else.
* Good, because Tokra's plugins carry no Rust, and Tokra itself carries
  none once the windowing gem replaces its extension.
* Bad, because Tokra depends only on released Ferro versions, a published
  gem or a pushed release tag, so Ferro work comes first when Tokra needs
  a binding, and one change can span two repositories and a release.
* Bad, because Ferro needs its own gate, docs, and agent instructions.
* Bad, because the windowing gem is the exception to a gem per crate: five
  crates share one version, one changelog, and one release, and its files
  carry different licenses.
* Bad, because the windowing gem and Tokra's extension can never load in
  one process, so Tokra changes over whole.
* Bad, because a one-to-one binding with its guards is more Rust than the
  extension it replaces. The Rust moves to Ferro and grows; what shrinks
  is Tauri's logic in Rust.
* Bad, because a window crosses from the windowing gem to another Ferro
  gem, such as ferro-rfd, only as a raw handle, an Integer that nothing
  ties to the window's lifetime and that works only on the thread owning
  the window.

### Confirmation

The `audit-parity` skill reviews each change against the crate's source.
Each gem's tests run against the real crate, never a stub. The packaging
check loads each built gem outside the repository, on its own. No check
yet enforces one native home for a crate that breaks as a second copy.
